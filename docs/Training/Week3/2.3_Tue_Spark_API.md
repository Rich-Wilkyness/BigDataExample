# Tuesday: Important PySpark DataFrame APIs

## Overview

PySpark has many methods, but data engineers repeatedly use a smaller group to read, inspect, clean, join, aggregate, order, partition, and write data. The important skill is not memorizing every method. It is predicting what each call returns, whether it is lazy, whether it can move data between partitions, and what finally triggers execution.

This guide focuses on the PySpark DataFrame API. RDDs remain useful for understanding Spark's foundations, but DataFrames and Spark SQL should normally be the first choice for structured data because Catalyst can analyze and optimize their plans.

## Learning objectives

After completing this guide, you should be able to:

- Distinguish a DataFrame transformation, action, lazy directive, and inspection operation.
- Classify common transformations as usually narrow, usually wide, or dependent on the physical plan.
- Use the common `functions`, `types`, `Window`, and `StorageLevel` APIs and explain what their calls return.
- Choose APIs in a sensible ETL order without assuming that source-code order is the final execution order.
- Explain Spark's ordering guarantees and write deterministic top-N or deduplication logic.
- Avoid common correctness and performance mistakes involving nulls, joins, collection, shuffles, and Python UDFs.
- Use `explain()` and the Spark UI to verify assumptions instead of relying only on a method's name.

## 1. The four questions to ask about every API

When you meet a new Spark API, ask these questions in order:

1. **What object does it belong to?** `DataFrame`, `Column`, `GroupedData`, `DataFrameReader`, and `DataFrameWriter` expose different operations.
2. **What does it return?** A new DataFrame is usually lazy. A Python value, displayed result, or completed write usually means execution occurred.
3. **Must rows move between partitions?** Row-local work is usually narrow; grouping or globally comparing rows is usually wide and causes a shuffle.
4. **What are the grain and ordering afterward?** An aggregation changes the meaning of one row, a join can multiply rows, and most operations provide no durable ordering guarantee.

```text
read source -> narrow cleanup -> join/aggregate/window -> final ordering -> action or write
                  |                    |
             usually pipelined    often a shuffle boundary
```

Spark may optimize this logical order. For example, Catalyst can push an eligible filter closer to a Parquet scan or choose a different join strategy. Your code defines the required result; the physical plan describes how Spark currently intends to produce it.

## 2. Core terms

| Term | Meaning |
| --- | --- |
| Transformation | A lazy operation that returns a new distributed DataFrame, such as `filter()` or `groupBy().agg()` |
| Narrow dependency | Each output partition can be computed from one parent partition, so a full redistribution is normally unnecessary |
| Wide dependency | An output partition needs rows from multiple parent partitions, so Spark normally performs an exchange or shuffle |
| Action | An operation that requests a result, side effect, or durable output and therefore executes the required lazy plan |
| Column expression | A symbolic calculation such as `F.col("quantity") * F.col("unit_price")`; it describes work and is not a Python scalar |
| Grain | What one output row represents, such as one transaction or one customer-day total |
| Ordering | The row sequence promised at a specific boundary; a DataFrame should be treated as unordered unless the final result explicitly requires ordering |

Two naming traps are worth learning immediately:

- `DataFrame.transform(function)` is a method for applying a reusable DataFrame-to-DataFrame function. The broader word **transformation** describes any lazy operation that creates a new dataset plan.
- `DataFrame.coalesce(4)` reduces partitions, while `F.coalesce("phone", "email")` returns the first non-null column value. They solve unrelated problems.

## 4. Quick API map

The classifications below describe the usual DataFrame behavior. Catalyst, Adaptive Query Execution, existing partitioning, the data source, and the surrounding plan can change the physical details. For DataFrame work, `explain()` and the Spark UI are authoritative.

### 4.1 Sources and inspection

| API | Purpose | Classification | Important note |
| --- | --- | --- | --- |
| `spark.read.schema(...).csv(...)` | Read CSV into a DataFrame | Lazy source-plan construction | Schema inference can require extra source work and can infer unsuitable types |
| `spark.read.parquet(...)` | Read Parquet into a DataFrame | Lazy source-plan construction | Projection and eligible filters may be pushed toward the scan |
| `spark.read.jdbc(...)` | Read a database table or query | Lazy source-plan construction | Parallel JDBC reads require deliberate partition-column bounds and connection limits |
| `df.printSchema()` | Display the resolved schema | Inspection operation | Does not process every data row |
| `df.explain("formatted")` | Display logical and physical plans | Inspection operation | Look for scans, filters, exchanges, sorts, and join strategies |
| `df.show(n)` | Display rows | Action | Bounded output still launches Spark work |

A source read is not called narrow or wide because it has no parent DataFrame dependency. It creates the starting point of a plan. Creating that plan is normally lazy, although schema resolution, file listing, catalog access, or source metadata checks may still contact external systems.

### 4.2 Usually narrow transformations

| API | Purpose | Classification | Important note |
| --- | --- | --- | --- |
| `select()` / `selectExpr()` | Choose or calculate columns | Narrow transformation | Prefer selecting only needed columns |
| `filter()` / `where()` | Keep matching rows | Narrow transformation | Use Column expressions and parenthesize compound conditions |
| `withColumn()` / `withColumns()` | Add or replace columns | Narrow when expressions are row-local | A window expression can make the resulting plan wide |
| `drop()` / `withColumnRenamed()` | Remove or rename columns | Narrow transformation | DataFrames are immutable; capture the returned DataFrame |
| `dropna()` / `fillna()` / `replace()` | Handle missing or known values | Usually narrow transformation | Treat null, `NaN`, empty text, and invalid text as different cases |
| `F.when(...).otherwise(...)` | Conditional column logic | Narrow column expression | Omitting `otherwise()` produces null for unmatched rows |
| `F.trim()`, `F.upper()`, `F.regexp_replace()` | Clean strings | Narrow column expressions | Built-in functions stay visible to Catalyst |
| `cast()` / `try_cast()` | Convert a column type | Narrow column expression | Decide whether invalid values should fail, become null, or be quarantined |
| `F.explode()` | Turn array elements into rows | Narrow transformation | Changes grain and can greatly increase row count |
| `sample()` | Sample rows | Narrow transformation | Use a seed for repeatable training examples |
| `unionByName()` | Append rows by matching column names | Usually narrow transformation | Does not remove duplicates |
| `sortWithinPartitions()` | Sort rows inside each current partition | Narrow transformation | Does not create a global order |
| `coalesce(n)` | Reduce the number of partitions | Usually narrow transformation | A severe reduction can create poorly balanced or single-threaded work |

### 4.3 Usually wide or plan-dependent transformations

| API | Purpose | Classification | Why rows may move |
| --- | --- | --- | --- |
| `groupBy(...).agg(...)` | Produce one row per group | Wide transformation | All rows for a key must meet |
| `distinct()` | Remove duplicate complete rows | Usually wide transformation | Equal rows may begin in different partitions |
| `dropDuplicates(keys)` | Keep one row per key | Usually wide transformation | Equal keys may begin in different partitions |
| `orderBy()` / `sort()` | Create a global order | Wide transformation | Rows must be range-partitioned and sorted |
| `repartition(n, *columns)` | Redistribute rows into new partitions | Wide transformation | The redistribution is the purpose of the call |
| `repartitionByRange()` | Range-partition rows | Wide transformation | Rows move to their target ranges |
| `join()` | Combine matching rows | Plan-dependent transformation | A sort-merge join commonly shuffles both sides; a broadcast join sends the small side to executors |
| Window expression with `over(...)` | Calculate rank, lag, running total, and similar values | Usually wide transformation | Window keys must meet and ordered windows require sorting |
| `pivot()` | Turn distinct values into columns | Wide transformation | Grouping and aggregation shuffle data; omitting pivot values can add eager discovery work |
| `cube()` / `rollup()` | Produce multiple aggregation levels | Wide transformation | Multiple grouped results must be calculated |

`groupBy()` by itself returns a `GroupedData` builder. The DataFrame transformation becomes complete when an aggregation such as `.agg()`, `.count()`, or `.sum()` defines the output.

### 4.4 Actions, directives, and terminal operations

| API | Classification | Result or risk |
| --- | --- | --- |
| `show()`, `first()`, `head(n)`, `take(n)` | Actions | Return or display a bounded number of rows, but still execute required work |
| `count()` | Action | Usually processes the full required input; repeated counts can repeat the lineage |
| `collect()` | Action | Moves every result row into driver memory; safe only when the result is proven small |
| `toPandas()` / `toArrow()` | Actions | Materialize data outside the distributed DataFrame; driver memory is the boundary |
| `foreach()` / `foreachPartition()` | Actions | Task retries can repeat external side effects |
| `df.write...parquet(...)` / `saveAsTable(...)` | Terminal write operations | Execute the plan and create external output |
| `cache()` / `persist()` | Lazy storage directives | Mark computed partitions for reuse; an action must materialize them |
| `unpersist()` | Storage-management operation | Releases cached blocks when the reuse window ends |
| `explain()` | Plan inspection | Shows the plan without materializing the complete result |

The `df.write` property only returns a writer. A terminal call such as `.parquet(path)`, `.save()`, or `.saveAsTable(name)` performs the write and executes the DataFrame plan.

### 4.5 The `pyspark.sql.functions` API

This import appears in most PySpark DataFrame programs:

```python
from pyspark.sql import functions as F
```

`pyspark.sql.functions` is a Python module containing Spark's built-in SQL functions. `F` is only a short alias chosen by convention. The alias keeps expressions readable and prevents names such as `sum`, `max`, `filter`, and `round` from being confused with Python built-ins.

Most `F` calls return a lazy `Column` expression. A `Column` is not a local list or a single Python value. It is an instruction that Spark places inside a DataFrame plan:

```python
amount_expression = F.col("quantity") * F.col("unit_price")

# withColumn() places the Column expression into a new DataFrame plan.
with_amount = sales.withColumn("sales_amount", amount_expression)

# No data has been processed yet because no action has run.
```

An `F` function does not determine narrow versus wide behavior by itself. Its surrounding DataFrame operation provides the execution context:

| Expression and context | Usual classification | Reason |
| --- | --- | --- |
| `df.select(F.upper("region"))` | Narrow transformation | Each row can be changed independently |
| `df.withColumn("amount", F.col("quantity") * F.col("unit_price"))` | Narrow transformation | The expression needs only the current row |
| `df.groupBy("region").agg(F.sum("amount"))` | Wide transformation | Values for the same region must meet |
| `df.withColumn("rank", F.row_number().over(spec))` | Usually wide transformation | Window keys must meet and ordered windows require sorting |
| `large.join(F.broadcast(small), "id")` | Plan-dependent transformation | `F.broadcast()` supplies a join-strategy hint rather than a scalar expression |

#### Common function families

| Family | Common APIs | What they are commonly used for |
| --- | --- | --- |
| Columns and literals | `F.col()`, `F.lit()`, `F.expr()` | Refer to a column, create a constant, or write a SQL expression |
| Conditions and nulls | `F.when()`, `F.coalesce()`, `F.isnan()`, `F.nanvl()` | Conditional values and missing-number handling |
| Strings | `F.trim()`, `F.lower()`, `F.upper()`, `F.length()`, `F.concat_ws()`, `F.split()`, `F.regexp_extract()`, `F.regexp_replace()` | Normalize, parse, and combine text |
| Numbers | `F.abs()`, `F.round()`, `F.bround()`, `F.ceil()`, `F.floor()`, `F.pow()`, `F.greatest()`, `F.least()` | Arithmetic and numeric comparison |
| Dates and timestamps | `F.to_date()`, `F.to_timestamp()`, `F.year()`, `F.month()`, `F.date_add()`, `F.datediff()`, `F.date_trunc()` | Parse, extract, shift, compare, and bucket time values |
| Aggregates | `F.count()`, `F.countDistinct()`, `F.sum()`, `F.avg()`, `F.min()`, `F.max()`, `F.collect_list()`, `F.collect_set()` | Reduce multiple input rows into grouped metrics or collections |
| Arrays and maps | `F.array()`, `F.array_contains()`, `F.array_distinct()`, `F.element_at()`, `F.explode()`, `F.create_map()`, `F.map_keys()` | Construct, inspect, and expand collection columns |
| Structs and JSON | `F.struct()`, `F.from_json()`, `F.to_json()`, `F.get_json_object()` | Construct nested records and parse or serialize JSON |
| Analytic windows | `F.row_number()`, `F.rank()`, `F.dense_rank()`, `F.lag()`, `F.lead()` | Rank rows or compare them with other rows in a window |
| Hashing and identity | `F.sha2()`, `F.xxhash64()`, `F.monotonically_increasing_id()` | Hash values, distribute keys, or create partition-dependent identifiers |
| Join and plan hints | `F.broadcast()` | Suggest broadcasting a small DataFrame during a join |

The table is a practical starting set, not the complete module. Search the official functions reference before writing a Python UDF; Spark already supplies built-ins for many string, date, JSON, array, map, mathematical, statistical, and conditional operations.

#### Columns, literals, and SQL expressions

```python
projected = sales.select(
    F.col("sale_id"),                          # Reference an existing column.
    F.lit("training").alias("source_system"), # Add the same literal to every row.
    F.expr("quantity * unit_price").alias("sales_amount"),
)
```

`F.expr()` parses a SQL expression and returns a Column. It can be concise for SQL users, while `F.col()` expressions are often easier for Python tooling to compose and refactor. Both become part of the same Catalyst plan.

#### Conditions and null handling

```python
classified = sales.select(
    "sale_id",
    # Choose the first non-null value; this does not change partition count.
    F.coalesce(F.col("customer_id"), F.lit("UNKNOWN")).alias("customer_id"),
    F.when(F.col("unit_price").isNull(), F.lit("invalid"))
    .when(F.col("quantity") >= 3, F.lit("large"))
    .otherwise(F.lit("standard"))
    .alias("record_status"),
)
```

Use `Column.isNull()` and `Column.isNotNull()` for SQL nulls. Use `F.isnan()` for floating-point `NaN`. Null, `NaN`, an empty string, and invalid text are different data-quality states.

#### Strings and dates

```python
event_timestamp = F.to_timestamp("updated_at")

normalized = sales.select(
    "sale_id",
    F.upper(F.trim("customer_id")).alias("customer_id"),
    F.regexp_replace("region", r"[^A-Za-z]", "").alias("clean_region"),
    event_timestamp.alias("event_timestamp"),
    F.to_date(event_timestamp).alias("event_date"),
    F.year(event_timestamp).alias("event_year"),
)
```

Parsing functions depend on the supplied pattern and Spark's session time-zone configuration. Parse source timestamps deliberately and keep the original raw value when invalid records must be investigated.

#### Aggregation functions

```python
summary = clean_sales.groupBy("region").agg(
    F.count("*").alias("row_count"),            # Every row.
    F.count("unit_price").alias("priced_count"), # Non-null prices only.
    F.countDistinct("customer_id").alias("customers"),
    F.sum("sales_amount").alias("revenue"),
    F.avg("sales_amount").alias("average_sale"),
)
```

These functions return aggregate Column expressions. The surrounding `groupBy().agg()` changes the grain and normally introduces a shuffle. `F.collect_list()` and `F.collect_set()` can create very large per-key arrays, so use them only when each group's size is bounded.

#### Arrays and higher-order functions

```python
tagged = spark.createDataFrame(
    [(1, ["spark", "python", "sql"]), (2, ["python", "docker"])],
    ["course_id", "tags"],
)

prepared_tags = tagged.select(
    "course_id",
    F.size("tags").alias("tag_count"),
    # This F.filter() filters elements inside each array, not DataFrame rows.
    F.filter("tags", lambda tag: tag != F.lit("docker")).alias("data_tags"),
)

# explode() changes the grain from one row per course to one row per course-tag.
one_row_per_tag = tagged.select("course_id", F.explode("tags").alias("tag"))
```

Higher-order functions such as `F.transform()`, `F.filter()`, `F.exists()`, and `F.aggregate()` operate inside array or map columns while remaining Catalyst-visible. They are different from `DataFrame.transform()` and `DataFrame.filter()`.

#### JSON with an explicit schema

```python
from pyspark.sql import types as T

payload_schema = T.StructType(
    [
        T.StructField("customer_id", T.StringType(), True),
        T.StructField("quantity", T.IntegerType(), True),
    ]
)

events = spark.createDataFrame(
    [(1, '{"customer_id":"C001","quantity":2}')],
    ["event_id", "payload"],
)

parsed_events = events.select(
    "event_id",
    F.from_json("payload", payload_schema).alias("payload"),
).select(
    "event_id",
    "payload.*",  # Expand fields from the parsed struct.
)
```

`F.from_json()` returns null when the input cannot be parsed under its configured behavior. Parsing a field does not prove that required business fields are present or valid, so validate the resulting struct and quarantine invalid records.

#### Functions that deserve extra care

| API | Important caution |
| --- | --- |
| `F.first()` / `F.last()` as aggregates | The selected row can be nondeterministic after a shuffle; use an ordered window when “first” or “last” has business meaning |
| `F.collect_list()` / `F.collect_set()` | One large group can create a very large in-memory collection |
| `F.monotonically_increasing_id()` | Values are unique and increasing but not consecutive; they depend on partition IDs and record positions and are not stable business keys |
| `F.rand()` / `F.randn()` | Supply a seed for repeatable exercises with the same plan and partitioning, but do not treat pseudorandom output as a durable identifier |
| `F.broadcast(df)` | The DataFrame must fit safely in executor memory; the hint still requires network transfer of the small side |
| `F.udf()` | Crosses the Python/JVM boundary and can hide logic from Catalyst; prefer built-ins and SQL expressions when they can express the rule |

### 4.6 Other common PySpark imports

```python
from pyspark.sql import SparkSession
from pyspark.sql import Window
from pyspark.sql import functions as F
from pyspark.sql import types as T
from pyspark import StorageLevel
```

| Import | Main responsibility | Common use |
| --- | --- | --- |
| `SparkSession` | Application entry point for structured Spark APIs | Build or obtain `spark`, read data, run SQL, and access configuration |
| `functions as F` | Built-in SQL and DataFrame expressions | Clean, calculate, parse, aggregate, rank, and construct complex columns |
| `types as T` | Spark SQL data-type classes | Define explicit schemas and nested types |
| `Window` | Analytic-window specification builder | Define partitioning, ordering, and row/range frames for window functions |
| `StorageLevel` | Persistence policy constants | Choose memory, disk, serialization, and replication behavior for `persist()` |

#### `types as T`: explicit schemas

```python
from pyspark.sql import types as T

sales_schema = T.StructType(
    [
        T.StructField("sale_id", T.LongType(), True),
        T.StructField("customer_id", T.StringType(), True),
        T.StructField("quantity", T.IntegerType(), True),
        T.StructField("unit_price", T.DecimalType(12, 2), True),
        T.StructField("updated_at", T.TimestampType(), True),
    ]
)

raw_sales = (
    spark.read
    .schema(sales_schema)
    .option("header", True)
    .csv("data/sales.csv")
)
```

An explicit schema prevents accidental inference changes and documents the source contract. It does not replace checks for required values, valid ranges, uniqueness, or referential integrity.

#### `Window`: analytic context

```python
from pyspark.sql import Window

customer_history = Window.partitionBy("customer_id").orderBy("updated_at")

with_previous_price = sales.withColumn(
    "previous_price",
    F.lag("unit_price").over(customer_history),
)
```

`Window.partitionBy()` does not repartition a DataFrame immediately. It builds a window specification. When the specification is used by `F.lag()`, `F.row_number()`, or another window function, Spark normally needs to cluster matching keys and sort them.

Do not confuse the `Window` class with `F.window()`: `Window` defines analytic relationships among rows, while `F.window(timestamp, duration)` places timestamps into time buckets, commonly for streaming or time-based aggregation.

#### `StorageLevel`: persistence choices

```python
from pyspark import StorageLevel

# Keep reusable partitions in memory when possible and spill them to disk if needed.
reusable = enriched.persist(StorageLevel.MEMORY_AND_DISK)

reusable.count()  # First action materializes the persisted DataFrame.
reusable.unpersist()
```

Choose a storage level from evidence about reuse, recomputation cost, executor memory, serialization cost, and spill. Persistence is a performance decision, not a correctness or durable-storage guarantee.

#### Common name collisions

| Similar names | Difference |
| --- | --- |
| Python `sum(values)` vs. `F.sum("amount")` | Python sums local objects; Spark builds a distributed aggregate expression |
| `df.filter(condition)` vs. `F.filter("items", lambda ...)` | The DataFrame method filters rows; the function filters elements inside an array column |
| `df.transform(function)` vs. `F.transform("items", lambda ...)` | The DataFrame method composes pipeline functions; the SQL function transforms elements inside an array column |
| `df.coalesce(4)` vs. `F.coalesce("phone", "email")` | The DataFrame method reduces partitions; the SQL function chooses the first non-null value |
| `F.broadcast(df)` vs. `spark.sparkContext.broadcast(value)` | The first is a DataFrame join hint; the second distributes a reusable read-only Python value |
| `Window.partitionBy(...)` vs. `F.window("event_time", "5 minutes")` | The class creates an analytic window specification; the function creates time buckets |

## 5. A practical ETL ordering

Use this as a reasoning checklist, not as a rule that Catalyst must execute literally from top to bottom:

1. **Read with a known schema.** Establish names and types at the source boundary.
2. **Select needed columns.** Reduce unnecessary width early.
3. **Normalize and validate.** Trim keys, parse types, and separate invalid records before silently dropping them.
4. **Filter when semantics allow.** Fewer rows can make later shuffles and joins cheaper.
5. **Check key uniqueness and grain.** Do this before joins or deduplication hide a source problem.
6. **Join deliberately.** Know the expected relationship: one-to-one, many-to-one, or many-to-many.
7. **Aggregate or use windows.** Decide whether the grain should collapse or remain row-level.
8. **Repartition only for a measured reason.** Do not insert it after every transformation.
9. **Order only where a consumer requires order.** Global sorting is expensive and ordering is not an inherent DataFrame property.
10. **Run a bounded action or publish output.** Validate counts, keys, nulls, and totals at the appropriate boundaries.

Writing `filter()` earlier can make intent clearer, but Catalyst may push or reorder eligible expressions. Operations with nondeterministic expressions, Python UDFs, outer-join semantics, or possible errors can constrain optimization. Preserve correctness first and inspect the optimized plan second.

## 6. Short code examples

### 6.1 Select, clean, cast, and filter: narrow transformations

```python
clean_sales = (
    sales
    .select(
        "sale_id",
        F.trim("customer_id").alias("customer_id"),
        F.upper("region").alias("region"),
        F.col("quantity").cast("int").alias("quantity"),
        F.col("unit_price").cast("double").alias("unit_price"),
        F.to_timestamp("updated_at").alias("updated_at"),
    )
    # `&` combines Column conditions; each condition needs parentheses.
    .filter((F.col("quantity") > 0) & F.col("unit_price").isNotNull())
    # This expression is evaluated per row and preserves transaction grain.
    .withColumn("sales_amount", F.col("quantity") * F.col("unit_price"))
)

# No action has run yet; `clean_sales` contains a lazy plan.
```

Prefer one clear `select()` or `withColumns()` call when adding many independent columns. Repeated `withColumn()` calls can create an unnecessarily large logical plan.

### 6.2 Null checks and conditional logic

```python
classified = clean_sales.withColumn(
    "order_size",
    F.when(F.col("sales_amount") >= 25, F.lit("large"))
    .otherwise(F.lit("small")),
)

# Use isNull()/isNotNull(); `column == None` does not express normal Python equality.
missing_customer = sales.filter(F.col("customer_id").isNull())
```

SQL null represents an unknown or missing value. Ordinary equality does not match two nulls. Use null-safe equality, `left["key"].eqNullSafe(right["key"])`, only when treating two null keys as equal is truly part of the data contract.

### 6.3 Aggregate: wide transformation followed by an action

```python
regional_totals = clean_sales.groupBy("region").agg(
    F.count("*").alias("sale_count"),       # Counts rows, including rows with nulls elsewhere.
    F.sum("sales_amount").alias("revenue"),
)

# groupBy().agg() is lazy and usually wide; show() triggers the plan.
regional_totals.show()
```

`F.count("*")` counts rows. `F.count("unit_price")` counts only non-null values in that column. Choose based on the metric definition.

### 6.4 Join: classify it from the physical strategy

```python
# Alias both sides so duplicate column names remain understandable.
s = clean_sales.alias("s")
c = customers.alias("c")

enriched = s.join(c, F.col("s.customer_id") == F.col("c.customer_id"), "left").select(
    "s.*",
    F.col("c.segment"),
)

# Inspect whether Spark chose exchanges, SortMergeJoin, or BroadcastHashJoin.
enriched.explain("formatted")
```

If `customers` is verified to be small enough for every executor, a broadcast hint can avoid redistributing the large sales side:

```python
# This is a DataFrame join hint, not SparkContext.broadcast().
enriched = clean_sales.join(F.broadcast(customers), "customer_id", "left")
```

Before joining, check the key grain on both sides. Duplicate dimension keys can multiply fact rows even when the join runs quickly and successfully.

### 6.5 Deduplicate deterministically

```python
# Convenient, but it does not define which row survives for each sale_id.
one_arbitrary_row = sales.dropDuplicates(["sale_id"])

# Prefer an explicit business rule when the surviving row matters.
latest_first = Window.partitionBy("sale_id").orderBy(
    F.to_timestamp("updated_at").desc(),
    F.col("customer_id").asc_nulls_last(),  # Stable tie-breaker for this fixture.
)

latest_sale = (
    sales
    .withColumn("row_number", F.row_number().over(latest_first))
    .filter(F.col("row_number") == 1)
    .drop("row_number")
)
```

The window usually requires a shuffle by `sale_id` and a sort within each window partition. A truly deterministic rule needs enough tie-breaker columns to select one record uniquely.

### 6.6 Global order versus order inside partitions

```python
# Wide: produces a globally ordered result for the next consumer of this plan.
top_sales = clean_sales.orderBy(
    F.col("sales_amount").desc(),
    F.col("sale_id").asc(),  # Break ties deterministically.
).limit(10)

top_sales.show(truncate=False)  # Action.

# Narrow: sorts only inside each existing partition.
locally_sorted = clean_sales.sortWithinPartitions("customer_id", "sale_id")
```

Without `orderBy()`, `limit(10)` means “some ten rows,” not a deterministic top ten. `sortWithinPartitions()` can help a partition-local consumer, but concatenating its partitions does not create a global order. A later shuffle can also replace an earlier ordering, so apply the consumer's required order at the final boundary.

### 6.7 `coalesce()` versus `repartition()`

```python
# Usually narrow: reduce partitions after the data has become much smaller.
small_result = regional_totals.coalesce(2)

# Wide: redistribute by region for balanced keyed downstream work or output.
by_region = clean_sales.repartition(8, "region")

print(by_region.rdd.getNumPartitions())  # Metadata inspection for this DataFrame.
```

Do not use `coalesce(1)` merely to make one convenient output file on production-sized data. It reduces parallelism and can turn one task into a bottleneck. Spark writes one part file per output task because a distributed dataset is normally published as a directory of files.

### 6.8 Cache only a reused expensive result

```python
reusable = enriched.persist()

# First action computes the lineage and stores available partitions.
reusable.groupBy("segment").count().show()

# Second action can reuse the persisted partitions.
reusable.filter(F.col("sales_amount") >= 25).show()

# Release executor storage after the reuse window.
reusable.unpersist()
```

Caching a DataFrame used once usually adds storage and serialization work without a reuse benefit. Cached data is temporary executor state, not a durable published dataset.

### 6.9 Write: a terminal operation

```python
(
    regional_totals
    .write
    .mode("overwrite")
    .parquet("tmp/regional-totals")  # Executes the required transformations.
)
```

`overwrite` is convenient for a training path but is not automatically an atomic production-publication strategy. Production pipelines also need a rerun contract, validation, candidate output, commit behavior, retention, and recovery from a partial failure.

### 6.10 Reusable transformations with `DataFrame.transform()`

```python
def normalize_customer_id(df):
    # A reusable function accepts and returns a DataFrame.
    return df.withColumn("customer_id", F.upper(F.trim("customer_id")))


normalized = sales.transform(normalize_customer_id)
```

This pattern can make a pipeline easier to test and read. It does not force execution; the returned DataFrame remains lazy.

## 7. Ordering rules that prevent subtle bugs

1. **A DataFrame is not inherently ordered.** Partitioning, retries, shuffles, optimizer choices, and file discovery can change observed row order.
2. **`orderBy()` is global and expensive.** Use it when a consumer truly needs a total order, especially for a final report or deterministic top-N result.
3. **`sortWithinPartitions()` is local.** Every partition is sorted independently, but partition 0 is not necessarily entirely less than partition 1.
4. **Ordering ties need a tie-breaker.** `orderBy(F.desc("score"))` is not deterministic among equal scores; add a stable unique key.
5. **`groupBy()`, `distinct()`, joins, and repartitioning do not preserve a useful input order.** Apply required ordering after the last order-destroying step.
6. **File names and partition IDs are not business sequence.** A reader should apply its own `orderBy()` when sequence is part of its contract.
7. **Window ordering is scoped to each window partition.** It does not globally sort the returned DataFrame.

## 8. Common pitfalls

| Pitfall | Why it fails or hurts | Prefer |
| --- | --- | --- |
| `df.filter(df.a > 1 and df.b < 5)` | Python tries to reduce distributed Column expressions to one Boolean | `(F.col("a") > 1) & (F.col("b") < 5)` |
| `df.filter(F.col("x") == None)` | SQL null does not behave like a normal value | `F.col("x").isNull()` |
| Calling `df.drop(...)` without assignment | DataFrames are immutable | `df = df.drop(...)` or use a new descriptive variable |
| Repeated `collect()` or `toPandas()` | Moves distributed data to the driver and can exhaust memory | Aggregate or limit in Spark; collect only a proven bounded result |
| Counting after every line | Each action can recompute the complete lineage | Validate meaningful boundaries; persist only when reuse justifies it |
| Assuming every join is wide | Broadcast or existing distribution can change the strategy | Inspect the physical plan and runtime metrics |
| Broadcasting based only on compressed file size | The in-memory relation and concurrent executor use can be much larger | Measure the built relation and executor memory behavior |
| Joining without checking key uniqueness | Many-to-many matches can silently multiply rows | Profile key counts and reconcile input/output grain |
| Using `dropDuplicates(keys)` to select the “latest” row | The survivor is not chosen by a business ordering rule | Use `row_number()` with explicit descending time and tie-breakers |
| Assuming `union()` removes duplicates | Spark DataFrame union has `UNION ALL` behavior | Add `distinct()` only when deduplication is required and affordable |
| Confusing `F.coalesce()` with `df.coalesce()` | One chooses a non-null value; the other changes partition count | Identify whether the receiver is `functions` or a DataFrame |
| Using a Python UDF for built-in string, date, array, or math logic | Adds a Python boundary and can hide optimization opportunities | Search `pyspark.sql.functions` first |
| Calling `repartition()` after every step | Repeated full shuffles add network, disk, and serialization cost | Repartition for a specific measured downstream need |
| Using `coalesce(1)` for every write | Collapses write parallelism and creates a bottleneck | Keep multiple output partitions or compact as a separate measured step |
| Using `orderBy()` early and then joining or grouping | A later shuffle can discard the useful order | Sort at the final consumer boundary |
| `pivot()` without explicit expected values | Spark may discover distinct pivot values eagerly and create an unexpectedly wide schema | Supply a bounded known values list when the domain is controlled |
| Performing external writes inside `foreach()` | Task retries can repeat side effects | Use an idempotent sink or a supported writer with a commit protocol |

## 9. DataFrame, Column, and grouped result shapes

Many PySpark mistakes are object mismatches rather than syntax mistakes:

| Expression | Result shape | What normally comes next |
| --- | --- | --- |
| `df.select(...)` | `DataFrame` | Another transformation or an action |
| `F.col("amount") * 2` | `Column` expression | Place inside `select()` or `withColumn()` |
| `df.groupBy("region")` | `GroupedData` builder | `.agg(...)`, `.count()`, or another grouped aggregation |
| `df.groupBy("region").agg(...)` | `DataFrame` at a new grain | Validate, join, order, or write |
| `df.write.mode("overwrite")` | `DataFrameWriter` builder | `.parquet(...)`, `.save()`, or `.saveAsTable(...)` |
| `df.count()` | Python integer after execution | Use as a bounded metric, not as another DataFrame |
| `df.collect()` | Python list of `Row` objects after execution | Only local Python work on a proven small result |

PySpark DataFrames and pandas DataFrames are different objects. A pandas DataFrame cannot use PySpark APIs such as `F.broadcast()` or `.explain()`, and a PySpark DataFrame does not support every pandas method or in-place mutation pattern.

## 10. Choosing between aggregation and a window

| Requirement | Prefer | Resulting grain |
| --- | --- | --- |
| One total row per customer | `groupBy("customer_id").agg(...)` | One row per customer |
| Add each customer's total to every transaction | `F.sum(...).over(Window.partitionBy(...))` | One row per transaction |
| Keep the latest row per key | `row_number()` over an ordered window, then filter | One selected row per key |
| Rank rows inside each region | `rank()` or `row_number()` over a partitioned and ordered window | Original rows plus rank |

Both aggregation and window operations are commonly wide. The important difference is whether the output collapses the input grain or preserves it.

## 11. Verify assumptions with the plan

```python
candidate = (
    clean_sales
    .filter(F.col("region") == "WEST")
    .join(F.broadcast(customers), "customer_id", "left")
    .groupBy("segment")
    .agg(F.sum("sales_amount").alias("revenue"))
)

candidate.explain("formatted")
```

Look for:

- `FileScan`, `BatchScan`, or another source scan and which columns are read.
- `PushedFilters` or data-source filters where supported.
- `Exchange`, which normally signals redistribution.
- `BroadcastExchange` and `BroadcastHashJoin`, which confirm a broadcast strategy.
- `SortMergeJoin`, which normally requires compatible partitioning and sorting.
- `HashAggregate` stages around a grouped aggregation.
- `Sort` and whether it is global or partition-local.

An explain plan is planned evidence, not runtime evidence. Use the Spark UI and metrics to check task duration, shuffle bytes, spill, skew, input/output rows, and whether Adaptive Query Execution changed the final plan.

## 12. API selection checklist

Before considering a pipeline complete, answer these questions:

1. What does one input row and one output row represent?
2. Which calls are lazy, and which calls trigger execution?
3. Which operations may introduce an exchange or shuffle?
4. Can a join multiply rows, and are the join keys clean and unique where required?
5. How are null, invalid, duplicate, late, and empty values handled?
6. Does any data cross from executors into driver memory?
7. Is ordering required, and is it fully deterministic with tie-breakers?
8. Is a cached DataFrame reused enough to justify its storage cost?
9. Is the output partition count appropriate for both parallelism and file size?
10. Do the physical plan and Spark UI support your assumptions?

## 13. Knowledge check

1. Why is `groupBy().agg()` both lazy and usually wide?
2. Why is `show()` an action even when it displays only 20 rows?
3. What is the difference between `orderBy()` and `sortWithinPartitions()`?
4. Why can a join be wide in one plan and avoid shuffling the large side in another?
5. What is wrong with `dropDuplicates(["customer_id"])` when the requirement says to retain the newest customer record?
6. Why can `unionByName()` increase duplicate rows?
7. What is the difference between `F.coalesce("a", "b")` and `df.coalesce(2)`?
8. When can `collect()` be safe, and what evidence should support that decision?
9. Why might a chain of narrow transformations run in one stage?
10. Which plan operators would you inspect to verify a broadcast join and a shuffle aggregation?

## Key takeaways

- A transformation describes a new DataFrame; an action requests an observable result or output.
- Narrow and wide describe partition dependencies, not whether an API is lazy. Both narrow and wide transformations are lazy.
- The receiver and return type—DataFrame, Column, GroupedData, writer, or Python value—often explain how an API should be used.
- Joins and window expressions require physical-plan inspection because method names alone do not reveal all data movement.
- Ordering must be explicit, late in the pipeline, and complete enough to break ties when deterministic results matter.
- Grain, row-count changes, driver boundaries, and retry behavior are as important as syntax.
- Prefer built-in DataFrame and SQL functions, validate correctness boundaries, and use plans plus runtime metrics before tuning.
