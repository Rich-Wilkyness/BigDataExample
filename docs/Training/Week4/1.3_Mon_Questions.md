Kafka is best understood as a **distributed, durable, partitioned event log**. Producers append records, Kafka retains them, and consumers independently track how far they have read.

## 1. Why does Kafka use partitions?

A topic may contain more data or traffic than one broker, disk, or consumer can handle. Kafka divides the topic into partitions so that storage and processing can be distributed.

Partitions provide several benefits:

1. **Storage scalability:** Different partitions can live on different brokers and disks.
2. **Write scalability:** Producers can write to several partition leaders concurrently.
3. **Read scalability:** Different consumers in the same consumer group can process different partitions concurrently.
4. **Ordering:** Each partition is an ordered, append-only log. Kafka guarantees order within a partition, not across an entire multi-partition topic.
5. **Replication and recovery:** Partitions are the units that Kafka replicates and fails over.

Partition count therefore affects throughput and parallelism. For a standard consumer group, a topic with 12 partitions can use at most 12 consumers concurrently for that topic; additional consumers will normally be idle. More partitions provide more potential parallelism, but they also create more metadata, files, replicas, network activity, and ordering boundaries.

## 2. What determines which partition receives a record?

The producer normally makes the partition decision using the following precedence:

1. **Explicit partition:** If the producer specifies partition 2, the record is sent to partition 2.
2. **Custom partitioner:** An application can install custom routing logic, such as routing by region or customer tier.
3. **Keyed default routing:** If no partition is specified but the record has a key, the default producer hashes the serialized key to select a partition.
4. **Unkeyed default routing:** If neither a partition nor key is supplied, the modern producer uses sticky partitioning. It sends records to one partition long enough to build an efficient batch and then selects another.

Conceptually, keyed routing works like this:

```text
serialized key -> hash -> topic partition
```

The broker does not redistribute the record after the producer selects its partition. Adding partitions can also change where future keyed records are routed because the hash is mapped across a different number of partitions.

## 3. Why do message keys matter?

A message key is commonly the identity around which related records must stay together, such as `customer_id`, `order_id`, `account_id`, or `machine_id`.

For example:

```text
key=order-817 -> created -> paid -> packed -> shipped
                       all routed to the same partition
```

Under a stable partition count and partitioning configuration, records with the same serialized key are normally routed to the same partition. Because they share a partition, a consumer can observe them in partition order.

Keys also matter for:

1. **Stateful processing:** Aggregations and joins often need all events for one entity to reach the same processing task.
2. **Log compaction:** In a compacted topic, Kafka retains the latest known value for each key. A null value can act as a deletion tombstone.
3. **Data distribution:** A well-distributed key spreads work across partitions.

Keys must be selected carefully. A low-cardinality or heavily skewed key, such as `country`, may route a large share of the traffic to one partition. That partition becomes a **hot partition** while other partitions remain lightly used.

A key does not automatically provide a unique event ID, deduplication, or global ordering. Its primary jobs are routing, partition-scoped locality, and support for compaction.

## 4. What do serialization and deserialization mean?

Kafka transports record keys and values as bytes.

**Serialization** converts application data into bytes before the producer sends it:

```text
Python, Java, or Scala object -> serializer -> bytes -> Kafka
```

**Deserialization** converts those bytes back into meaningful data after a consumer reads them:

```text
Kafka bytes -> deserializer -> Python, Java, or Scala object
```

Common formats include:

- UTF-8 strings
- JSON
- Avro
- Protocol Buffers
- Raw binary data

Keys and values have separate serializers. For example, a key might be serialized as a string while the value uses Avro.

Producers and consumers must agree on the format. If a producer writes Avro but a consumer treats the bytes as JSON, deserialization fails. Production systems therefore normally define schemas, compatibility rules, and a controlled error path for malformed or incompatible records.

Kafka itself usually does not interpret the business meaning of a record value. It stores and transfers the serialized bytes, while producers and consumers own the format and schema contract.

## 5. Why do production clusters replicate partitions?

A partition stored on only one broker becomes unavailable, and may lose data, if that broker or disk fails. Replication places copies of each partition on multiple brokers:

```text
orders partition 0
├── broker 1: leader
├── broker 2: follower
└── broker 3: follower
```

A replication factor of three means three total copies: one leader and two followers. It is a common production configuration, although the correct number depends on durability, availability, and cost requirements.

Replication supports:

- Broker and disk failure tolerance
- Maintenance without intentionally stopping the entire topic
- Partition-leader replacement
- Rack or availability-zone resilience when replicas are correctly placed

Replication factor alone does not guarantee durable writes. It must be combined with appropriate producer acknowledgements, `min.insync.replicas`, replica placement, and leader-election settings. A common design is replication factor 3, `min.insync.replicas=2`, and producer `acks=all`.

Kafka's normal partition replication is also not automatically a complete cross-region disaster-recovery strategy. Cross-cluster replication and tested recovery procedures are separate architectural concerns.

## 6. What do partition leaders and followers do?

Every replicated partition has one active leader and one or more followers.

The **leader**:

- Accepts producer writes for that partition.
- Assigns offsets to new records.
- Normally serves consumer reads.
- Tracks which replicas are sufficiently caught up.

The **followers**:

- Fetch records from the leader.
- Reproduce the leader's log in the same order.
- Remain candidates for future leadership when sufficiently synchronized.

Kafka tracks sufficiently caught-up replicas in the **in-sync replica set**, or ISR. A slow, disconnected, or failed follower can be removed from the ISR until it catches up.

The leader/follower relationship is assigned per partition. One broker might lead partition 0, follow partition 1, and lead partition 2. Kafka spreads leadership across brokers to distribute client traffic.

## 7. What happens when a partition leader fails?

The recovery sequence is approximately:

1. Kafka's controller detects that the broker hosting the leader is unavailable.
2. The controller selects an eligible synchronized replica as the new leader.
3. Cluster metadata is updated.
4. Producers and consumers receive an error or discover the metadata change, refresh their metadata, and retry against the new leader.
5. The partition may be briefly unavailable during failure detection and leader election.

After the election, the partition is usually under-replicated until another follower catches up or a replacement replica is created.

If no eligible replica exists, Kafka faces an availability-versus-durability decision:

- With safe leader election, the partition remains unavailable until a suitable replica returns.
- With unclean leader election enabled, Kafka may elect an out-of-date replica, restoring availability at the risk of losing records.

Whether an acknowledged record survives also depends on how it was produced. A record acknowledged only by the failed leader has weaker durability than one accepted with `acks=all` under a suitable minimum ISR policy.

## 8. What do consumer groups accomplish?

A consumer group lets several consumer instances cooperate as one logical subscriber.

For a standard consumer group:

- Each assigned partition has at most one active consumer owner within that group.
- One consumer may own multiple partitions.
- Different consumers can process different partitions concurrently.
- Different consumer groups can independently read the same topic.

For example:

```text
orders topic: P0 P1 P2 P3

fulfillment group:
  consumer A -> P0, P1
  consumer B -> P2, P3

fraud-detection group:
  consumer C -> P0, P1, P2, P3
```

The fulfillment consumers divide the work between themselves. Fraud detection still receives the entire topic because it uses a different group.

Consumer groups therefore provide:

1. **Load balancing within one logical application:** Partitions are divided among the group's consumers.
2. **Publish-and-subscribe behavior between applications:** Separate groups receive and track the topic independently.

## 9. What does an offset represent?

An offset is the numerical position assigned to a record within one partition.

```text
partition 0: [offset 0] [offset 1] [offset 2]
partition 1: [offset 0] [offset 1]
```

Offset 2 in partition 0 is unrelated to offset 2 in partition 1. One Kafka record occurrence is located by the combination:

```text
topic + partition + offset
```

An offset is not:

- A global topic sequence number
- A timestamp
- A business-event identifier
- Proof that a downstream side effect succeeded

Consumers maintain a current position and may commit progress for their consumer group. A committed offset conventionally represents the **next record to read**. After successfully processing record offset 42, a consumer normally commits offset 43.

Kafka stores group offset commits in the replicated and compacted `__consumer_offsets` topic. If a consumer stops, another consumer can retrieve the group's committed position and resume the partition's work.

## 10. Why does consumer lag matter?

Consumer lag measures how far a consumer group is behind the available end of a partition:

```text
lag ≈ log-end offset - consumer's committed or current position
```

If Kafka receives 100,000 records per second while consumers complete only 70,000, the backlog grows by roughly 30,000 records per second.

Growing lag can mean:

- Consumers lack CPU, memory, or I/O capacity.
- A database, API, or other sink is slow.
- A hot partition is limiting progress.
- Consumers are failing or repeatedly rebalancing.
- Deserialization errors or poison records are blocking processing.
- Processing each record has become more expensive.

Lag matters because it can cause stale analytics, delayed alerts, delayed customer actions, and eventual data loss for that consumer if records expire from Kafka before it catches up.

Record-count lag should be paired with event age or end-to-end freshness. Ten unusually expensive records may be more serious than thousands of tiny records, and zero Kafka lag does not prove that a downstream database contains correct results.

## 11. What happens during a consumer-group rebalance?

A rebalance changes which consumer owns each partition. It can be triggered when:

- A consumer joins the group.
- A consumer shuts down or crashes.
- A consumer misses its membership or processing deadlines.
- The subscription changes.
- The number of topic partitions changes.
- Other group-assignment conditions change.

During the transition:

1. Existing owners may have partitions revoked or lost.
2. The group coordinator determines new assignments.
3. Consumers receive their new partitions.
4. Consumers resume from committed offsets or restored checkpoints.

The application must safely transfer both ownership and state. Before relinquishing a partition, a consumer may need to finish work, commit proven progress, flush state, and stop downstream writes. Otherwise, the new owner may replay records while a stale previous owner is still producing side effects.

Classic rebalances could pause the entire group. Kafka 4.x also supports the newer incremental consumer rebalance protocol, which reduces disruption by avoiding a global synchronization barrier. Kafka 4.x servers support the protocol, but consumers currently opt in with `group.protocol=consumer`.

## 12. Why does Kafka retain messages after they have been consumed?

Reading a Kafka record does not remove it. Consumption changes the consumer group's offset, not the partition log.

This design allows:

- Multiple independent groups to read the same records.
- A failed application to restart and replay data.
- A new application to process historical events.
- Engineers to repair a bug and recompute results.
- Backfills, audits, and incident investigations.
- Kafka to absorb traffic bursts while slower consumers catch up.

Ordinary retention is normally based on time or partition size, independently of whether a consumer has read the data. Compacted topics instead preserve the latest value for each key. A topic can also combine deletion and compaction policies.

Retention creates a recovery window, but it is not infinite unless deliberately configured that way. If a consumer remains behind longer than the available retention window, the records it still needs may no longer exist.

## 13. What is the difference between at-most-once, at-least-once, and exactly-once processing?

These terms describe the processing effects a pipeline can produce when failures and retries occur.

### 13.1 At-most-once: zero or one processing effect

Progress is recorded before processing, or failed work is not retried:

```text
commit offset -> process record
```

If the application crashes after committing the offset but before completing the work, the record is skipped after restart.

- **Advantage:** Replay does not create duplicates.
- **Risk:** Records or processing effects may be lost.

### 13.2 At-least-once: one or more processing attempts

Processing completes before progress is committed:

```text
process record -> commit offset
```

If the process writes to a database and then crashes before committing the Kafka offset, Kafka delivers the record again after restart.

- **Advantage:** Work is not silently skipped when the complete durability and retention configuration supports the guarantee.
- **Risk:** Duplicate processing or duplicate side effects can occur.
- **Typical protection:** Idempotent writes, unique event IDs, upserts, or explicit deduplication.

### 13.3 Exactly-once: one logical result despite retries

Exactly-once does not normally mean that a record travels across the network only once. Retries can still occur. It means those retries do not create more than one visible logical outcome.

Within a Kafka read-process-write pipeline, Kafka transactions can atomically commit:

- Output records
- Consumer offsets

Consumers using `read_committed` then avoid seeing aborted transactional output. Kafka Streams builds on these capabilities.

Exactly-once does not automatically extend to an arbitrary database, email service, payment API, or filesystem. The external sink must participate in a compatible transaction or provide idempotency, deduplication, or another coordinated commit design. Delivery semantics are therefore an **end-to-end pipeline property**, not merely a Kafka broker setting.

## 14. Why did Kafka move from ZooKeeper to KRaft?

Older Kafka clusters used ZooKeeper as a separate distributed system for cluster metadata and controller coordination. Operators therefore had to deploy, secure, monitor, upgrade, and troubleshoot both Kafka and ZooKeeper.

KRaft, meaning Kafka Raft metadata mode, moves the control plane into Kafka itself:

- Brokers handle event-data requests.
- KRaft controllers manage metadata and partition leadership.
- Controllers maintain a replicated metadata log using a Raft-based quorum.
- Kafka no longer depends on an external ZooKeeper cluster.

This gives Kafka one integrated metadata system, clearer broker and controller responsibilities, and a control plane designed for better scalability, consistency, and recovery.

Do not confuse two kinds of leader:

- A **partition leader** handles records for one data partition.
- The **active KRaft controller** coordinates cluster metadata and partition leadership.

Kafka 4.0 and later run only in KRaft mode. ZooKeeper mode was removed.

## 15. Where does Kafka fit into a larger real-time data architecture?

Kafka normally sits between event producers and one or more independently operated processing systems:

```text
Applications, devices, and database CDC
                  |
                  v
          Kafka producers/connectors
                  |
                  v
    Kafka: durable partitioned event log
      /              |               \
     v               v                v
stream processing  raw archive     application consumers
Spark/Flink/Streams lakehouse       alerts/services
     |               |                |
     v               v                v
aggregates/models  replay/history  databases/search/cache
```

Kafka's main architectural responsibilities are:

1. **Decoupling:** A producer publishes once without directly calling every downstream system.
2. **Buffering:** Kafka absorbs temporary differences between producer and consumer speeds.
3. **Durability and replay:** Retained data can be reread after failures, code changes, or the creation of a new consumer.
4. **Fan-out:** Fraud detection, analytics, archival, monitoring, and operational services can use separate consumer groups.
5. **Ordered event streams:** Records requiring relative order can be grouped by key within partitions.
6. **Integration:** Kafka Connect can move data between Kafka and external systems, while Kafka Streams, Spark Structured Streaming, or Flink can transform the streams.

A complete production architecture also needs schema governance, security, access controls, monitoring, dead-letter or rejection handling, capacity planning, data-quality checks, and downstream idempotency.

Kafka is normally the **event backbone**, not the entire platform. It does not replace databases, lakehouses, stream processors, observability systems, or serving layers. It connects them while preserving a durable event history.

## Key takeaways

1. Partitions provide distribution, parallelism, partition-scoped ordering, and a unit of replication.
2. Keys control record locality and often preserve per-entity order, but poor keys can create hot partitions.
3. Offsets identify positions within partitions; consumer groups use committed offsets to preserve independent progress.
4. Replicas and leader election improve availability, but durable acknowledgement requires a complete replication and ISR policy.
5. Lag and rebalances are operational signals that must be interpreted alongside processing latency, downstream health, and end-to-end freshness.
6. Delivery semantics depend on the producer, broker, consumer, processing state, offset or checkpoint policy, and destination system together.
7. Kafka connects real-time producers and consumers through retained, replayable event logs; it does not replace every processing or storage system.
