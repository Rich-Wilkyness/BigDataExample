## Overview

Your market producer generates trades, Kafka buffers them, and Spark calculates statistics or writes Parquet files. The next problem is making that data available for durable SQL analysis: comparing symbols, exploring historical trading activity, and sharing results with dashboards.

Snowflake is a managed cloud data platform that can store analytical tables and execute SQL against them. In this guide, it is the destination after your existing pipeline. You do not need to create an account, configure services, install packages, or run the example commands for this homework preparation.

This is a study guide, rather than a completed homework response. Use the explanations to write your own brief notes in [your answers file](3.2-wed-market/homework/answers.md).

## Mental model: storage, compute, and cloud services

| Layer | Responsibility | Market example |
| --- | --- | --- |
| Storage | Persists data in Snowflake-managed storage | Historical trades remain stored between queries |
| Compute | Executes work such as SQL queries and bulk loads | Calculates average price per symbol |
| Cloud services | Coordinates authentication, authorization, metadata, and query planning | Checks your permissions and resolves the requested table |

- **Storage** answers “Where is the data?” Snowflake organizes standard table data into compressed columnar micro-partitions.
- **Compute** answers “What resources perform the work?” User-managed virtual warehouses run ordinary analytical queries and bulk loading; some services use Snowflake-managed compute.
- **Cloud services** answers “How is the platform coordinated?” It manages the control functions around storage and execution.
- Separating these layers lets compute change while stored data remains available. Suspending a virtual warehouse does not delete the tables.

Source: [Snowflake key concepts and architecture](https://docs.snowflake.com/en/user-guide/intro-key-concepts).

### A query moving through the layers

```sql
SELECT symbol, AVG(price) AS average_price
FROM market_db.bronze.market_ticks
GROUP BY symbol;
```

Conceptually: Snowflake checks the session's access and plans the query, a selected virtual warehouse reads the needed table data, and the result returns to the client. The table is persistent; the returned average is a query result unless separately stored.

The names `market_db`, `bronze`, and `market_ticks` are example names chosen for this guide. `SELECT`, `FROM`, and `GROUP BY` are SQL syntax.

## Virtual warehouses: the compute resources

A **virtual warehouse** supplies compute for queries, bulk loading, and other supported operations. It does not contain your database or tables.

- You can select a warehouse for a session using `USE WAREHOUSE`.
- Warehouses have configurable sizes and can be suspended, resumed, and resized.
- Separate warehouses can run different workloads against the same stored tables.
- For example, a load warehouse and a dashboard warehouse can separate their compute workloads.
- Larger compute does not guarantee faster execution for every workload. File layout, query shape, and concurrency still matter.
- Auto-suspend stops idle warehouse compute; auto-resume starts it when eligible work arrives. Stored data remains, and storage still has its own cost.

```sql
-- Illustrative: assumes these warehouses already exist and your role can use them.
USE WAREHOUSE learning_wh;
SHOW WAREHOUSES;

-- Lifecycle commands to recognize; do not run for this preparation.
ALTER WAREHOUSE learning_wh SUSPEND;
ALTER WAREHOUSE learning_wh RESUME;
```

Memory aid: **a database organizes stored objects; a virtual warehouse performs work.** Source: [Overview of warehouses](https://docs.snowflake.com/en/user-guide/warehouses-overview).

## Databases, schemas, and tables

```text
Snowflake account
└── Database: market_db
    ├── Schema: bronze
    │   ├── Table: market_ticks
    │   └── Named stage: market_stage
    └── Schema: gold
        └── Table or view: market_summary

Virtual warehouse: learning_wh → computes against these objects
```

| Object | Meaning |
| --- | --- |
| Database | A named container for schemas |
| Schema | A namespace that groups objects such as tables, views, stages, and file formats |
| Table | Rows with declared columns and data types |
| View | A named query definition |
| Fully qualified table name | `database.schema.table`, such as `market_db.bronze.market_ticks` |

This hierarchy resembles your PostgreSQL database → schema → table organization. Snowflake can reference accessible tables across databases using three-part names within a query; a typical PostgreSQL connection queries one database, with schema-qualified names inside it. A Hive “database” often serves as the namespace directly above tables, so its naming hierarchy is not identical.

`bronze` and `gold` are organization choices, not required Snowflake keywords. They express the medallion conventions you have already studied.

```sql
-- Illustrative: assumes the database, schema, and table already exist.
USE DATABASE market_db;
USE SCHEMA bronze;
SHOW TABLES;
DESCRIBE TABLE market_ticks;
SELECT CURRENT_DATABASE(), CURRENT_SCHEMA(), CURRENT_WAREHOUSE();
```

Source: [Snowflake databases, tables, and views](https://docs.snowflake.com/en/user-guide/databases).

## Stages: the file boundary before loading

A **stage** identifies where data files are available for loading or unloading. A staged Parquet file and a row in a Snowflake table are different things: uploading a file does not automatically load it into a table.

| Stage type | Where the files live | How to think about it |
| --- | --- | --- |
| Internal | Snowflake-managed file storage | Upload local files into Snowflake's staging area |
| External | Supported cloud storage, such as S3, Azure, or Google Cloud Storage | A Snowflake object references a cloud location with access configuration |

For internal stages, recognize these references:

- `@market_stage`: a named stage.
- `@%market_ticks`: the table stage associated with `market_ticks`.
- `@~`: the current user's stage.
- The `@` prefix means a stage reference in this SQL context.

A named stage lives in a schema and can use a fully qualified name such as `@market_db.bronze.market_stage`. Sources: [Choosing an internal stage](https://docs.snowflake.com/en/user-guide/data-load-local-file-system-create-stage) and [CREATE STAGE](https://docs.snowflake.com/en/sql-reference/sql/create-stage).

### Connecting this to your actual files

Your Spark writer produced paths like:

```text
/tmp/market-lake/spark/market_ticks/
└── event_date=2026-10-01/
    └── event_hour=16/
        └── part-....snappy.parquet
```

Those files currently live on your Mac. Snowflake runs in the cloud and cannot directly read your Mac's `/tmp` directory. A client must upload them into an internal stage, or transfer them to cloud storage referenced by an external stage.

The directory partitions are a property of your Spark output. Loading the file into a standard Snowflake table does not reproduce those folders as Snowflake's internal micro-partitions. Also, Spark normally places partition values in directory names rather than inside each Parquet file. A later loader must preserve or derive `event_date` and `event_hour`, for example from `exchange_ts` or source-file metadata.

## `COPY INTO`: staged files become table rows

This direction loads a table:

```text
Local Parquet file → upload → internal stage → COPY INTO → Snowflake table
```

The following is an **illustrative sequence to read**, not a task to execute now. It assumes `market_db`, `bronze`, `learning_wh`, and a compatible target table already exist, and your role has the required privileges. The file path is a placeholder for one actual file.

```sql
USE WAREHOUSE learning_wh;
USE DATABASE market_db;
USE SCHEMA bronze;

CREATE STAGE market_stage
    FILE_FORMAT = (TYPE = PARQUET);

-- Run through a client supporting local file upload, such as the Python connector.
PUT 'file:///tmp/market-lake/spark/market_ticks/event_date=2026-10-01/event_hour=16/part-example.snappy.parquet'
    @market_stage
    AUTO_COMPRESS = FALSE;

LIST @market_stage;

COPY INTO market_ticks
FROM @market_stage
FILE_FORMAT = (TYPE = PARQUET)
MATCH_BY_COLUMN_NAME = CASE_INSENSITIVE
ON_ERROR = ABORT_STATEMENT;

SELECT COUNT(*) FROM market_ticks;
```

Read each operation separately:

- `CREATE STAGE` defines a named internal stage and its default file format.
- `PUT` transfers the local file; it does not insert table rows. `AUTO_COMPRESS = FALSE` avoids wrapping an already compressed Parquet file in additional upload compression.
- `LIST` checks which files are present at the stage.
- `COPY INTO market_ticks` reads staged files and loads the target table.
- `MATCH_BY_COLUMN_NAME` matches file fields to compatible table columns by name. It does not create the table or solve every schema mismatch.
- `ON_ERROR = ABORT_STATEMENT` makes a loading error fail the statement rather than intentionally skipping bad data.
- The final query checks table row count, which must still be reconciled with expected inputs.

The client executing `PUT` must have access to the local path. SQL text sent through a cloud-only API does not grant that service access to your laptop. Sources: [PUT](https://docs.snowflake.com/en/sql-reference/sql/put), [COPY INTO a table](https://docs.snowflake.com/en/sql-reference/sql/copy-into-table), and [Python connector examples](https://docs.snowflake.com/en/developer-guide/python-connector/python-connector-example).

There is also a `COPY INTO <location>` form that unloads query results into files. Look at the target to tell whether data is entering a table or leaving one. Source: [COPY INTO a location](https://docs.snowflake.com/en/sql-reference/sql/copy-into-location).

## Snowpipe: continuously load new files

Snowpipe uses Snowflake-managed compute to load staged files as new work is submitted. A **pipe** stores the loading definition, based on a `COPY INTO` statement.

```text
Spark → Parquet files → cloud storage / stage
                              ↓
                    file-arrival notification
                              ↓
                         Snowpipe → table
```

- Supported cloud event notifications can trigger automated loading.
- An application can alternatively notify Snowpipe through its REST API.
- Files must already be staged; notifications do not upload local file contents.
- Snowpipe does not require your user-managed warehouse for ingestion. Queries against the loaded table generally still use a warehouse.
- “Continuous” describes ongoing ingestion; it does not promise that each incoming Kafka event becomes a queryable row instantly.

Illustrative pipe definition, assuming the stage and table exist:

```sql
CREATE PIPE market_pipe AS
COPY INTO market_ticks
FROM @market_stage
FILE_FORMAT = (TYPE = PARQUET)
MATCH_BY_COLUMN_NAME = CASE_INSENSITIVE;
```

This definition alone does not configure automatic cloud notifications. Sources: [Snowpipe overview](https://docs.snowflake.com/en/user-guide/data-load-snowpipe-intro) and [CREATE PIPE](https://docs.snowflake.com/en/sql-reference/sql/create-pipe).

## Snowpipe Streaming: ingest rows directly

Snowpipe Streaming accepts rows through supported SDKs, REST APIs, or integrations. Applications do not need to create and stage Parquet files first.

```text
Kafka → processing engine / ingestion client → Snowpipe Streaming → table
```

- The high-performance architecture supports Python, Java, and other client paths; older material may describe its classic architecture.
- A channel is a logical ingestion path. **Named Channels** support ordered ingestion and recovery using offset tokens; **Elastic Channels** provide at-least-once delivery without ordering guarantees.
- Sending a row and making it queryable are separate milestones. Delivery guarantees depend on the channel and correct recovery behavior.
- Retain Kafka when buffering, replay, or multiple consumers are useful. Direct ingestion does not make those needs disappear.

Source: [Snowpipe Streaming overview](https://docs.snowflake.com/en/user-guide/snowpipe-streaming/data-load-snowpipe-streaming-overview). APIs evolve; use documentation for the architecture and SDK version selected for a future implementation.

### Choose the path by the input boundary

| Mechanism | Application supplies | Ingestion compute | Useful starting case |
| --- | --- | --- | --- |
| Bulk `COPY INTO` | Staged files | Selected user-managed warehouse | A bounded load or scheduled file batch |
| Snowpipe | Staged files plus notifications or REST requests | Snowflake-managed | Continuously arriving files |
| Snowpipe Streaming | Rows through a supported client or integration | Snowflake-managed | Direct event ingestion |

For your existing Parquet branch, the next step is file transfer plus `COPY INTO` or Snowpipe. Choosing Snowpipe Streaming would change the ingestion branch to send rows. It does not load your existing Parquet directory. Source: [Overview of data loading](https://docs.snowflake.com/en/user-guide/data-load-overview).

## Important SQL commands and APIs

### SQL reference

| Command or API | What it does | When you would use it |
| --- | --- | --- |
| `USE WAREHOUSE`, `USE DATABASE`, `USE SCHEMA` | Set session context | Before loading or querying the intended objects |
| `SHOW WAREHOUSES`, `SHOW TABLES`, `DESCRIBE TABLE` | Inspect available resources and schema | Diagnose context or type mismatches |
| `CREATE STAGE`, `LIST @stage` | Define and inspect a file landing location | Prepare or inspect file ingestion |
| `PUT` | Upload client-local files to an internal stage | Move your Mac's Parquet files into staging |
| `COPY INTO <table>` | Load staged files into a table | Perform a bulk load |
| `CREATE PIPE`, `SYSTEM$PIPE_STATUS('pipe_name')` | Define a pipe and inspect its status | Understand and monitor Snowpipe |
| `SELECT`, `GROUP BY`, `COUNT`, `AVG`, `SUM` | Query stored rows | Recalculate your market statistics in SQL |

`COPY INTO` is a Snowflake SQL loading command, not a Python filesystem copy. A pipe is a Snowflake object, not a Kafka topic or a running Spark query. See [SYSTEM$PIPE_STATUS](https://docs.snowflake.com/en/sql-reference/functions/system_pipe_status) for its monitoring fields.

### Python and HTTP interfaces

| Interface | Important operations to recognize | Boundary |
| --- | --- | --- |
| Snowflake Connector for Python | `snowflake.connector.connect()`, `connection.cursor()`, `cursor.execute()`, `cursor.fetchall()` | Your Python client connects, submits SQL, and retrieves results |
| Snowflake SQL API | `POST /api/v2/statements` | An HTTP client submits SQL; this is not the row-streaming API |
| Snowpipe REST API | `insertFiles`, `insertReport`, `loadHistoryScan` | Submit staged filenames or inspect file-ingestion reports |
| Snowpipe Streaming Python SDK | Client/channel operations for appending rows and tracking progress | Direct row ingestion; consult the current SDK reference |
| Snowpipe Streaming REST API | Open a Named Channel, append rows, inspect committed progress | Direct row ingestion with architecture-specific endpoints |

Minimal connector example to understand, not run now:

```python
import snowflake.connector

# Assumes an approved connection profile named "market_learning" already exists.
with snowflake.connector.connect(connection_name="market_learning") as connection:
    with connection.cursor() as cursor:
        cursor.execute("SELECT symbol, price FROM market_db.bronze.market_ticks LIMIT 5")
        rows = cursor.fetchall()
```

- `connection` represents a Snowflake session, not the table data itself.
- `execute` submits the SQL; Snowflake performs the query.
- `fetchall` returns the result rows to your Python process. Use bounded results while learning.
- Connection profiles and authentication are future setup work. No credentials are included here.

Sources: [Python connector examples](https://docs.snowflake.com/en/developer-guide/python-connector/python-connector-example), [Python connection profiles](https://docs.snowflake.com/en/developer-guide/python-connector/python-connector-connect), [SQL API](https://docs.snowflake.com/en/developer-guide/sql-api/intro), [Snowpipe REST endpoints](https://docs.snowflake.com/en/user-guide/data-load-snowpipe-rest-apis), [Snowpipe Streaming Python SDK reference](https://docs.snowflake.com/en/user-guide/snowpipe-streaming-sdk-python/reference/latest/index), and [Streaming REST endpoints](https://docs.snowflake.com/en/user-guide/snowpipe-streaming/snowpipe-streaming-high-performance-rest-api).

## Requirements, data ownership, and boundaries

- **Grain:** one raw `market_ticks` row represents one trade event. One summary row represents a symbol's aggregate, so it has a different grain.
- **Event time:** keep `exchange_ts` when loading, even if ingestion happens later. Specify UTC consistently before deriving hourly groups.
- **Identity:** the classroom API restarts its sequence counter when restarted. Sequence alone is therefore not a durable global event ID; a later pipeline needs a stable identity contract, such as a source-run ID plus sequence or Kafka topic/partition/offset.
- **Replay:** Kafka retains events according to broker policy; exported Parquet files provide another replay source while retained. Snowflake stores loaded analytical data under its own lifecycle.
- **Schema ownership:** the producer defines event fields, the file writer defines exported fields, and the target table defines accepted columns and types. These contracts must agree.
- **Freshness:** this exercise has no measured Snowflake latency or throughput target. Any future design must distinguish event occurrence, file creation, upload, ingestion, and query visibility.
- **Access boundary:** permissions to use compute, read a stage, and load or query a table are separate requirements.

## Failure model and recovery

| Failure | What to inspect | Recovery principle |
| --- | --- | --- |
| A local file never arrives in the stage | Upload result and `LIST` output | Confirm transfer before requesting ingestion |
| A load fails because fields or types differ | Target schema, file schema, and loading errors | Repair the contract and reconcile accepted versus rejected rows |
| A request succeeds but the client loses the response | Load history or committed streaming progress | Determine what committed before retrying |
| A replay repeats events under new filenames | Event identities and source totals | Deduplicate by a deliberate identity contract |
| A query uses the wrong database or schema | Session context and qualified object names | Verify the intended target before interpreting results |

File-load metadata helps avoid reloading known files, within the documented tracking rules. It is not permanent business-event deduplication: identical trades can arrive in different files, and forced reloads can duplicate data. Streaming recovery likewise needs the selected channel's progress protocol. Source: [COPY INTO loading behavior](https://docs.snowflake.com/en/sql-reference/sql/copy-into-table).

## Data quality, testing, and evidence

When you eventually run a bounded load, check more than whether a command returned success:

- Reconcile expected source events with loaded rows and rejected records.
- Compare counts and total volume per symbol with the same bounded input set. Two live consumers may process different offsets, so matching their totals is not automatic.
- Check nulls, numeric types, event timestamps, and duplicate identities.
- Confirm that partition fields are retained or derived correctly rather than silently becoming null.
- Record the warehouse, target table, files or offsets, errors, and timing used for the check.

## Common pitfalls

- Calling a virtual warehouse “storage”: it provides compute.
- Treating a stage as a table: staged files still need loading.
- Expecting Snowflake to see `/tmp` on your laptop: upload or cloud transfer is required.
- Assuming a file landing in cloud storage automatically loads: the ingestion trigger must be configured.
- Treating Snowpipe and Snowpipe Streaming as interchangeable: their inputs are files versus rows.
- Confusing Snowflake **Streams** with Snowpipe Streaming: Streams track changes to table data; Snowpipe Streaming ingests rows from clients. See [Introduction to Streams](https://docs.snowflake.com/en/user-guide/streams-intro).
- Assuming Streamlit requires JSON: a dashboard can query Snowflake and display returned data instead.
- Treating a successful upload, ingestion acknowledgement, and queryable row as the same milestone.

## Production considerations

- **Small files:** your two-second classroom writer creates many files. A future pipeline should measure file sizes and load overhead, then balance freshness against batching or compaction.
- **Compute and concurrency:** choose workload isolation and warehouse sizes using actual query and queueing evidence.
- **Cost:** storage, warehouse compute, managed ingestion, and other services have different cost drivers. Suspending one warehouse does not eliminate all platform charges.
- **Recovery:** keep source identity, checkpoint or ingestion progress, and retained replay inputs consistent.
- **Observability:** monitor failed loads, backlog, accepted/rejected rows, freshness, query duration, and compute usage.
- **Permissions:** give an ingestion client access to its intended stages and tables, and keep authentication outside source code.

These are future design considerations, not additional homework configuration tasks. Source for service cost categories: [Understanding overall cost](https://docs.snowflake.com/en/user-guide/cost-understanding-overall).
