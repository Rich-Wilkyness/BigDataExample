## Part 6 — Architecture Questions

Answer each in approximately 2–4 sentences:

1. What is the difference between a Snowflake **database, schema, table, stage, and virtual warehouse**?
    - A database contains schemas, and a schema organizes objects such as tables and stages. A table stores data in rows and columns, while a stage stores files in Snowflake or references files in external cloud storage.
    - A virtual warehouse provides the compute resources used to run queries and load data; it does not store the table data itself. 
2. If you suspend a virtual warehouse, what happens to the data stored in your Snowflake tables?
    - The data stays in Snowflake storage because storage and compute are separate.
    - Suspending the warehouse stops its compute resources, but it does not delete the tables or their data. 
3. Why can two different warehouses query the same table?
    - Both warehouses can access the same centrally stored data because the table is not tied to one warehouse.
    - Each warehouse supplies its own compute resources, so different workloads can query the same table independently as long as the users have the required permissions. 
4. What is the difference between an **internal stage** and an **external stage**?
    - An internal stage stores files in storage managed by Snowflake, like the stage used for my game sessions CSV.
    - An external stage references files stored outside Snowflake in a cloud storage location such as Amazon S3, Azure Blob Storage, or Google Cloud Storage. 
5. Why is `COPY INTO` preferable to manually inserting thousands of CSV rows?
    - `COPY INTO` loads rows directly from staged files instead of requiring a separate manually written insert for each row.
    - It supports bulk loading with file format settings, error handling, and load results, making large file loads easier to manage and verify.
6. What is a micro-partition, and what does **partition pruning** mean?
    - A micro-partition is a small storage unit that Snowflake automatically creates for table data, with metadata such as the minimum and maximum values in its columns.
    - Partition pruning uses that metadata to skip micro-partitions that cannot match a query's filters, reducing how much data needs to be scanned. 
7. What is the difference between **Time Travel** and **zero-copy cloning**?
    - Time Travel lets me query earlier data or restore dropped objects within the configured retention period.
    - Zero-copy cloning creates a separate object that initially shares the original data storage instead of copying all the data. Changes to a cloned table do not change the original table, and changed data can require additional storage.
8. What is the difference between Snowflake's **result cache** and a warehouse's **local data cache**?
    - The result cache stores completed query results, allowing Snowflake to reuse them without running the query again when reuse conditions are met.
    - A warehouse's local data cache stores table data that it has read, helping later queries access that data faster while still executing the queries. Suspending the warehouse drops its local data cache but does not clear the separate result cache.
9. What problem do **Streams and Tasks** solve?
    - A Stream tracks changes to a table, allowing a pipeline to process new or changed rows instead of repeatedly processing the whole table.
    - A Task runs SQL or a stored procedure on a schedule or when triggered, so the processing can happen automatically. Together, they support incremental pipelines such as updating Silver data when Bronze data changes. 
10. How are **Dynamic Tables** different conceptually from explicitly scheduling a series of SQL transformations?
    - With a Dynamic Table, I define the query that produces the table and a desired freshness target using `TARGET_LAG`.
    - Snowflake manages refreshes and dependencies to try to meet that target, instead of requiring me to write and schedule each processing step myself. 
11. In a production system, why might data arrive through something like Snowpipe, Fivetran, Kafka, or another ingestion system rather than through a manually uploaded CSV?
    - Production data arrives repeatedly and can come from many systems, so uploading every file by hand would be slow and difficult to maintain.
    - An ingestion pipeline automates delivery and can provide monitoring, retries, and timely updates depending on the tools and configuration. For example, Snowpipe can automatically load new staged files instead of waiting for someone to upload and load each batch manually. [
12. In today's dbt demonstration, what was the difference between `source()` and `ref()`?
    - `source()` points to a table that already exists in the database. It uses a YAML file to define the table's database, schema, and name. 
    - `ref()` points to a model managed by dbt, which can be built as a table or view. It allows for dependency management and ensures models are built in the correct order.
