# Part 2 — Theory: Sources, Models and DAGs

Review the concepts from today's demonstration.

A **source** represents data that already exists in the database/warehouse:

```sql
{{ source('raw', 'orders') }}
```

A **model** represents a transformation managed by dbt.

Models can reference other models:

```sql
{{ ref('silver_orders') }}
```

These dependencies allow dbt to construct a **Directed Acyclic Graph (DAG)**.

For example:

```text
RAW.ORDERS
     ↓
STG_ORDERS
     ↓
SILVER_ORDERS
   /       \
  ▼         ▼
ORDER_TOTAL SHIPPING_STATS
```

### Be prepared to answer

- What is a dbt source?
    - data that you plan to transform that is located in the snowflake warehouse.
    - **addition**: Your description fits this Snowflake project. More precisely, a source is a YAML declaration of an existing database table or view, usually loaded by another process. Declaring it does not load data; dbt also supports platforms besides Snowflake.
- What is a dbt model?
    - a single model represents a stage of transformation, the model directory represents all of the transformations
    - **addition**: For this SQL project, a model is a named SQL transformation defined in a `.sql` file, usually with a `SELECT`. Its materialization determines how dbt represents the result. The models directory organizes these files; it does not determine execution order.
- What is the difference between `source()` and `ref()`?
    - source() is used to access a source file located in the warehouse
    - ref() is used to access other model files from the dbt repo
    - **correction**: `source()` resolves a declared source table/view in the warehouse; it does not read a source file. `ref()` resolves a dbt resource, usually another model, to its database relation. Both also register dependencies; neither simply opens a repository file.
- What is a DAG?
    - directed acyclic graph
    - meaning that data moves unidirectionally (acyclic), each stage of transformations happens all on one node and then is separated by an edge and then the new node. the main concept is that data is transformed in stages and a stage cannot reference or go back to a previous stage.
    - **correction**: DAG means **directed acyclic graph**. Directed means dependency edges have a direction; acyclic means there are no circular dependencies. A later model can reference an earlier model—that is how dependencies work. The invalid case is A depending on B while B also depends on A.
- What represents a node in a dbt DAG?
    - a single complete stage of transformation like bronze/silver/gold
    - **correction**: A node represents an individual resource, such as a model, source table, test, seed, or snapshot. Bronze/Silver/Gold are architectural layers; each layer may contain many model nodes.
- How does `ref()` create dependencies?
    - whatever model is referenced becomes a dependency
    - **addition**: Correct. If `shipping_stats` calls `ref('silver_orders')`, dbt records `silver_orders → shipping_stats`. When both are selected for execution, dbt builds the upstream model first. `ref()` alone does not select every ancestor; `+shipping_stats` does.
- Does a dbt DAG necessarily represent Bronze → Silver → Gold? Why or why not?
    - i believe so, each stage is independent of other stages. like if bronze has a field named transaction_id and customer_id, but it went through a transformation to be customer_transaction_id that combines the two columns, the silver model cannot make reference to transaction_id because it no longer exists. 
    - **correction**: No. Bronze/Silver/Gold is one design convention; dbt supports any dependency structure without cycles, including branches and joins. Layers depend on upstream data rather than being independent.
    - **addition**: Your column example is about the output schema: if a model drops `transaction_id`, a consumer cannot select it from that model. It can still reference another upstream model that exposes the column, provided that does not create a cycle.
- Why is `ref()` preferable to hard-coding database and schema names?
    - because ref is more loosly connected, so if a change happens, it is easier to resolve, where hardcoded names can be lost if the name changes and you cannot determine what the previous name was.
    - **addition**: It records lineage and lets dbt resolve the database, schema, and configured alias for the active environment. The same `ref('silver_orders')` can work in development and production. Renaming the logical model still requires updating references.

# Part 3 — Theory: dbt Testing

Remember the basic principle:

```text
Test finds 0 bad records → PASS

Test finds bad records   → FAIL
```

Study the four common generic tests:

| Test | Purpose |
|---|---|
| `not_null` | Column cannot contain NULL |
| `unique` | Values must be unique |
| `accepted_values` | Values must belong to an allowed set |
| `relationships` | Values must exist in another table/model |

For example:

```yaml
- name: order_number
  data_tests:
    - unique
    - not_null
```

### Be prepared to answer

- Why do we test data even when the SQL pipeline completed successfully?
    - double checking our work? 
    - **addition**: Successful SQL execution shows the query ran, but its results can still violate business rules: duplicate order IDs, missing values, or invalid statuses. Data tests check these assumptions about the actual rows.
- What is the difference between `unique` and `not_null`?
    - unique is finding one exact match. like if you define transaction_id as unique, then you should not find T001 and T001, this would fail
    - not_null checking that there are no null values, T001 is not null, in SQL only Null fields are null
    - **correction**: `unique` checks for duplicate non-NULL values; it does not search for one exact match. Your repeated `T001` example is correct. `not_null` checks for SQL NULLs, so use both tests when a key must be present and unique.
    - **addition**: An empty string or the text `'NULL'` is not a SQL NULL in Snowflake; `not_null` alone does not reject those strings.
- When would you use `accepted_values`?
    - for things like categories, like Electronics, Clothing, Health, etc.
    - **addition**: Correct—use it when a column must belong to a defined set, such as an order status of `PLACED`, `SHIPPED`, or `CANCELLED`. It checks non-NULL values; add `not_null` if missing values are also invalid.
- What does a `relationships` test check?
    - checks for foreign keys i believe.
    - **addition**: Yes: it checks referential integrity, such as every non-NULL `orders.customer_id` matching a customer ID in the customers model. It checks existing data rather than creating a database foreign-key constraint. Add `not_null` separately if the reference is required.
- What is the difference between testing a source and testing a model?
    - I'm not sure
    - **addition**: Source tests validate externally loaded input data; model tests validate dbt transformation outputs. For example, test raw order IDs for missing values at the source and test the transformed order IDs for uniqueness in Silver.
- What is the difference between `dbt run`, `dbt test`, and `dbt build`?
    - dbt run = runs the whole dbt pipeline
    - dbt test = runs all the tests associated with the pipeline
    - dbt build = checks for compile errors, like syntax issues
    - **correction**: `dbt run` executes selected models; it does not run all resource types or their tests. `dbt test` executes selected tests; data tests check existing relations without rebuilding them. `dbt build` runs selected models, tests, seeds, and snapshots in dependency order. It performs real builds, not just syntax checking.
    - **addition**: `dbt compile` generates executable SQL from SQL/Jinja without building model relations; it does not guarantee the warehouse will accept every SQL statement. With default error severity, upstream data-test failures during `dbt build` can cause dependent resources to be skipped.

# Part 4 — Reading: Materializations

A **materialization** determines how dbt represents a model in the database.

Research these four:

### View

```sql
{{ config(materialized='view') }}
```

The model becomes a database view.

### Table

```sql
{{ config(materialized='table') }}
```

The model becomes a physical table.

### Incremental

Only new or changed data needs to be processed instead of rebuilding the entire dataset.

### Ephemeral

The model is not directly created as a table or view. dbt incorporates its SQL into dependent models.

### Be prepared to answer

- What is a dbt materialization?
    - determines what the end product/result will be
    - **addition**: More specifically, it is the strategy dbt uses to represent and maintain a model: for example, a view, a rebuilt table, an incrementally updated table, or SQL embedded in dependent models.
- What is the difference between `view` and `table`?
    - view does not create disk or a new table, it is a temporary table created from a select that you can run other queries against.
    - both view and table act the same in practice.
    - **correction**: An ordinary view is a persistent saved query, not a temporary table. It stores its definition rather than its own result rows, and evaluates the underlying query when read. A table stores result rows. A dbt table model needs another run to reflect source changes; a view queries current underlying data.
- When would a table be preferable to a view?
    - you want to have the data live for a long time?
    - **correction**: Choose a table when repeatedly running expensive joins or aggregations through a view makes queries slow. Storing the computed rows can speed up downstream queries, at the cost of storage and rebuilding. Both tables and ordinary views can persist long term.
- What does `ephemeral` mean?
    - even more temporary than a view
    - **correction**: dbt creates no standalone table or view for an ephemeral model. It embeds the SQL into dependent models as a common table expression (CTE). You can reuse its logic with `ref()`, but cannot query it directly as a warehouse relation.
- Why might a large dataset use an incremental materialization?
    - if data is slowly trickling in like a stream or batch
    - **addition**: To avoid recomputing the full history on each run. This helps large batch datasets too; it does not require slowly arriving data or make dbt a streaming engine. You define which new or changed rows to process.

# Part 5 — Reading: Incremental Models

A normal table model might rebuild millions or billions of rows every time it runs.

An incremental model can instead process only the necessary records.

Research:

```sql
{{ config(materialized='incremental') }}
```

and:

```sql
{% if is_incremental() %}

...

{% endif %}
```

Think about a table containing five years of sales data. If 100,000 new transactions arrive today, ask yourself:

> Why process five years of data again if we only need to process today's new records?

### Be prepared to answer

- What problem does an incremental model solve?
    - it reduces duplication of work
    - allows for work to be done little by little, rather than waiting for everything to be ready for a one shot
    - **addition**: Your first point is correct: it avoids rebuilding unchanged historical rows. A typical use is maintaining a large sales table through scheduled runs that process only new or changed records.
- Why can incremental processing reduce cost and execution time?
    - because you are not repeating work
    - **addition**: Processing fewer rows can reduce scanning, joins, aggregations, and writes, which lowers compute work. Savings depend on the filter and warehouse execution plan; an inefficient filter can still scan substantial history.
- What does `is_incremental()` mean?
    - is used in if statements to only run specified code after the first pass
    - **correction**: It returns true when the model is configured as incremental, its target already exists as a table, and `--full-refresh` is not active. It commonly enables a row filter; it does not detect changed rows itself. The model SQL must work with the condition both true and false.
- What difficulties can **updates and late-arriving data** create for incremental models?
    - schema changes can cause huge issues, because the pipeline is expecting consistency
    - **correction**: Schema changes are a separate concern. Here, an old row may be updated, or a late record may have an event date older than your cutoff. A filter that only selects newer event dates can miss both.
    - **addition**: Common approaches include a reliable `updated_at`, a lookback window, and a stable `unique_key` with an update/merge strategy. Reprocessed rows must not become duplicates.
- When might you intentionally perform a full refresh instead?
    - schema changes or a new desired output
    - **addition**: When changed transformation logic must be reapplied to history, incorrect results need rebuilding, or a schema change requires it. Not every schema change needs a full refresh. Confirm the retained source data is sufficient to reconstruct the target.

# Part 6 — Reading: Snapshots

Snapshots address a different problem: **preserving history when records change**.

Suppose today:

```text
CUSTOMER_ID    STATUS
1001           ACTIVE
```

Next month:

```text
CUSTOMER_ID    STATUS
1001           INACTIVE
```

If we simply update the row, we lose the fact that the customer was previously active.

A snapshot can preserve something conceptually like:

```text
CUSTOMER_ID    STATUS      VALID_FROM    VALID_TO

1001           ACTIVE      Jan 1         Feb 1
1001           INACTIVE    Feb 1         NULL
```

Research the relationship between **dbt snapshots and Slowly Changing Dimension Type 2 (SCD Type 2).**
- **addition**: Job-focused snapshot checklist:
    - Choose a stable, non-NULL business key; validate uniqueness in the input.
    - Use the timestamp strategy with a reliable `updated_at`, or the check strategy for selected attribute changes. 
    - Understand `dbt_valid_from` and `dbt_valid_to`; current versions have NULL `dbt_valid_to` by default.
    - Schedule captures deliberately: changes overwritten between runs can be missed, and snapshots cannot recover unseen history.
    - Decide how to handle deleted source rows and join facts to the version valid at the event time.

### Be prepared to answer

- What problem do snapshots solve?
    - slowly evolving data, audits
    - **addition**: They preserve previously observed versions of mutable records that would otherwise be overwritten, such as a customer changing from ACTIVE to INACTIVE.
- Why would a business need historical versions of records?
    - audits, check historical data
    - **addition**: To answer questions using the attributes valid at that time, such as which customer segment an order belonged to when it was placed.
- What is an SCD Type 2?
    - 
    - **addition**: Slowly Changing Dimension Type 2 preserves changed attributes as a new row version rather than overwriting the old one. Each version has a validity interval; the business key can appear in multiple versions.
- Give a real-world example of data where tracking historical changes would be valuable.
    - for business needs like if sales changed over time or something
    - **correction**: A more specific example is a customer moving from Idaho to Oregon. Preserving address versions lets the business report each sale against the customer location at the time of sale. Increasing sales totals alone do not require snapshots.
- How is a snapshot different from an incremental model?
    - snapshot is a history, incrememntal is slowly changing data in batches
    - **correction**: A snapshot preserves record versions for historical analysis. An incremental model reduces repeated processing and may update rows in place, losing previous values. Incremental does not inherently mean slowly changing data or preserved history.

# Part 7 — Reading: Documentation and Lineage

Research:

```bash
dbt docs generate
```

and:

```bash
dbt docs serve
```

dbt can use information about models, sources and dependencies to document the project and display its lineage.

For example:

```text
RAW.ORDERS
     ↓
STG_ORDERS
     ↓
SILVER_ORDERS
   /       \
  ▼         ▼
ORDER_TOTAL SHIPPING_STATS
```

### Be prepared to answer

- What is **data lineage**?
    - the order in how data moves through the dbt pipeline
    - **addition**: Lineage traces where a dataset comes from, how it is transformed, and which datasets depend on it. It describes dependencies and provenance, beyond execution order.
- How does dbt know that one model depends on another?
    - use of ref or source
    - **addition**: `ref()` declares dependencies on other models/resources; `source()` declares dependencies on source tables. dbt parses these references to build its graph. Hard-coded table names do not automatically register those dependencies.
- Why is lineage useful when troubleshooting?
    - you can identify where failures are happening
    - **addition**: It helps trace a bad result back to upstream inputs and identify downstream consumers that may be affected. It narrows the investigation, though you still need to inspect SQL and data to establish the cause.
- If `STG_ORDERS` contains incorrect data, how could lineage help identify the affected downstream models?
    - find out what columns are affected in each layer/stage and make the appropriate updates
    - **correction**: Follow downstream edges from `STG_ORDERS`: in this diagram, `SILVER_ORDERS`, then `ORDER_TOTAL` and `SHIPPING_STATS`, are potentially affected. Inspect their SQL to see which values use the bad data; a model dependency graph alone does not prove which columns or rows are affected.
- What information can dbt documentation provide to another data engineer who did not build the pipeline?
    - a visual representation and summarized breakdown of what data looks like from one layer to the next
    - **addition**: It can provide model/source descriptions, column descriptions and types, defined tests, model SQL, and dependency graphs. Document grain and business rules so readers understand the rows. Useful explanations depend on what the team actually documents.
