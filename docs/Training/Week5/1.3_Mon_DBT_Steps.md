## Step 3 — Configure the Snowflake profile

The connection configuration lives in `~/.dbt/profiles.yml`, outside the repository. An existing `dbt_test` profile was preserved, and a separate top-level `shipping_analytics` profile was added.

The final working configuration is:

```yaml
shipping_analytics:
  target: dev
  outputs:
    dev:
      type: snowflake
      account: OYCADDS-VT09863
      user: UNBROKENBOND
      authenticator: snowflake
      password: "{{ env_var('DBT_ENV_SECRET_SNOWFLAKE_PASSWORD') }}"
      role: ACCOUNTADMIN
      warehouse: HOMEWORK_WH
      database: HOMEWORK_DB
      schema: DBT_DEV
      threads: 1
```

- `shipping_analytics` is our chosen profile name; the project's `profile:` setting must match it.
- `dev` is our chosen target name.
- `DBT_DEV` is the chosen output schema, distinct from the `RAW` source schema.
- `threads: 1` limits concurrent model execution to one thread for this small walkthrough.
- `password` reads an environment variable instead of storing the password in this file.
- These account and role settings describe this successful session; use your assigned objects and role when adapting the example elsewhere.

### Authentication correction made during setup

The first configuration used `authenticator: externalbrowser`. Connection testing failed with error `390190`, reporting a problem with the SAML identity-provider account parameter.

`externalbrowser` uses SAML single sign-on; it is not a general shortcut for Snowflake's ordinary web login. The learner used Snowflake username/password login, so we replaced that setting with `authenticator: snowflake` and the password environment-variable field above. See [Snowflake federated authentication](https://docs.snowflake.com/en/user-guide/admin-security-fed-auth-overview) and [Python connector authentication](https://docs.snowflake.com/en/developer-guide/python-connector/python-connector-connect).

Enter the password in the zsh terminal:

```bash
read -rs "DBT_ENV_SECRET_SNOWFLAKE_PASSWORD?Snowflake password: "
echo
export DBT_ENV_SECRET_SNOWFLAKE_PASSWORD
```

The prompt hides the typed password. `export` makes the variable available to dbt launched from that shell. A new terminal session needs the variable supplied again. Authentication policies can differ between accounts; this native password configuration succeeded in the observed session.

`raw_shop` and `orders` are logical dbt names. `database`, `schema`, and `identifier` locate the physical table. `source('raw_shop', 'orders')` resolves to `HOMEWORK_DB.RAW.ORDERS` and records the source dependency. Declaring the source does not create its table or load records.

## Step 9 — Build and inspect the Silver table

The [Silver model](shipping-analytics/models/silver/silver_orders.sql) contains:

```sql
select
    nullif(trim(order_number), '') as order_number,
    shipping_date,
    nullif(upper(trim(status)), '') as status,
    days_to_ship
from {{ ref('stg_orders') }}
```

- `TRIM` removes ordinary surrounding spaces.
- `UPPER` standardizes status capitalization.
- `NULLIF(..., '')` converts empty normalized strings into SQL NULLs.
- `ref('stg_orders')` resolves the staging relation and records its dependency.
- Dates and durations pass through unchanged; this model does not calculate shipping duration or deduplicate orders.

Run:

```bash
dbt run \
  --project-dir docs/Training/Week5/shipping-analytics \
  --select silver_orders
```

## Step 10 — Write and build the Gold shipping summary

The learner filled in the aggregation expressions and saved the [Gold model](shipping-analytics/models/gold/shipping_stats.sql):

```sql
select
    status,
    COUNT(*) as order_count,
    AVG(days_to_ship) as avg_days_to_ship
from {{ ref('silver_orders') }}
group by status
```

- `COUNT(*)` counts every order row, including pending orders whose duration is NULL.
- `COUNT(days_to_ship)` would count only non-NULL durations, so it would not meet the total-order-count requirement here.
- `AVG(days_to_ship)` averages non-NULL durations. If every duration in a group is NULL, its average is NULL.
- `GROUP BY status` changes the grain from one row per order to one row per status.
- `ref('silver_orders')` supplies the required dbt dependency instead of hard-coding the warehouse relation.

Run:

```bash
dbt run \
  --project-dir docs/Training/Week5/shipping-analytics \
  --select shipping_stats
```

The Gold folder configuration creates a table. Inspect it in Snowflake:

```sql
SELECT *
FROM HOMEWORK_DB.DBT_DEV.SHIPPING_STATS
ORDER BY STATUS;
```

The learner's screenshot verified the final result:

| STATUS | ORDER_COUNT | AVG_DAYS_TO_SHIP |
| --- | ---: | ---: |
| PENDING | 2 | NULL |
| SHIPPED | 4 | 4.000000 |

The shipped average is `(2 + 4 + 3 + 7) / 4 = 4`. Pending has no measured shipping durations; NULL does not mean zero days.
