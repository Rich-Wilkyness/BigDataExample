# Homework: Build the Citi Bike AWS Bronze → Silver Pipeline

## Objective

Your goal is to reproduce the AWS data pipeline demonstrated in class **inside your own AWS environment**.

Do **not** use the instructor's S3 bucket, IAM roles, Lambda functions, or EMR Serverless application. Create your own resources with unique names.

By the end of the assignment, your architecture should look like:


The objective is to demonstrate a realistic **serverless AWS data-engineering pipeline** that ingests live operational data, preserves the raw source data, processes it with Spark, and produces an analytics-ready Silver dataset.

## Part 1 — Create your S3 data lake

Create your own uniquely named S3 bucket.

For example:

```text
studentname-citibike-pipeline
```

Do **not** attempt to use:

```text
citi-bike-nyc-pipeline
```

because S3 bucket names are globally unique.

Organize your bucket logically around the medallion architecture:

```text
s3://YOUR-BUCKET/

bronze/
    citibike/
        gbfs_discovery/
        system_information/
        station_information/
        station_status/

silver/
    citibike/
        station_status/

scripts/
```

Remember:

**Bronze = raw source data**

**Silver = cleaned, structured and enriched data**

## Part 2 — Build the Citi Bike ingestion program locally

Write a Python program that connects to the Citi Bike GBFS API.

Start with the discovery endpoint:

```text
https://gbfs.citibikenyc.com/gbfs/gbfs.json
```

Your program should discover and retrieve at least:

```text
station_information
station_status
system_information
```

Understand what these datasets represent.

`station_information` contains relatively static metadata such as:

```text
station_id
name
latitude
longitude
capacity
station_type
```

`station_status` contains changing operational information such as:

```text
station_id
num_bikes_available
num_ebikes_available
num_bikes_disabled
num_docks_available
num_docks_disabled
is_installed
is_renting
is_returning
last_reported
```

Test the program **locally before putting it into AWS**.

## Part 3 — Write Bronze data to S3

Extend the Python ingestion program using `boto3`.

One execution should retrieve the Citi Bike data and write raw JSON objects into your S3 Bronze layer.

Use timestamped paths such as:

```text
bronze/citibike/station_status/
    year=2026/
        month=10/
            day=07/
                hour=20/
                    station_status_20261007T201500Z.json
```

Do not flatten, join, aggregate, or otherwise significantly transform the source data during ingestion.

The principle is:

```text
Source
   ↓
Ingestion
   ↓
Bronze

Preserve what the source gave us.
```

## Part 4 — Move the ingestion program to Lambda

Create a Lambda function containing your working ingestion code.

Create a dedicated Lambda execution role.

The role should trust:

```text
lambda.amazonaws.com
```

Give it the permissions necessary to:

```text
write Citi Bike data → your S3 Bronze prefix
write logs           → CloudWatch
```

Use **least privilege** rather than simply assigning AdministratorAccess to the Lambda.

Remember that code running inside Lambda does **not** use your local AWS CLI profile.

Locally you might use:

```python
boto3.Session(profile_name="...")
```

Inside Lambda, use:

```python
s3 = boto3.client("s3")
```

The AWS SDK obtains credentials from the Lambda execution role.

Manually invoke the Lambda and verify that new JSON files appear in your S3 bucket before proceeding.

**Trust policy**

**Permissions policy**

> What is the role allowed to do?

## Part 8 — Build the Bronze → Silver Spark transformation

Write a PySpark job that reads:

```text
bronze/citibike/station_status/
```

and:

```text
bronze/citibike/station_information/
```

The source JSON contains a nested array:

```text
data
  |
  +-- stations
         |
         +-- station
         +-- station
         +-- station
         ...
```

Use Spark's `explode()` operation to convert the station array into individual rows.

Flatten relevant fields from `station_status`, including:

```text
station_id
num_bikes_available
num_ebikes_available
num_bikes_disabled
num_docks_available
num_docks_disabled
is_installed
is_renting
is_returning
last_reported
```

Flatten relevant fields from `station_information`, including:

```text
station_id
station_name
latitude
longitude
capacity
station_type
```

Join the datasets using:

```text
station_status.station_id
              =
station_information.station_id
```

## Part 9 — Add useful Silver transformations

Your Silver dataset should contain both source attributes and useful derived information.

For example:

```text
station_id
station_name

snapshot_timestamp
last_reported_timestamp

latitude
longitude

capacity

bikes_available
ebikes_available
bikes_disabled

docks_available
docks_disabled

is_installed
is_renting
is_returning

utilization_pct
is_empty
is_full
is_operational
```

For example:

```text
utilization_pct =
    bikes_available / capacity * 100
```

You can define:

```text
is_empty =
    bikes_available == 0
```

and:

```text
is_full =
    docks_available == 0
```

Do **not** simply delete stations that aren't operational.

Preserve legitimate source records in Silver and represent their state with fields such as:

```text
is_operational = false
```

Business-specific filtering can occur later in Gold.

## Part 10 — Write Silver as Parquet

Your EMR Serverless Spark job should write the resulting dataset to:

```text
s3://YOUR-BUCKET/silver/citibike/station_status/
```

using **Parquet**, not JSON.

After a successful job you should see something similar to:

```text
silver/citibike/station_status/

    _SUCCESS
    part-00000-....snappy.parquet
    part-00001-....snappy.parquet
    ...
```

Be able to explain why Spark creates multiple `part-*` files rather than a single `station_status.parquet` file.
