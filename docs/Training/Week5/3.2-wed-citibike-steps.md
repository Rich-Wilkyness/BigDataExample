# Citi Bike AWS: a step-by-step Bronze → Silver walkthrough

> Status: Prepared guide; AWS execution pending permissions. Sources reviewed: 2026-10-07. The Python examples adapt the instructor code supplied in conversation. Commands below are instructions for later execution, not evidence of an AWS deployment.

> Console companion: [AWS console walkthrough with permission checkpoints](3.3-wed-citibike-console-steps.md).

## Overview and learning objectives

A live station-status API tells us what is happening now. Repeated ingestion preserves a history of observations; Spark turns those nested observations into a structured dataset that downstream analytics can use.

After working through this guide, you should be able to explain each service's responsibility, distinguish local credentials from service execution roles, preserve source JSON in Bronze, flatten station arrays, join metadata without multiplying status rows, and diagnose a failure at the correct boundary.

The walkthrough ends at Silver Parquet. Redshift, Gold models, Streamlit, ECS/Fargate, and QuickSight are possible later stages. They are not required to establish this pipeline. This is periodic batch ingestion of a live source, not a continuous streaming engine or trip-history dataset.

```text
EventBridge Scheduler ── every 5 minutes ──► Lambda
                                            │ fetches
                                            ▼
                                      Citi Bike GBFS API
                                            │ returns JSON
                                            ▼
                                      Lambda → S3 Bronze
                                                   │
                                          manual EMR job run
                                                   ▼
                                           Spark → S3 Silver
                                                      Parquet
```

The schedule invokes Lambda; the API does not invoke Scheduler. EMR runs separately. Scheduling ingestion does not schedule transformation.

## Data contract, ownership, and terminology

| Item | Meaning and boundary |
| --- | --- |
| GBFS discovery | Lists feed names and their current URLs; this supplied sample is version `1.1`, with English feeds under `data.en.feeds` |
| `station_information` | Station metadata such as name, coordinates, capacity, and type |
| `station_status` | Changing availability and operating state; stations are under `data.stations` |
| `system_information` | System/operator metadata; its `data` object is not a station array |
| Bronze grain | One complete feed document per ingestion run, plus the discovery document |
| Silver grain | One station-status observation per station per ingestion snapshot |
| `station_id` | String join key; the samples contain both numeric-looking strings and UUID-like strings |
| Snapshot time | UTC time recorded once at ingestion start and encoded into filenames |
| `last_reported` | Source-reported Unix seconds for a station; different from our ingestion time |
| ARN | AWS resource identifier, used in role policies and service targets |
| Trust policy | Which service may assume a role |
| Permissions policy | What actions the assumed role may perform on which resources |

The supplied status sample contains `num_bikes_available`, `num_ebikes_available`, disabled-bike/dock counts, and integer operating flags. Use these observed names rather than the first draft's `num_vehicles_available`. Inspect a complete fresh feed before execution: the pasted status/metadata excerpts are truncated, not valid standalone fixture files. Upstream changes remain possible.

The API owns source values. Bronze preserves their structure and values, though JSON reserialization does not preserve original whitespace or byte-for-byte formatting. Silver owns flattened names and derived flags. The three feeds are downloaded sequentially: sharing an ingestion timestamp does not mean the source observations were captured atomically.

## Step 4 — Prepare `lambda_function.py`

Save the following as `lambda_function.py`. This is an instructor-derived ingestion example with the bucket moved to a Lambda environment variable. It can be read and syntax-checked before AWS access is available.

```python
import json
import os
import urllib.request
from datetime import datetime, timezone

import boto3

GBFS_URL = "https://gbfs.citibikenyc.com/gbfs/gbfs.json"
BUCKET = os.environ["CITIBIKE_BUCKET"]
WANTED_FEEDS = {"station_information", "station_status", "system_information"}
s3 = boto3.client("s3")


def get_json(url):
    print(f"Downloading: {url}")
    request = urllib.request.Request(
        url, headers={"User-Agent": "NYC-DOT-DataEngineering-Demo/1.0"}
    )
    with urllib.request.urlopen(request, timeout=30) as response:
        return json.loads(response.read())


def write_json_to_s3(dataset_name, data, snapshot_time):
    key = (
        f"bronze/citibike/{dataset_name}/"
        f"year={snapshot_time:%Y}/month={snapshot_time:%m}/"
        f"day={snapshot_time:%d}/hour={snapshot_time:%H}/"
        f"{dataset_name}_{snapshot_time:%Y%m%dT%H%M%SZ}.json"
    )
    body = json.dumps(data, separators=(",", ":")).encode("utf-8")
    s3.put_object(Bucket=BUCKET, Key=key, Body=body, ContentType="application/json")
    print(f"Uploaded {len(body):,} bytes -> s3://{BUCKET}/{key}")
    return key


def lambda_handler(event, context):
    snapshot_time = datetime.now(timezone.utc)
    discovery = get_json(GBFS_URL)
    feed_urls = {
        feed["name"]: feed["url"]
        for feed in discovery["data"]["en"]["feeds"]
        if feed["name"] in WANTED_FEEDS
    }
    missing = WANTED_FEEDS - set(feed_urls)
    if missing:
        raise RuntimeError(f"Missing expected feeds: {missing}")

    uploaded = [write_json_to_s3("gbfs_discovery", discovery, snapshot_time)]
    for dataset_name, url in feed_urls.items():
        uploaded.append(write_json_to_s3(dataset_name, get_json(url), snapshot_time))

    result = {
        "statusCode": 200,
        "snapshot_time": snapshot_time.isoformat(),
        "files_uploaded": len(uploaded),
        "objects": uploaded,
    }
    print(json.dumps(result))
    return result
```

How to read it:

- AWS calls `lambda_handler(event, context)`. The scheduled event can be `{}` because this code gets its configuration elsewhere.
- `boto3.client("s3")` gets credentials from the Lambda execution role in AWS. There is no local `company` profile inside Lambda.
- Four objects are expected per successful run: discovery plus three feeds.
- The timestamp is captured once, so related files share the same snapshot suffix.
- JSON is serialized and uploaded without station-level cleaning, joining, or filtering.
- Exceptions propagate and are logged. Returning a dictionary with `statusCode` is this example's result format, not an HTTP response or an independent proof that the function succeeded.

Managed Python Lambda runtimes include Boto3. For this small demonstration, zipping the source file is sufficient; you do not need a VM or an S3-hosted deployment package just because the code imports Boto3. Dependencies beyond the included runtime need packaging. Production builds should pin/package their SDK dependencies to control versions. See [Python Lambda runtimes](https://docs.aws.amazon.com/lambda/latest/dg/lambda-python.html) and [Python deployment packages](https://docs.aws.amazon.com/lambda/latest/dg/python-package.html).

## Step 5 — Create the Lambda execution role

Save `lambda-trust-policy.json`:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Service": "lambda.amazonaws.com"},
    "Action": "sts:AssumeRole"
  }]
}
```

Create the role and attach logging permissions:

```bash
aws iam create-role \
  --role-name "$LAMBDA_ROLE_NAME" \
  --assume-role-policy-document file://lambda-trust-policy.json \
  --profile "$AWS_PROFILE"

aws iam attach-role-policy \
  --role-name "$LAMBDA_ROLE_NAME" \
  --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole \
  --profile "$AWS_PROFILE"
```

Generate `lambda-s3-policy.json` using the current bucket variable:

```bash
cat > lambda-s3-policy.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "s3:PutObject",
    "Resource": "arn:aws:s3:::$BUCKET/bronze/citibike/*"
  }]
}
EOF

aws iam put-role-policy \
  --role-name "$LAMBDA_ROLE_NAME" \
  --policy-name WriteCitiBikeBronze \
  --policy-document file://lambda-s3-policy.json \
  --profile "$AWS_PROFILE"
```

This walkthrough uses an inline permissions policy to avoid creating a separate managed policy for every student. The instructor used `create-policy` followed by `attach-role-policy`; both approaches can grant the same S3 action. An inline policy belongs to one role; a managed policy can be attached to several identities.

Checkpoint: trust permits Lambda; logging permissions are attached; S3 writes are allowed only under your Bronze Citi Bike prefix. If your company bucket uses a customer-managed KMS key, additional key permissions/policy access may be required.

## Step 6 — Package and create the Lambda

```bash
zip lambda.zip lambda_function.py

LAMBDA_ROLE_ARN=$(aws iam get-role \
  --role-name "$LAMBDA_ROLE_NAME" \
  --query Role.Arn --output text --profile "$AWS_PROFILE")

aws lambda create-function \
  --function-name "$FUNCTION_NAME" \
  --runtime python3.14 \
  --role "$LAMBDA_ROLE_ARN" \
  --handler lambda_function.lambda_handler \
  --zip-file fileb://lambda.zip \
  --environment "Variables={CITIBIKE_BUCKET=$BUCKET}" \
  --timeout 120 \
  --memory-size 256 \
  --region "$AWS_REGION" \
  --profile "$AWS_PROFILE"
```

`lambda_function.py` must sit at the ZIP root. `lambda_function.lambda_handler` means module filename without `.py`, then function name. `fileb://` sends binary ZIP contents; `file://` reads a text policy file.

Python 3.14 is documented as a supported managed runtime at review time. This guide uses a 120-second total timeout instead of the instructor's 60 seconds because four sequential HTTP calls each have a 30-second timeout; total processing also includes S3 writes. This is a starting setting, not a latency guarantee. Measure and adjust later.

New role permissions can take time to propagate. If Lambda reports it cannot assume a newly created role, verify the trust policy, allow propagation, and retry. Do not create another broadly privileged role as a workaround.

## Step 10 — Understand the Bronze → Silver Spark job

Before running Spark, verify automatic ingestion. The supplied later instructor script is the relevant version for the observed `num_bikes_available` field.

Transformation sequence:

1. Read all status documents under the Bronze status prefix and retain each source filename.
2. `explode(data.stations)` makes one row for each station in each document.
3. Extract the UTC ingestion timestamp from the filename.
4. Flatten station fields; convert integer operating flags into booleans and Unix seconds into timestamps.
5. Read and flatten metadata, retaining one metadata row per station.
6. Left-join on `station_id` so a missing metadata match does not delete a status observation.
7. Add utilization and state flags, then write Parquet to Silver.

Save the instructor-derived example below as `bronze_to_silver.py`. It takes your bucket as an argument and explicitly sets Spark's timezone to UTC. The transformation remains the supplied teaching example; its metadata-selection limitation is explained immediately afterward.

```python
import sys
from pyspark.sql import SparkSession
from pyspark.sql.functions import (
    col, explode, input_file_name, regexp_extract,
    to_timestamp, from_unixtime, when, round as spark_round,
)

bucket = sys.argv[1]
spark = (
    SparkSession.builder.appName("CitiBikeBronzeToSilver")
    .config("spark.sql.session.timeZone", "UTC")
    .getOrCreate()
)
base = f"s3://{bucket}"

status_raw = (
    spark.read.option("multiLine", "true")
    .json(f"{base}/bronze/citibike/station_status/")
    .withColumn("source_file", input_file_name())
)
status_raw.printSchema()
status = status_raw.select(
    explode(col("data.stations")).alias("station"), col("source_file")
)
status = (
    status.withColumn(
        "snapshot_string",
        regexp_extract(col("source_file"), r"station_status_(\d{8}T\d{6}Z)", 1),
    )
    .withColumn(
        "snapshot_timestamp",
        to_timestamp(col("snapshot_string"), "yyyyMMdd'T'HHmmss'Z'"),
    )
    .select(
        col("station.station_id").alias("station_id"),
        col("snapshot_timestamp"),
        col("station.num_bikes_available").alias("bikes_available"),
        col("station.num_ebikes_available").alias("ebikes_available"),
        col("station.num_bikes_disabled").alias("bikes_disabled"),
        col("station.num_docks_available").alias("docks_available"),
        col("station.num_docks_disabled").alias("docks_disabled"),
        col("station.is_installed").cast("boolean").alias("is_installed"),
        col("station.is_renting").cast("boolean").alias("is_renting"),
        col("station.is_returning").cast("boolean").alias("is_returning"),
        col("station.last_reported").alias("last_reported_epoch"),
        col("station.legacy_id").alias("legacy_id"),
    )
    .withColumn(
        "last_reported_timestamp", to_timestamp(from_unixtime(col("last_reported_epoch")))
    )
)

info_raw = (
    spark.read.option("multiLine", "true")
    .json(f"{base}/bronze/citibike/station_information/")
)
info_raw.printSchema()
info = (
    info_raw.select(explode(col("data.stations")).alias("station"))
    .select(
        col("station.station_id").alias("station_id"),
        col("station.name").alias("station_name"),
        col("station.short_name").alias("short_name"),
        col("station.lat").alias("latitude"),
        col("station.lon").alias("longitude"),
        col("station.region_id").alias("region_id"),
        col("station.capacity").alias("capacity"),
        col("station.station_type").alias("station_type"),
        col("station.has_kiosk").alias("has_kiosk"),
    )
    .dropDuplicates(["station_id"])
)

silver = (
    status.join(info, on="station_id", how="left")
    .withColumn(
        "utilization_pct",
        when(col("capacity") > 0,
             spark_round(col("bikes_available") / col("capacity") * 100, 2)),
    )
    .withColumn("is_empty", col("bikes_available") == 0)
    .withColumn("is_full", col("docks_available") == 0)
    .withColumn("is_operational",
                col("is_installed") & col("is_renting") & col("is_returning"))
)
silver.printSchema()
print(f"SILVER RECORD COUNT: {silver.count()}")
silver.select(
    "station_id", "station_name", "snapshot_timestamp", "last_reported_timestamp",
    "capacity", "bikes_available", "ebikes_available", "docks_available",
    "utilization_pct", "is_empty", "is_full", "is_operational",
).show(20, truncate=False)

output_path = f"{base}/silver/citibike/station_status/"
silver.write.mode("overwrite").parquet(output_path)
print(f"Silver dataset written to {output_path}")
spark.stop()
```

### What this example guarantees, and what it does not

- Repeated status observations are preserved. Do not deduplicate status by `station_id` alone; that would discard history.
- Metadata deduplication prevents a many-to-many join explosion, but `dropDuplicates(["station_id"])` does not choose the latest metadata. If attributes change, the retained row is unspecified. This example does not provide historically correct metadata matching. See [Spark dropDuplicates](https://spark.apache.org/docs/latest/api/python/reference/pyspark.sql/api/pyspark.sql.DataFrame.dropDuplicates.html).
- A later improvement can select the latest metadata deterministically or match metadata from the same ingestion snapshot. Those produce different historical semantics; choose deliberately before implementing.
- The filename's `Z` is parsed as a literal in the supplied format. Explicit UTC session configuration makes its interpretation match the UTC ingestion clock. See [Spark session timezone](https://spark.apache.org/docs/latest/sql-ref-syntax-aux-conf-mgmt-set-timezone.html).
- `last_reported=86400` converts to `1970-01-02 00:00:00 UTC`. In the supplied sample it appears on inactive stations. Preserve the raw value and flag its age; the excerpt alone does not establish an official sentinel definition. Do not treat it as the current ingestion time.
- Inactive stations stay in Silver. A station can have both `is_empty=true` and `is_full=true` when both counts are zero; `is_operational` provides context. These flags are count comparisons, not complete business classifications.
- Missing metadata yields null attributes. Nonpositive or missing capacity yields null utilization. Utilization here means available bikes divided by reported capacity; it is not a measure of trip demand or a complete physical occupancy model.
- Do not assume e-bike counts should be added to available-bike counts; establish the source definition first.
- Schema inference is convenient for class, but absent expected fields can fail field selection. Record actual schemas and establish an explicit validated contract as the pipeline matures.
- `overwrite` rebuilds Silver from the Bronze files visible to that run. It is not incremental processing or atomic publication of a whole multi-file dataset. Use only your dedicated Silver prefix, avoid overlapping jobs, and rebuild after a failed write.

## Step 11 — Create the EMR job execution role

Save `emr-trust-policy.json`:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Service": "emr-serverless.amazonaws.com"},
    "Action": "sts:AssumeRole"
  }]
}
```

Generate a permissions policy. The logs prefix is included because the later submission explicitly requests S3 logs. Bucket listing uses the bucket ARN; object access uses object ARNs.

```bash
cat > emr-s3-policy.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::$BUCKET",
      "Condition": {"StringLike": {"s3:prefix": ["bronze/*", "scripts/*", "silver/*", "logs/emr/*"]}}
    },
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": ["arn:aws:s3:::$BUCKET/bronze/*", "arn:aws:s3:::$BUCKET/scripts/*"]
    },
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::$BUCKET/silver/*"
    },
    {
      "Effect": "Allow",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::$BUCKET/logs/emr/*"
    }
  ]
}
EOF

aws iam create-role \
  --role-name "$EMR_ROLE_NAME" \
  --assume-role-policy-document file://emr-trust-policy.json \
  --profile "$AWS_PROFILE"

aws iam put-role-policy \
  --role-name "$EMR_ROLE_NAME" \
  --policy-name CitiBikeEMRS3Access \
  --policy-document file://emr-s3-policy.json \
  --profile "$AWS_PROFILE"

EMR_ROLE_ARN=$(aws iam get-role \
  --role-name "$EMR_ROLE_NAME" \
  --query Role.Arn --output text --profile "$AWS_PROFILE")
```

Silver deletion is included because overwrite replaces existing output objects. Lambda does not need that permission. Company encryption or networking constraints may require additional approved configuration. Production trust policies should also scope service access with applicable source-account/source-ARN conditions. See [EMR job runtime roles](https://docs.aws.amazon.com/emr/latest/EMR-Serverless-UserGuide/security-iam-runtime-role.html).

## Step 14 — Verify Silver and its data quality

```bash
aws s3 ls "s3://$BUCKET/silver/citibike/station_status/" \
  --recursive --profile "$AWS_PROFILE"

aws s3 ls "s3://$BUCKET/logs/emr/" \
  --recursive --profile "$AWS_PROFILE"
```

Expect Parquet `part-*` files; a `_SUCCESS` marker may also be present depending on the configured output committer. Spark writes files from distributed output tasks instead of automatically gathering everything into one named file.

Object existence is only a storage checkpoint. Inspect the job's printed schemas/sample rows and, when possible, read Silver back with Spark. Verify:

- Status row count equals the total station observations read from the status documents.
- Left-join output count equals status count when metadata is unique by station ID.
- Missing names/capacities are measured, not silently dropped.
- `(station_id, snapshot_timestamp)` duplicates are investigated rather than assumed impossible.
- Availability/disabled counts are nonnegative; unexpected nulls and types are counted.
- Snapshot timestamps parse successfully and align with the filename in UTC.
- Old `last_reported` values and inactive stations remain distinguishable.
- Utilization is null when capacity is unavailable/nonpositive; unusual ratios are investigated rather than clipped automatically.

These are verification tasks, not claims that checks have already passed.

## Failure model and recovery

| Symptom | Boundary to inspect | Recovery/check |
| --- | --- | --- |
| CLI authentication fails | Human identity/profile | Use company authentication and verify caller identity |
| Create/submit denied | Deployment permissions | Identify the denied action, resource, and applicable `iam:PassRole` permission |
| Lambda cannot assume role | Trust/propagation | Confirm `lambda.amazonaws.com` trust and allow policy propagation |
| Lambda `AccessDenied` on upload | Bucket/policy/KMS | Match configured bucket to Bronze policy ARN; check company key/bucket policies |
| Manual ingestion works; scheduled ingestion does not | Scheduler target/role/state | Verify target ARN, enabled state, Scheduler trust, and invocation permission |
| Scheduler delivery occurs; no four-object snapshot | Lambda execution | Inspect CloudWatch errors, timeouts, and partially written snapshots |
| Spark cannot resolve a field | Source schema | Compare current `printSchema()` with the expected GBFS version and names |
| EMR fails to read/write/log | Job role and S3 paths | Check list/read/write/delete permissions and S3 log permissions |
| Silver row count grows unexpectedly after join | Metadata multiplicity | Verify one metadata row per station before joining |
| Silver missing/incomplete after failure | Overwrite publication | Stop concurrent jobs, inspect failure, rebuild from intact Bronze |

A four-object upload is not a transaction. A failure after two uploads can leave a partial snapshot. Retries can create a new snapshot timestamp, and filenames have only second-level uniqueness. Before production, add a stable run identity, explicit completion manifest, bounded retries, and validation of completed snapshot groups. Preserve Bronze so transformations can be replayed. Do not treat today's example as exactly-once ingestion.

## Cost, operations, and production progression

- At five-minute intervals, nominal ingestion is 288 runs/day and 1,152 objects/day: four objects per successful run, excluding retries and failures. This is a planning estimate, not a measured bill.
- Lambda duration/requests, S3 storage/requests, logs, scheduling, and EMR capacity can incur charges. EMR full-prefix reads grow with retained history; repeated full rebuilds are a learning approach, not a long-term incremental strategy.
- Record retention and budget decisions. Bound log retention and stop unneeded schedules/capacity after practice.
- Next engineering steps: explicit schemas, deterministic metadata selection, completion manifests, retry identity, freshness/completeness metrics, incremental processing, and versioned or transactional Silver publication. Introduce them after the basic boundaries are understood.
- Fargate is managed container compute used with ECS; it does not inherently scale an application to zero when no one visits. Running tasks can incur compute charges while idle. The rough note's no-traffic/no-cost assumption should not guide deployment decisions. See [Fargate pricing](https://aws.amazon.com/fargate/pricing/).

To pause ingestion later, open the schedule in the console, choose **Disable**, and verify its state with `get-schedule`. Disabling does not remove stored data or necessarily cancel invocations already delivered. To disable by CLI, first retrieve the current configuration and provide the required existing target/expression settings to `update-schedule`; do not use an incomplete update command.
