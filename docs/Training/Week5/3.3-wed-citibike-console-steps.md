# Citi Bike Bronze → Silver: AWS console walkthrough

> Prepared: 2026-10-08. Permission analysis is based on the policy supplied by the learner, not a live inspection of the AWS account. Console procedures were checked against official AWS documentation. No AWS resources were created or tested while writing this guide.

## Overview

Use this guide to build the same pipeline through the AWS Management Console. The [code and concepts walkthrough](3.2-wed-citibike-steps.md) supplies the Python examples; this file explains where to put them, which settings to choose, what to verify, and where the supplied permissions require administrator help. You do not need to configure the AWS CLI for this console path.

Learning objectives:

- Create a private bucket and deploy ingestion using an existing execution role.
- Manually verify that Lambda writes four Bronze objects.
- Configure scheduled ingestion once the required access is available.
- Upload the Spark script, submit an EMR Serverless job, and inspect Silver output.
- Distinguish your own permissions from permissions used by AWS services.

```text
Scheduler → Lambda → fetch Citi Bike feeds → S3 Bronze
                                              │
                                    manual EMR Spark job
                                              ▼
                                          S3 Silver
```

Scheduler starts ingestion; it does not receive data from the API. This is periodic batch capture of live station state. EMR transformation is submitted separately. Redshift, dashboards, and Gold are later topics.

## First: understand your supplied permissions

The policy grants broad actions on S3, Lambda, EMR Serverless, and several other services. Its only IAM action is conditional `iam:PassRole`. This means you can pass eligible existing roles to certain services; it does not let you create or edit those roles, and it does not guarantee a role selector can list them.

The table describes this policy's grants only. Other attached policies could add permissions, while organization policies, permission boundaries, explicit denies, resource policies, or KMS policies could limit them. Treat an actual successful console action as evidence; the table is not a live access test.

| Console task | Supplied policy | Practical consequence |
| --- | --- | --- |
| Create/private-configure a bucket, upload/download/list objects | Includes `s3:*` | Proceed with your own bucket, subject to company restrictions |
| Create/edit/test Lambda | Includes `lambda:*` | Proceed once an appropriate existing execution role is available |
| Pass a role to Lambda | Includes `iam:PassRole` for `lambda.amazonaws.com` | You may use an eligible role, but its trust and permissions still need to be correct |
| Create/edit IAM roles or role policies | No such IAM actions | Administrator setup is needed unless another policy grants access |
| List/inspect IAM roles in console selectors | No `iam:ListRoles` or `iam:GetRole` | Selectors or role details can fail even with PassRole; request read access or administrator assistance |
| Create/edit/view EventBridge Scheduler schedules | No `scheduler:*` actions | Administrator must create the schedule or grant scoped Scheduler access |
| Pass a role to Scheduler | PassRole service list omits `scheduler.amazonaws.com` | Scheduler creation still fails without this grant even if Scheduler API access is added |
| Use legacy EventBridge scheduled rules instead | No `events:*` actions | That is not an available workaround under this policy |
| Read CloudWatch log groups/streams | No `logs:*` actions | Lambda may write logs through its role while you cannot browse them |
| View CloudWatch metrics | No `cloudwatch:*` actions | Monitoring panels may show access errors; those do not alone prove a job failed |
| Create EMR Serverless applications/submit jobs | Includes `emr-serverless:*` and EMR actions | Proceed once runtime role and account prerequisites exist |
| Pass an EMR runtime role | Includes PassRole for `emr-serverless.amazonaws.com` | Role can be used if it trusts EMR Serverless and has the right S3 access |
| Create EMR Serverless's service-linked role on first use | No `iam:CreateServiceLinkedRole` | Administrator may need to initialize this account prerequisite |

Console forms may call multiple services. Broad permission for a service does not automatically provide IAM, Scheduler, or CloudWatch permissions. See [Scheduler identity permissions](https://docs.aws.amazon.com/scheduler/latest/UserGuide/security_iam_id-based-policy-examples.html) and [EMR Serverless user access examples](https://docs.aws.amazon.com/emr/latest/EMR-Serverless-UserGuide/security-iam-user-access-policies.html).

### What to have the administrator prepare

This is a checklist you can share yourself; it is not a message sent to anyone. Creating the roles for you is sufficient—you do not need general IAM administration access to learn the pipeline.

| Needed resource | Example name | Trust principal | Permissions used by that role |
| --- | --- | --- | --- |
| Lambda execution role | `RichardCitiBikeLambdaRole` | `lambda.amazonaws.com` | `s3:PutObject` on `arn:aws:s3:::YOUR-BUCKET/bronze/citibike/*`; CloudWatch log-writing permissions, such as `AWSLambdaBasicExecutionRole` |
| Scheduler execution role | `RichardCitiBikeSchedulerRole` | `scheduler.amazonaws.com` | `lambda:InvokeFunction` on your exact Lambda ARN |
| EMR job execution role | `RichardCitiBikeEMRRole` | `emr-serverless.amazonaws.com` | List appropriate bucket prefixes; read Bronze and scripts; read/write/delete Silver; write `logs/emr/*` |

The complete teaching trust/S3 policy examples are in Steps 5, 8, and 11 of the [code walkthrough](3.2-wed-citibike-steps.md). Administrator-managed roles may include additional company-required conditions or encryption permissions. Supply your final bucket name first and the actual Lambda ARN after creation. Never copy the instructor's account ID.

Also request or confirm:

- IAM read access needed to select the approved roles: typically `iam:ListRoles` and `iam:GetRole`. Additional policy-inspection actions are needed only if you are expected to inspect attached policies yourself.
- Either administrator creation/management of the five-minute schedule, or learner permissions for `scheduler:CreateSchedule`, `scheduler:GetSchedule`, `scheduler:ListSchedules`, `scheduler:ListScheduleGroups`, and `scheduler:UpdateSchedule`, plus `iam:PassRole` on the approved Scheduler role with `iam:PassedToService` equal to `scheduler.amazonaws.com`. Delete access is needed only if you will remove the schedule yourself. The administrator should scope actions appropriately; console navigation may need additional read actions.
- Read access to your Lambda's logs: relevant `logs:DescribeLogGroups`, `logs:DescribeLogStreams`, `logs:GetLogEvents`, and `logs:FilterLogEvents`. Querying with Logs Insights needs additional query actions; ordinary stream browsing is enough to start.
- An existing EMR Studio usable in the selected Region, or administrator help with first-time console setup if additional IAM/Identity Center permissions are required. Batch jobs do not require an interactive notebook Workspace.
- Confirmation that the EMR Serverless service-linked role already exists, or administrator creation of it. This infrastructure role is different from the job runtime role.

You can manually ingest and transform after the Lambda/EMR roles are ready, even while scheduling access is pending. Label that milestone **manual pipeline**, not automated ingestion.

## Step 1 — Sign in and record your configuration

1. Open the company-provided AWS console sign-in page and sign in using the assigned account/identity.
2. Check the account menu so you know which account you are using.
3. Select the company-approved Region in the top-right Region selector. Use `us-east-2` only if approved; it matches the instructor's final example.
4. Choose your own resource names and record them below. IAM roles are account-wide; buckets have a selected Region even though the S3 console lists buckets across Regions.

| Setting | Your value |
| --- | --- |
| Account ID | To record |
| Region | To record; example `us-east-2` |
| Bucket | Example pattern `richard-wilkerson-citibike-pipeline-<unique-suffix>`; replace the placeholder |
| Lambda name | `richard-citibike-ingestion` |
| Lambda execution role name/ARN | Administrator-provided |
| Schedule name | `richard-citibike-every-five-minutes` |
| Scheduler execution role name/ARN | Administrator-provided |
| EMR application name | `richard-citibike-spark` |
| EMR runtime role name/ARN | Administrator-provided |
| EMR application ID/release | Record when created |

Checkpoint: account, Region, and names are consistent. Do not use the instructor's bucket or roles simply because they appear in a selector.

## Step 2 — Create your private S3 bucket

1. Search for **S3** using the console's service search.
2. Open **Buckets → Create bucket**.
3. Choose a **general purpose** bucket. Use the ordinary shared namespace option if a namespace choice is shown; choose an available lowercase name.
4. Set the bucket Region to the Region recorded in Step 1.
5. Keep **Object Ownership: ACLs disabled** and all **Block Public Access** settings enabled.
6. Use the company-required encryption setting. For a basic example without a company KMS requirement, the default SSE-S3 encryption is sufficient. A customer-managed KMS key requires matching key permissions for your identity and service roles.
7. Review and create the bucket. Versioning is optional for this learning path; if enabled, record that overwritten/deleted objects can retain billable older versions.

Check the bucket's **Properties** and **Permissions** tabs. This step follows [S3 bucket creation guidance](https://docs.aws.amazon.com/AmazonS3/latest/userguide/create-bucket-overview.html).

You do not need to create `bronze` or `silver` folders first; Lambda and Spark create objects with those key prefixes. You will create `scripts/` for the console upload later.

Checkpoint: the bucket exists in your chosen Region and remains private. Tell the administrator this exact name so role policies reference the correct object ARNs.

## Step 3 — Create Lambda using the approved existing role

**Dependency:** the administrator has prepared the Lambda execution role from the checklist. The supplied policy does not authorize creating a new role automatically.

1. Search for **Lambda**, check the Region, and choose **Create function → Author from scratch**.
2. Enter your function name.
3. Select **Python 3.14** if offered and approved. Keep `x86_64` for consistency with this example; no native dependency build is involved.
4. Expand **Change default execution role** under permissions.
5. Select **Use an existing role**, then the administrator-provided Lambda role.
6. Create the function.

If the dropdown cannot list roles, record the denied action and request IAM read access or administrator assistance. Do not select **Create a new role with basic Lambda permissions** as a workaround: that needs IAM permissions absent from the supplied policy.

After creation, **Configuration → Permissions** identifies the execution role. You may be able to see the ARN even if following its IAM link is denied. Record it.

See [Lambda function creation](https://docs.aws.amazon.com/lambda/latest/dg/getting-started.html) and [managed Python runtimes](https://docs.aws.amazon.com/lambda/latest/dg/lambda-python.html).

Checkpoint: your function exists and uses the intended execution role.

## Step 4 — Set configuration and paste the ingestion code

1. Open **Configuration → Environment variables → Edit**.
2. Add key `CITIBIKE_BUCKET` and value equal to your exact bucket name, without `s3://` or a prefix. Save.
3. Open **Configuration → General configuration → Edit**. Set memory to **256 MB** and timeout to **2 minutes** as the walkthrough's starting settings. Save.
4. Open **Code**, then `lambda_function.py` in the editor.
5. Copy the entire Python block from **Step 4 — Prepare `lambda_function.py`** in the [code walkthrough](3.2-wed-citibike-steps.md), replacing the default example code.
6. Choose **Deploy** and wait for the update to finish.
7. Under **Runtime settings**, verify the handler is `lambda_function.lambda_handler`.

The environment variable is required because the guide code reads `os.environ["CITIBIKE_BUCKET"]`. The original instructor version hardcodes a bucket; use the guide code consistently with these settings. Boto3 is included in the managed runtime, and the execution role supplies credentials. A local AWS profile or access key is not needed in this code.

Do not attach a VPC solely to make S3 private. Leave the ordinary Lambda networking configuration for this public-API example unless the company requires a VPC. A VPC-attached function needs suitable outbound connectivity to fetch the public feed; attaching it to a public subnet alone does not provide internet access. See [Lambda internet access with a VPC](https://docs.aws.amazon.com/lambda/latest/dg/configuration-vpc-internet.html).

See [console environment variable configuration](https://docs.aws.amazon.com/lambda/latest/dg/configuration-envvars.html). Setting the bucket and changing Python are separate configuration/code updates; saved editor changes must be deployed.

Checkpoint: bucket variable, handler, timeout, role, and deployed code all match this guide.

## Step 5 — Test Lambda manually

1. Open **Test**, or the code editor's **TEST EVENTS** panel.
2. Create a test event named `manual-ingestion`.
3. Choose **Private** and replace the event JSON with `{}`.
4. Save and run the test. Depending on the console layout, the action is **Test** or the event's run button.
5. Inspect the execution result, response, and any returned log output.

Expected function response fields:

| Field | Expected value |
| --- | --- |
| `statusCode` | `200`, produced by this code after its uploads finish |
| `files_uploaded` | `4` |
| `snapshot_time` | UTC ingestion timestamp |
| `objects` | Discovery, station information, station status, and system information keys |

Use a private event because shareable events need extra EventBridge schema permissions absent from your supplied policy. The empty event is valid because the code fetches the feeds rather than reading input data from the event. See [console Lambda testing](https://docs.aws.amazon.com/lambda/latest/dg/testing-functions.html).

The return dictionary alone is not the checkpoint: verify actual S3 objects next. A successful invocation request is also different from a successful function execution.

## Step 6 — Inspect Bronze through S3

1. Open S3 in another tab and select your bucket.
2. Refresh the **Objects** list; navigate to `bronze/citibike/`.
3. Open each of the four dataset prefixes and follow `year=.../month=.../day=.../hour=.../` to the JSON object.
4. Verify the filenames share the same snapshot suffix from the successful test.
5. Select a JSON object and use **Open** or **Download** through your authorized console session. A public object URL need not work for this private bucket.
6. Inspect station status for `data.stations`, string station IDs, and `num_bikes_available`. Inspect metadata for names, `lat`, `lon`, and capacity.

Expected prefixes: `gbfs_discovery/`, `station_information/`, `station_status/`, and `system_information/`, all under `bronze/citibike/`.

Checkpoint: one complete four-object snapshot exists and its structure matches the code's expected GBFS feed. A failure midway can leave fewer than four objects; S3 uploads across these files are not one transaction.

## Step 7 — View logs if log-read access is available

1. From Lambda, open **Monitor → View CloudWatch logs**, or open **CloudWatch → Logs → Log groups**.
2. Select `/aws/lambda/richard-citibike-ingestion`, using your actual function name.
3. Open the relevant recent log stream and find the invocation's downloads, upload messages, result, or exception.

The Lambda role's log-write permission and your log-read permission are different. Your supplied policy does not grant log browsing. If the page is denied, use the manual test result and S3 checkpoint for now, and request the log-read access described above. Synchronous test output may contain a limited log excerpt; that does not grant access to the stored log history or prove scheduled runs succeeded.

See [viewing Lambda logs](https://docs.aws.amazon.com/lambda/latest/dg/monitoring-cloudwatchlogs-view.html). Monitoring graphs can separately require CloudWatch metrics permissions.

Checkpoint: record whether stored-log inspection succeeded or remains blocked; do not label an access error as a function failure.

## Step 8 — Record the Lambda ARN and configure Scheduler when authorized

**Current policy gap:** neither Scheduler API access nor PassRole to `scheduler.amazonaws.com` is included. An administrator must perform this step or supply the scoped access first. You can continue with manual ingestion and EMR meanwhile.

To obtain the target without a CLI command:

1. Open your Lambda's function overview.
2. Copy its **Function ARN** from the overview/details area.
3. Record the actual ARN, with this shape: `arn:aws:lambda:REGION:ACCOUNT-ID:function:FUNCTION-NAME`.

Supply that ARN to the administrator for the Scheduler role's `lambda:InvokeFunction` permission. The role must trust `scheduler.amazonaws.com`; it is separate from the Lambda role.

Once authorized, use **EventBridge Scheduler → Schedules → Create schedule**:

| Setting | Value |
| --- | --- |
| Name | Your schedule name from Step 1 |
| Group | `default`, unless your administrator specifies another |
| Pattern | Recurring, rate-based: every **5 minutes** / `rate(5 minutes)` |
| Flexible time window | **Off** for this checkpoint |
| Target | Templated **AWS Lambda Invoke** |
| Function | Your function, matching the recorded ARN |
| Input payload | `{}` |
| Execution permissions | **Use existing role**: your Scheduler role |
| Encryption | AWS-owned key unless company policy requires another choice |
| State | Enabled |

Review retry/event-age settings and record the selected values. Use a company-provided dead-letter queue if one is required; SQS creation is not granted by the supplied policy. Avoid asking the console to create a new role automatically under the current IAM grants.

Review and create the schedule. If using Lambda's **Add trigger** route instead, select Scheduler and the equivalent settings. Legacy scheduled rules are a different mechanism. Follow [AWS's Lambda scheduling guide](https://docs.aws.amazon.com/lambda/latest/dg/with-eventbridge-scheduler.html) and [flexible window documentation](https://docs.aws.amazon.com/scheduler/latest/UserGuide/managing-schedule-flexible-time-windows.html).

Checkpoint: the schedule details show the correct expression, function ARN, Scheduler role ARN, enabled state, and flexible window setting. Flexible window Off does not guarantee second-exact execution.

## Step 9 — Verify scheduled ingestion

1. Allow two or three five-minute intervals.
2. Refresh the S3 station-status prefix and compare snapshot filenames. Avoid manually invoking during this check, so the new objects can be attributed to the schedule more clearly.
3. Check the other three feed prefixes for matching snapshots.
4. Inspect Lambda logs for those runs if permitted, or have the administrator inspect failures.

Checkpoint: multiple complete snapshots accumulated automatically at approximately five-minute intervals. Scheduler target delivery is asynchronous; delivery alone does not prove Lambda finished its work.

If scheduling is still blocked, run a second manual test to capture another snapshot and continue learning Spark. Record **scheduled ingestion pending access**; do not claim this proves automation.

## Step 10 — Save and upload the Spark script using S3

1. On your computer, create `bronze_to_silver.py` in your chosen working directory.
2. Copy the entire Python block from **Step 10 — Understand the Bronze → Silver Spark job** in the [code walkthrough](3.2-wed-citibike-steps.md).
3. In S3, open your bucket and choose **Create folder**, naming it `scripts` if the prefix does not already exist.
4. Open `scripts/`, choose **Upload → Add files**, select `bronze_to_silver.py`, and upload.
5. Select the uploaded object and choose **Copy S3 URI**. Record `s3://YOUR-BUCKET/scripts/bronze_to_silver.py`.

This job script takes the bucket name from its first argument (`sys.argv[1]`). It expects the later guide's bucket argument, not the original instructor script's hardcoded bucket. Upload the `.py` file, not `lambda.zip` or a Markdown file. Do not run this Spark script in the Lambda editor.

Checkpoint: your script object exists and its S3 URI uses your bucket.

## Step 11 — Create the EMR Serverless Spark application

**Dependencies:** approved EMR runtime role; service-linked role initialized; EMR Studio console access available. The current service grants cover many EMR actions, but IAM role creation is still missing. Identity Center setup can require additional permissions depending on the account's Studio configuration.

1. Open **Amazon EMR**, confirm the Region, then select **EMR Serverless**.
2. Choose **Manage applications** and an existing company-approved Studio. If no Studio exists, the console offers a get-started/create-and-launch flow. Use administrator assistance if that flow requires permissions you do not have.
3. From the application interface, choose **Create application**.
4. Enter your application name and choose **Spark**.
5. Select an approved supported release; record its label and Spark version.
6. Choose batch jobs rather than interactive notebook workloads. Review application settings: maximum capacity, pre-initialized capacity, auto-start, auto-stop, and networking.
7. For this intermittent example, use no pre-initialized workers where allowed, keep automatic start/stop enabled, and use a company-approved capacity limit. Do not change network settings without understanding the account's requirements.
8. Create the application and record its ID.

These steps follow [EMR console getting started](https://docs.aws.amazon.com/emr/latest/EMR-Serverless-UserGuide/gs-console.html); capacity/settings details are in [application creation](https://docs.aws.amazon.com/emr/latest/EMR-Serverless-UserGuide/studio.html). Menu labels can change. The bundled Spark version need not match your local installation.

If first use fails on `iam:CreateServiceLinkedRole`, have the administrator prepare the EMR Serverless service-linked role. The role used for submitting your job is a separate runtime role. A notebook Workspace is not needed for this batch path.

Checkpoint: the Spark application exists, and its Region, release, ID, capacity, and auto-stop choices are recorded.

## Step 12 — Submit your Bronze → Silver job

1. Open the application details and choose **Submit job**.
2. Configure these fields; names may vary slightly with the console layout.

| Field | Value |
| --- | --- |
| Job name | `richard-citibike-bronze-to-silver` |
| Runtime/execution role | Administrator-provided EMR role, such as `RichardCitiBikeEMRRole` |
| Script location | The copied S3 URI of `bronze_to_silver.py` |
| Script arguments | Your bucket name alone, without `s3://` or a prefix |
| Spark submit parameters | `--conf spark.sql.session.timeZone=UTC` |
| S3 log destination | `s3://YOUR-BUCKET/logs/emr/` |

3. Review and submit your job. Do not choose a built-in sample in place of your script.
4. Record the job run ID and follow its state until it reaches `SUCCESS` or a failure state.
5. If it fails, open the state details and inspect available logs before resubmitting.

The runtime role needs Bronze/script read access and Silver read/write/delete access; overwrite can delete existing output. The guide also requests logs under `logs/emr/`, so the role needs write permission there. Configure S3 logging explicitly if it is not enabled by default. Read [EMR log destinations](https://docs.aws.amazon.com/emr/latest/EMR-Serverless-UserGuide/logging.html).

Checkpoint: the job reached `SUCCESS`, not merely submitted/running. Save its ID, script URI, role, bucket argument, release, and log location. Role-selection failures may reflect missing IAM read permissions even though EMR PassRole is allowed.

## Step 13 — Verify Silver and inspect Spark's results

1. In S3, refresh your bucket and navigate to `silver/citibike/station_status/`.
2. Confirm Parquet `part-*` objects exist. A `_SUCCESS` marker can also appear depending on the committer.
3. Open the EMR job's available log links or navigate to `logs/emr/` in S3; locate/download the driver output. Logs may be compressed. Managed application UI/log links depend on enabled monitoring and permissions.
4. Find the printed input schemas, Silver schema, row count, and sample rows.
5. Verify the source used `num_bikes_available`, the snapshot timestamps are populated, and inactive stations remain present.

Parquet is binary columnar storage; S3's object details page does not provide a general table preview. Downloading a Parquet object proves it is accessible, not that all rows are correct. Spark read-back and the fuller count/null/key checks remain separate verification work in Step 14 of the [code walkthrough](3.2-wed-citibike-steps.md). Do not add Athena/catalog setup solely to finish this console checkpoint.

Important interpretation:

- Silver grain is one station observation per ingestion snapshot. Removing duplicates by station ID alone would remove history.
- Metadata `dropDuplicates(["station_id"])` prevents repeated metadata from multiplying joined rows, but does not select the latest metadata. Changing metadata needs a deliberate deterministic matching strategy later.
- `last_reported` belongs to the source; snapshot time belongs to ingestion. Old source values should remain visible.
- The example overwrites Silver from all Bronze data read in that job. This is a full rebuild, not incremental processing or atomic multi-file publication. Avoid overlapping jobs, and rerun after diagnosing a failed rebuild.
- Five-minute Lambda ingestion does not refresh Silver automatically. Submit EMR again when you intentionally want to rebuild it.

Checkpoint: job success, output files, and sample/schema inspection are recorded separately. Complete data-quality validation is pending until measured.

## Troubleshooting: locate the boundary before changing anything

| Symptom | Likely boundary | Next check |
| --- | --- | --- |
| No roles shown in Lambda/EMR selector | Human IAM read access | Capture denied action; request role-list/read access or administrator setup |
| Creating Lambda with a new basic role fails | Human IAM create-role access | Use an administrator-created role |
| Lambda cannot write to S3 | Lambda role or bucket/key policy | Match `CITIBIKE_BUCKET` and Bronze object ARN; administrator checks effective permissions |
| `KeyError: CITIBIKE_BUCKET` | Function configuration | Add exact environment variable and save |
| Test still returns default greeting | Deployment | Replace default code, deploy, and test again |
| Handler/module import error | Filename/handler | Verify `lambda_function.py` and `lambda_function.lambda_handler` |
| Public feed request times out | API/networking | Check source availability and any VPC outbound configuration |
| Logs page denied but test succeeded | Human logs permissions | Request read access; check actual S3 objects meanwhile |
| Creating schedule denied | Human Scheduler/PassRole access | Both Scheduler actions and PassRole for Scheduler are required |
| Schedule exists but no snapshots | Target role or function execution | Verify Scheduler trust/invoke permission, target ARN, state, and Lambda errors |
| First EMR application creation fails on IAM | Service-linked role/account bootstrap | Administrator initializes required infrastructure role |
| EMR script cannot be read | Job role/S3 script path | Check script URI, read permissions, and encryption access |
| EMR `IndexError` for argument | Submission | Supply bucket name as the script argument |
| EMR cannot resolve a source field | Schema contract | Compare printed feed schema with expected version/field names |
| EMR output/log write denied | Job role | Check Silver/log prefixes and overwrite delete permission |

When requesting help, capture the action you attempted, resource name/ARN, Region, error text, and request/job ID. An access-denied message names a boundary to investigate; it does not justify changing unrelated roles or making the bucket public.

## Operations, cost, and completion checklist

At the nominal schedule rate, four documents per run means 288 runs and 1,152 objects per day, before retries. This is a planning estimate. Stored objects, logs, Lambda activity, and EMR capacity can incur charges; a growing Bronze prefix makes full rebuilds increasingly expensive.

- Disable the schedule in the Scheduler console when practice is paused. Under the supplied policy, an administrator may need to do this for you; agree who owns it before enabling automation.
- Stop unneeded EMR capacity and check auto-stop configuration. Disabling ingestion does not stop a running EMR job or remove stored objects.
- Preserve Bronze for replay unless an intentional retention policy says otherwise. If bucket versioning is on, replacing Silver can retain older versions.
- Do not delete company-shared roles, applications, or buckets during cleanup.

| --- | --- | --- |
