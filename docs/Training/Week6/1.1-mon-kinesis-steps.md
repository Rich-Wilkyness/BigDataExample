# Citi Bike Kinesis walkthrough: capture, publish, archive, and replay

> Status: Prepared learning lab; AWS execution, permissions, delivery latency, and billing unverified. Sources reviewed: 2026-10-12. Scale: Two real Citi Bike station observations plus one intentional resend, one provisioned shard. No AWS resources were created while authoring this guide.

## Overview and learning objectives

Build a small pipeline with an inspectable data contract, raw archive, independent reader, replay experiment, and cleanup procedure. These are useful workplace habits before adding a distributed engine and a private database.

```text
Citi Bike GBFS API → local Python capture → AWS CLI producer
                                                 │
                                                 ▼
                      Kinesis Data Streams → Data Firehose → private S3 Bronze
                                  │
                                  └── independent CLI reader → inspect / replay

Later extension, planned:
Kinesis → Glue Streaming → validated history / latest state → Aurora PostgreSQL
```

Firehose supplies managed archival delivery. The CLI reader makes the log behavior visible; it is a diagnostic tool, not a production consumer with durable checkpointing. The local Python capture uses the same GBFS discovery source as your Week 5 pipeline. A deployed Lambda producer can later replace the local capture/CLI without changing the event contract; this first stage does not modify your existing Lambda.

This architecture deliberately begins with durable ingestion before database integration. The [lecture](1_Mon_AWS_Kinesis_MSK.md) explains the classroom Lambda → Kinesis → Glue → Aurora pipeline; the [homework](1.2-mon-kinesis-msk-homework.md) does not require this cloud lab.

After the core lab, you should be able to publish records, explain partition keys, verify S3 delivery by payload, read independently, reproduce duplicates, replay retained records, and remove the billable lab resources.

The [lab files and concept map](1.3-mon-kinesis-lab/README.md) connect lecture sections to named functions, fixtures, policies, and the SQL illustration. Start with its offline retry demonstration before spending time on cloud setup.

## Checkpoint 2: capture Citi Bike and define the event contract

Use Citi Bike's [GBFS discovery endpoint](https://gbfs.citibikenyc.com/gbfs/gbfs.json) to look up `station_status`; do not hardcode the redirected feed host. Discovery was checked on 2026-10-12 and advertised GBFS 1.1 with English feed URLs. This adapter expects that response shape and fails visibly if it changes. GBFS versions can change field names and timestamp representations; do not silently apply a newer version's schema. See the [versioned GBFS specification](https://github.com/MobilityData/gbfs/blob/v1.1/gbfs.md).

**Grain:** One captured station-status observation. The script keeps the complete station record under `source_record`, copies key fields to the event envelope, and adds ingestion metadata. No availability calculation or homework transformation is performed.

The source code lives in [capture.py](1.3-mon-kinesis-lab/capture.py), with identity and validation in [contract.py](1.3-mon-kinesis-lab/contract.py). Read the comments around `ingested_at`, `make_event`, and validation, then run the saved script. It writes data into your scratch directory, not into the code folder:

```bash
python3 "$KINESIS_LAB_CODE/capture.py" --output-dir "$KINESIS_LAB_DIR" --limit 2
python3 -m json.tool "$KINESIS_LAB_DIR/station-a.json"
python3 -m json.tool "$KINESIS_LAB_DIR/station-b.json"
export KINESIS_LAB_STATION_A="$(jq -r '.station_id' "$KINESIS_LAB_DIR/station-a.json")"
export KINESIS_LAB_STATION_B="$(jq -r '.station_id' "$KINESIS_LAB_DIR/station-b.json")"
```

The manifest lists the source station count, selected event IDs, capture timestamp, source TTL, and snapshot ID. The script also writes `events.jsonl` for the later batched producer. Use a fresh scratch directory if you repeat this capture.

**Expected:** The manifest contains two event hashes, the source station count, feed TTL, and one snapshot ID; the event files contain two different real station IDs. Actual IDs, counts, timestamps, and availability vary; no fixed source count is promised. A network/HTTP/JSON/schema failure stops this checkpoint: fix it before publishing. Do not fall back to invented station values.

**Identity policy:** `event_id` hashes the source-system name and complete canonical station payload, excluding capture metadata. An unchanged station payload has the same ID across polls; changed content produces a new ID even if its source timestamp is unchanged. `snapshot_id` identifies this particular API capture. This is the lab's explicit duplicate definition, not a claim that GBFS supplies a unique event ID. Production schema changes need a versioned identity policy if added/removed source fields change these hashes.

**Record boundaries:** Each event file ends with a newline, making Firehose's concatenated S3 output readable as JSON Lines. Leave extra newline appending off. The local full response supports inspection; the S3 archive receives only the selected station events. It is not yet a complete archive of every Citi Bike station or source envelope.

**Freshness:** Fetching now does not prove the station report is current. Inspect `last_reported`, feed `last_updated`, and `ingested_at` separately. A later poll may return the same state. Preserve source fields rather than replacing source timestamps with the current time.

**Ownership:** Your producer owns capture metadata, serialization, and identity. Kinesis stores bytes; it does not validate JSON or enforce uniqueness. Explain what your pipeline should do with an absent station ID, a negative count, or an unsupported schema version before proceeding.

## Checkpoint 3: create a bounded stream

One provisioned shard makes capacity explicit for this tiny experiment. It continues to incur shard charges until deleted. This is not a recommendation for production traffic.

```bash
aws kinesis create-stream --stream-name "$KINESIS_LAB_STREAM" --stream-mode-details StreamMode=PROVISIONED --shard-count 1 --region "$KINESIS_LAB_REGION" --no-cli-pager
aws kinesis wait stream-exists --stream-name "$KINESIS_LAB_STREAM" --region "$KINESIS_LAB_REGION" --no-cli-pager
aws kinesis describe-stream-summary --stream-name "$KINESIS_LAB_STREAM" --region "$KINESIS_LAB_REGION" --no-cli-pager
export KINESIS_LAB_STREAM_ARN="$(aws kinesis describe-stream-summary --stream-name "$KINESIS_LAB_STREAM" --query StreamDescriptionSummary.StreamARN --output text --region "$KINESIS_LAB_REGION" --no-cli-pager)"
aws kinesis add-tags-to-stream --stream-name "$KINESIS_LAB_STREAM" --tags Project=week6-kinesis Environment=learning --region "$KINESIS_LAB_REGION" --no-cli-pager
```

**Expected:** `ACTIVE`, one open shard, and the default retention of 24 hours. Save the stream ARN. If the name already exists, inspect ownership and choose a new dedicated name rather than silently adopting an existing stream.

The waiter is a readiness check, not a producer or recurring task. [CreateStream](https://docs.aws.amazon.com/cli/latest/reference/kinesis/create-stream.html) and [stream waiter](https://docs.aws.amazon.com/cli/latest/reference/kinesis/wait/stream-exists.html).

## Checkpoint 4: create the private raw archive

Use the AWS console for these configuration steps:

1. **S3 → Create bucket:** Choose a globally unique name such as `week6-station-archive-ACCOUNTID-SUFFIX`, the same Region, and a general purpose bucket. Keep Block Public Access enabled, ACLs disabled, and default encryption enabled. Leave versioning disabled for this disposable lab; production versioning requires its own retention and deletion policy.
2. Record the exact bucket name. Use a dedicated bucket to make ownership and cleanup unambiguous.
3. **Amazon Data Firehose → Create Firehose stream:** Source = **Amazon Kinesis Data Streams**; destination = **Amazon S3**. Select your stream and name the delivery stream `week6-station-archive-dev`, or the value you chose earlier.
4. Set the destination to the new bucket and S3 prefix to `bronze/station-status/`. Set an error-output prefix such as `errors/!{firehose:error-output-type}/`. Keep dynamic partitioning, Lambda transformation, format conversion, and extra newline appending disabled. Choose uncompressed output for easy inspection.
5. For a short lab, use a 1 MiB buffer size and a 60-second buffer interval if offered for this configuration. These are delivery hints, not an exact latency promise. Record the actual accepted values.
6. Enable error logging. Create/select a dedicated Firehose role with source-stream read and destination-bucket write access; inspect its policy and trust before proceeding.
7. Create the delivery stream and wait until its status is **Active**. Record its ARN, role name, logging group, and settings.

Firehose starts reading a Kinesis source at `LATEST`. Publish the test records **after** Firehose is active; records published earlier are not automatically backfilled into the new delivery stream. [Source/destination choices](https://docs.aws.amazon.com/firehose/latest/dev/create-name.html) and [Kinesis source behavior](https://docs.aws.amazon.com/firehose/latest/dev/writing-with-kinesis-streams.html).

Back in the terminal, set the bucket name and inspect the delivery configuration:

```bash
export KINESIS_LAB_BUCKET='your-exact-new-bucket-name'
aws firehose describe-delivery-stream --delivery-stream-name "$KINESIS_LAB_DELIVERY" --region "$KINESIS_LAB_REGION" --no-cli-pager
```

**Expected:** Active status, your Kinesis source ARN, and your bucket ARN. A name match alone is insufficient evidence of correct wiring.

## Checkpoint 5: publish and deliberately resend one observation

Publish captured station A, resend its exact saved event, then publish captured station B. A and B are local labels for the two real IDs selected in checkpoint 2:

```bash
aws kinesis put-record --stream-name "$KINESIS_LAB_STREAM" --partition-key "$KINESIS_LAB_STATION_A" --data "fileb://$KINESIS_LAB_DIR/station-a.json" --region "$KINESIS_LAB_REGION" --no-cli-pager
aws kinesis put-record --stream-name "$KINESIS_LAB_STREAM" --partition-key "$KINESIS_LAB_STATION_A" --data "fileb://$KINESIS_LAB_DIR/station-a.json" --region "$KINESIS_LAB_REGION" --no-cli-pager
aws kinesis put-record --stream-name "$KINESIS_LAB_STREAM" --partition-key "$KINESIS_LAB_STATION_B" --data "fileb://$KINESIS_LAB_DIR/station-b.json" --region "$KINESIS_LAB_REGION" --no-cli-pager
```

**Expected:** Each accepted write returns a `ShardId` and `SequenceNumber`. The two A writes have the same business event identity but different stream positions. All three records use one shard because the stream has only one shard, not because their keys match.

`fileb://` sends raw file bytes, avoiding accidental double base64 encoding. The returned sequence numbers describe stream positions, not uniqueness of your station observations. [CLI binary input and PutRecord](https://docs.aws.amazon.com/cli/latest/reference/kinesis/put-record.html).

**Job connection:** This deliberate resend models a producer that retries after an uncertain timeout. Raw ingestion should preserve what arrived; a curated sink decides how duplicates contribute to published results.

## Checkpoint 6: read independently from the beginning

List shards, select the sole shard, and request its oldest retained position:

```bash
aws kinesis list-shards --stream-name "$KINESIS_LAB_STREAM" --region "$KINESIS_LAB_REGION" --no-cli-pager
export KINESIS_LAB_SHARD="$(aws kinesis list-shards --stream-name "$KINESIS_LAB_STREAM" --query 'Shards[0].ShardId' --output text --region "$KINESIS_LAB_REGION" --no-cli-pager)"
export KINESIS_LAB_ITERATOR="$(aws kinesis get-shard-iterator --stream-name "$KINESIS_LAB_STREAM" --shard-id "$KINESIS_LAB_SHARD" --shard-iterator-type TRIM_HORIZON --query ShardIterator --output text --region "$KINESIS_LAB_REGION" --no-cli-pager)"
aws kinesis get-records --shard-iterator "$KINESIS_LAB_ITERATOR" --limit 100 --region "$KINESIS_LAB_REGION" --no-cli-pager > "$KINESIS_LAB_DIR/read.json"
jq '{records: (.Records | length), lag_ms: .MillisBehindLatest}' "$KINESIS_LAB_DIR/read.json"
python3 "$KINESIS_LAB_CODE/inspect-stream.py" "$KINESIS_LAB_DIR/read.json"
```

**Expected eventually:** The two A observations and one B observation. A read can return fewer records or an empty batch even when you expect more. Wait at least one second between these small manual reads, then advance using the response's `NextShardIterator`:

```bash
export KINESIS_LAB_ITERATOR="$(jq -r '.NextShardIterator' "$KINESIS_LAB_DIR/read.json")"
aws kinesis get-records --shard-iterator "$KINESIS_LAB_ITERATOR" --limit 100 --region "$KINESIS_LAB_REGION" --no-cli-pager > "$KINESIS_LAB_DIR/read.json"
```

Decode each response before overwriting it if you want to save all observed records. Iterators expire; if you pause too long, request a new one. This manual reader does not persist a checkpoint or track every shard in a scaled stream. [GetShardIterator](https://docs.aws.amazon.com/kinesis/latest/APIReference/API_GetShardIterator.html) and [GetRecords](https://docs.aws.amazon.com/kinesis/latest/APIReference/API_GetRecords.html).

**Explain:** Reading did not remove data and did not change Firehose's independent progress. Independent consumers still share read throughput unless a dedicated-throughput approach is used.

## Checkpoint 7: verify archival delivery by payload

Wait for buffering/delivery, then list the archive. An empty result immediately after publishing is not proof of failure.

```bash
aws s3 ls "s3://$KINESIS_LAB_BUCKET/bronze/station-status/" --recursive --region "$KINESIS_LAB_REGION" --no-cli-pager
aws s3 cp "s3://$KINESIS_LAB_BUCKET/bronze/station-status/" "$KINESIS_LAB_DIR/archive/" --recursive --region "$KINESIS_LAB_REGION" --no-cli-pager
```

Use [inspect-archive.py](1.3-mon-kinesis-lab/inspect-archive.py) to inspect all downloaded nonempty JSON lines and compare business identities:

```bash
python3 "$KINESIS_LAB_CODE/inspect-archive.py" "$KINESIS_LAB_DIR/archive"
```

**Expected baseline:** Three raw records and two unique event IDs, with the event ID from `station-a.json` present twice and the ID from `station-b.json` once. Firehose retries can produce additional duplicates; investigate and record them rather than claiming the service guarantees exactly three. Re-download if delivery is still incomplete. File counts need not equal event counts because Firehose batches records. [Delivery behavior](https://docs.aws.amazon.com/firehose/latest/dev/basic-deliver.html).

If parsing fails, inspect one file and verify your producer newline and Firehose delimiter settings. Do not enable both without considering the resulting record boundaries.

## Checkpoint 8: replay and reason about sink safety

Request another `TRIM_HORIZON` iterator using checkpoint 6 and read again. You should be able to observe the same retained events, subject to reading enough responses. The replay remains possible because reading did not delete the records.

Record these distinctions:

- A replayed record has its original sequence number; the deliberately republished A record has a different sequence number.
- Both can produce repeated business effects in a naive sink.
- Kinesis retention limits how far back you can replay. S3 provides a separate archive after stream expiry.
- Replaying through the diagnostic reader does not ask Firehose to archive old data again.

**Learner design task:** Describe how a curated destination would recognize the repeated `event_id`, how it would handle an older observation arriving late, and what transaction boundary would make retries safe. Do not delete a running query's checkpoint to experiment on a shared sink.

### Next practice: batched production and partial failures

Read [producer.py](1.3-mon-kinesis-lab/producer.py), especially `batches` and `publish_batch`. First run the local [failure demonstration](1.3-mon-kinesis-lab/demonstrate-retries.py), which uses labeled synthetic fixtures and makes no AWS requests:

```bash
python3 "$KINESIS_LAB_CODE/demonstrate-retries.py"
```

**Predict, then verify:** The request sizes are `[2, 1, 1]`. The first response is HTTP 200 with one failed record. Only that failed entry is retried. Its next reply is lost after simulated acceptance, so retrying it again produces three simulated stored records for two business identities. The code preserves the original bytes and ID across attempts, uses bounded exponential backoff with full jitter, and fails visibly if retries are exhausted. These are the lecture's producer guarantees and limitations made observable.

After the baseline and second capture, install the cloud-only SDK in the repository environment and publish the second capture's saved JSON Lines:

```bash
.venv/bin/python -m pip install -r "$KINESIS_LAB_CODE/requirements.txt"
.venv/bin/python "$KINESIS_LAB_CODE/producer.py" --events "$KINESIS_LAB_NEXT_DIR/events.jsonl" --stream-arn "$KINESIS_LAB_STREAM_ARN" --region "$KINESIS_LAB_REGION" --profile "$AWS_PROFILE" --journal "$KINESIS_LAB_DIR/publish-next.jsonl"
```

**Expected:** A new JSON Lines journal records planned events, attempts, each confirmed sequence number, retry delays/failures when encountered, and completion or abort. A healthy live run may have no partial failures; the local demo supplies the deterministic failure case. Review the [producer permission template](1.3-mon-kinesis-lab/policies/producer-permissions.template.json) for `PutRecords` access to the dedicated stream.

A complete producer journal means Kinesis acknowledged the entries, not that Firehose delivered them. Revisit the S3 inspection and reconcile against all accepted writes. Repeated captures can reuse event IDs when source state is unchanged. Use a new journal filename for each additional run; inspect unresolved attempts rather than blindly resending a whole capture. The README explains SDK/request retries, application/record retries, and restart limitations.

For job-oriented evolution, move capture and publishing into a dedicated Lambda producer with bounded SDK retries and per-record failure accounting, then schedule it at a source-appropriate cadence. A one-time local capture is a foundation for streaming ingestion; it is not continuous API collection. The supplied producer demonstrates batching/backoff for a saved sample, and the capture supports up to 100 selected stations. Full-city collection additionally needs a durable outbox/restart strategy and complete per-snapshot reconciliation; do not send the entire snapshot as one oversized record.

## Checkpoint 9: inspect operations and collect evidence

Use **Kinesis → stream → Monitoring**, **Firehose → stream → Monitoring / error logs**, and the **CloudWatch console**. Low-volume metrics may take time to appear.

| Boundary | Evidence to collect | Interpretation |
| --- | --- | --- |
| Producer → Kinesis | Saved successful responses; `IncomingRecords`, `IncomingBytes` | Writes reached the stream |
| Kinesis → diagnostic reader | Decoded payloads and sequence numbers; `MillisBehindLatest` | This reader can access retained data |
| Firehose → S3 | `DeliveryToS3.Success`, `DeliveryToS3.DataFreshness`, logs, downloaded payloads | Delivery progressed and content matches the contract |
| Business output | Raw and distinct event counts | Demonstrates repeated observations and reconciliation |
| Cost | Created resources, session duration, configuration, later billing review | Makes resource lifetime and spend attributable |

Do not use this reader's lag as proof that another consumer is caught up. Do not use a successful write API response as proof that the event reached S3. [Kinesis monitoring](https://docs.aws.amazon.com/streams/latest/dev/monitoring-with-cloudwatch.html) and [Firehose monitoring](https://docs.aws.amazon.com/firehose/latest/dev/monitoring-with-cloudwatch-metrics.html).

## Failure model and debugging guide

| Symptom | First checks | Repair and validation |
| --- | --- | --- |
| `AccessDenied` on creation | Identity, account/Region, exact denied action/resource | Obtain the scoped required permission; repeat the failed checkpoint |
| Firehose active but no objects | Published after activation? Correct source ARN? Buffering? Role/log errors? | Fix source/destination or role; publish a new event and read its archived payload |
| `ExpiredIteratorException` | Time since iterator creation | Get a fresh iterator with an intentional starting position |
| Empty CLI response | Starting position, propagation, selected shard | Follow `NextShardIterator`; do not interpret one empty response as end-of-stream |
| Unexpected raw count | Producer resends, delivery retries, archive not fully delivered | Compare identities and timestamps; separate missing events from duplicates |
| Throttled reads/writes | Consumer count, hot shard, request rate, capacity | Back off, inspect usage, and size intentionally before retrying |

The capture validates selected fields and the producer validates saved input before sending. Invalid selected input fails the bounded run visibly. Durable quarantine with an error reason and safe identifying context remains planned; the core lab does not prove that production behavior.

## Production evolution: Glue Streaming → Aurora (planned extension)

Add this only after the core lab works and you need relational serving or Spark processing. It is a separate billable integration project, not an unexecuted code snippet claimed to be production-ready.

1. **Define the destination contract:** Decide history versus latest-state grain, source identity, event key, late-update policy, and duplicate behavior. Use a dedicated database schema and test data. Keep the homework's ordinary `station_stream` table separate from a production design that enforces uniqueness.
2. **Provision private connectivity:** Put Aurora in private subnets; allow PostgreSQL access from the Glue connection's security group. Configure Glue's required internal security-group rules and service access paths. Provide S3 access and Kinesis interface endpoint access or suitable egress; add routes/endpoints for logs and other APIs actually called. An S3 gateway endpoint alone does not provide Kinesis access.
3. **Configure database authentication:** Enable supported IAM DB authentication, provision a limited PostgreSQL writer with `rds_iam` and needed SQL privileges, and grant the Glue role `rds-db:connect` for that exact resource-ID/user. Generate tokens for new connections and verify TLS. Alternatively use a rotated Secrets Manager secret with scoped access when that fits the environment.
4. **Configure the Glue source:** Use a streaming job and a supported Glue runtime. Set the exact stream ARN, JSON classification, explicit DDL schema with inference disabled, and a unique S3 checkpoint prefix. The saved [Glue source options](1.3-mon-kinesis-lab/glue-source.template.json) provide this projection; replace the stream ARN before use. Turn on consumer-lag metrics if supported. The projected event fields are `schema_version INT`, `event_id STRING`, `station_id STRING`, count fields `INT`, `last_reported BIGINT`, and `ingested_at STRING`; add `source_system STRING`, `snapshot_id STRING`, and provenance fields as needed. The archive retains the nested `source_record`; a curated projection need not parse every nested field. Parse and validate time before publication.
5. **Implement processing incrementally:** First inspect a small batch's schema and safe identifiers. Then add validation/quarantine. Finally add a bounded database sink with transactions, conflict behavior, and controlled writer concurrency. Avoid collecting the entire production stream or opening one connection per event.
6. **Test the commit boundary:** Send valid, duplicate, malformed, and late observations. Stop/restart with the same checkpoint; prove stable curated counts and latest state. The optional [PostgreSQL idempotency illustration](1.3-mon-kinesis-lab/sql/idempotency-demo.sql) shows a unique event key and repeat-safe insert in a separate learning table. In an isolated test environment, simulate failure after database commit but before checkpoint progress and verify safe reprocessing.
7. **Test an outage and reconcile:** Temporarily stop the dedicated consumer while sending a bounded number of events. Restore it within retention, confirm lag decreases, and reconcile accepted, rejected, and published identities. Extend this to a database outage only after the retry/idempotency behavior is implemented.
8. **Operationalize and clean up:** Record freshness objectives, lag alerts, database connection limits, retry ownership, schema deployment rules, cost controls, and shutdown procedure. Stop Glue streaming explicitly when the experiment ends; inspect Aurora's actual auto-pause eligibility and retained storage.

Use [Glue Kinesis options](https://docs.aws.amazon.com/glue/latest/dg/aws-glue-programming-etl-connect-kinesis-home.html), [Glue JDBC/VPC guidance](https://docs.aws.amazon.com/glue/latest/dg/setup-vpc-for-glue-access.html), and the lecture's Aurora authentication references. This extension deliberately leaves business transformations and SQL for the learner; database provisioning and runtime validation remain pending.
