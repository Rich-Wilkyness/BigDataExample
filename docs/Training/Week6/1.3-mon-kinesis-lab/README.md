## Read the files in this order

Start with `contract.py` → `capture.py` → `demonstrate-retries.py` → `producer.py` → the two inspection scripts. Read the tests and optional Glue/SQL/policy files after you can trace one event through that path.

Each Python file has `Section` comments for its major responsibilities and `Step` comments inside longer functions. Function docstrings describe the input/output or purpose. Read the section headings first, then trace the data through one function at a time. `main()` connects terminal arguments to the reusable functions; the final `if __name__ == '__main__'` block starts the program only when you run that file directly.

The first learning goal is to explain where an event comes from, how its identity survives a retry, and what counts as success. You can leave the SDK test machinery until later. JSON explanations live below and in the policy README because standard JSON does not allow comments or extra explanatory fields in AWS configuration.

## Run the local failure demonstration first

From the repository root, no AWS credentials or third-party packages are needed:

```bash
python3 docs/Training/Week6/1.3-mon-kinesis-lab/demonstrate-retries.py
python3 -m unittest discover -s docs/Training/Week6/1.3-mon-kinesis-lab/tests -v
```

The demonstration prints attempts, failures, and deterministic delays. Its final summary should include:

```json
{
  "http_status_on_partial_success": 200,
  "request_sizes": [2, 1, 1],
  "confirmed_logical_entries": 2,
  "simulated_stored_records": 3,
  "distinct_event_ids": 2
}
```

This is a selection of summary fields. Two entries were submitted initially; only B was retried. The fake service stored B before raising an ambiguous timeout, so retrying B created a second stored copy. The producer could not distinguish that timeout from a request that never arrived. No AWS network call or actual waiting occurs in this demonstration.

The fixture station IDs begin with `fixture-`; they must not be described as live Citi Bike observations. The core cloud walkthrough continues to use real source capture.

## Cloud SDK setup

The capture, inspection, and offline demonstration use Python's standard library. The cloud producer additionally needs Boto3. Use the repository environment; install the lab-specific requirement only if needed:

```bash
.venv/bin/python -m pip install -r docs/Training/Week6/1.3-mon-kinesis-lab/requirements.txt
```

Run the SDK request/journal check after installation:

```bash
.venv/bin/python docs/Training/Week6/1.3-mon-kinesis-lab/tests/check-sdk.py
```

The pinned SDK version records the local validation environment; update it intentionally when revisiting the lab. Local SDK validation does not prove AWS permissions or writes.

The producer uses one reusable Kinesis client and the default credential chain or an explicitly supplied profile. Never put credentials in a JSON event or policy file. Request-level SDK retries use standard mode with three total attempts. The outer loop separately handles partial record results and ambiguous transport failures, with five total application attempts per batch. These layers can compound to as many as fifteen SDK request attempts for one continually pending batch. This is an attempt bound, not a strict wall-clock deadline.

## File-by-file reading guide

### contract.py — define one valid observation

[Open the file](contract.py). Input: a source station dictionary plus capture metadata. Output: a validated event dictionary. Read its sections as **build event → validate fields → load saved events**.

`make_event` generates a stable content hash without the changing capture timestamp. `validate_event` checks the fields used by this lab; it does not implement a full schema registry or quarantine system. `load_events` validates the small saved sample before the producer sends it. The original station fields stay under `source_record` so you can inspect what the source supplied.

### capture.py — retrieve and save a bounded sample

[Open the file](capture.py). Input: `--output-dir PATH` and optional `--limit 2`. Output: event files, raw response copies, and `capture-manifest.json`. Read **HTTP fetch → feed discovery → sample selection → event construction → file publication**.

`fetch` is a replaceable function: the normal run uses the API, while tests supply local dictionaries. `snapshot_id` groups one capture, and `ingested_at` records when the producer retrieved it. A capture manifest describes selected work; it does not prove any Kinesis write. Use a fresh output directory each time; existing captures are protected. The lab allows 2–100 selected stations.

### producer.py — publish saved events with bounded retries

[Open the file](producer.py). Input: saved JSON Lines, stream ARN, Region/profile, and a new journal path. Output: Kinesis requests and a local acknowledgement journal. Read **limits → failure outcomes → batches → retry loop → AWS/CLI wiring**.

Inside `publish_batch`, follow `pending`: it begins as all entries, loses confirmed entries after a partial response, and remains unchanged after an ambiguous timeout. `send`, `emit`, `sleep`, and `uniform` are supplied functions; replacing them lets the same algorithm run in a deterministic local demonstration. The comments explain where ordering, identity, retry limits, and uncertainty matter.

The journal records intended work and observed acknowledgements, not an atomic commit with Kinesis. Preserve the event file and inspect unresolved attempts before replaying. This synchronous teaching producer loads a small sample; durable outbox/restart handling, full-city collection, source retry policy, and dead-letter routing remain later work.

### demonstrate-retries.py — see why duplicates happen

[Open the file](demonstrate-retries.py). Input: the two saved synthetic fixtures. Output: a predictable timeline and summary. Read **prepare events → fake service → real retry algorithm → assertions → summary**.

The fake service first accepts A and rejects B, then accepts B but loses the reply, then accepts B again. `calls` tracks what the producer sent; `stored` tracks what the simulated service accepted. Comparing them shows why confirmed writes and actual stored records can differ. Replaced wait/random functions make the demo immediate and repeatable.

### inspect-stream.py — decode one saved read response

[Open the file](inspect-stream.py). Input: a saved AWS CLI GetRecords JSON response. Output: one decoded record per line, with sequence number and broker arrival time.

Read **decode base64 → decode UTF-8 → parse JSON** as three different operations. Base64 is a transport representation, not encryption. The script preserves broker metadata next to the payload so arrival time is not confused with the station's event time or the producer's ingestion time. It does not poll, checkpoint, or process every shard.

### inspect-archive.py — reconcile what reached S3

[Open the file](inspect-archive.py). Input: the local directory containing downloaded, uncompressed archive files. Output: raw record count, distinct event count, and occurrences per identity.

Firehose can put several events in one object, so object count is not event count. `Counter` stores the number of appearances of each `event_id`; summing its values counts all records, while counting its keys counts distinct identities. Point this script only at the archive, not at a folder also containing manifests. File-at-a-time text loading is sufficient for this bounded lab; large archives need bounded readers.

### fixtures/station-status.json — a predictable source-shaped example

[Open the fixture](fixtures/station-status.json). This is synthetic test data, not a live capture. `version` selects the expected GBFS contract; `last_updated` is feed update time; `ttl` describes the refresh interval; `data.stations` holds the two station dictionaries.

Within each station, `station_id` identifies the station, counts describe availability, and `last_reported` is source event time. `is_installed` is an additional source field retained in `source_record`; it demonstrates that the event can preserve more source information than its top-level projection uses.

### fixtures/put-records-partial.json — HTTP success with one failed entry

[Open the fixture](fixtures/put-records-partial.json). `ResponseMetadata.HTTPStatusCode = 200` describes the request response. `FailedRecordCount = 1` says one submitted entry failed. The two `Records` results match the two request entries by array position.

The first result has `ShardId` and `SequenceNumber`, indicating acceptance. The second has `ErrorCode` and `ErrorMessage`, indicating a failed entry. This is why the producer must inspect individual results instead of treating HTTP 200 as complete success. The response is simulated and includes clearly labeled fixture values.

### glue-source.template.json — declare how Glue reads the payload

[Open the template](glue-source.template.json). Replace `__STREAM_ARN__` with the dedicated stream ARN. `classification = json` chooses the payload format; `inferSchema = false` and `schema` declare the expected top-level fields using Spark DDL text. `ingested_at` is initially a string and still needs timestamp parsing/validation in processing.

`startingPosition = trim_horizon` requests the oldest retained records when there is no recovered checkpoint. It does not reset existing checkpoint progress. `emitConsumerLagMetrics` requests supported Glue lag reporting. These are source options, not a complete job: durable per-query checkpoints, validation/quarantine, and the database sink remain separate. Nested `source_record` remains in the raw archive even though this projection omits it.

### policies/ — separate who may do what

Start with the [policy reading guide](policies/README.md). It has a separate section for each of the producer, diagnostic reader, and Firehose templates. Replace placeholders in scratch copies. Permission statements, service trust, and network reachability solve different problems; no script attaches a policy.

### sql/idempotency-demo.sql — make a repeated write harmless

[Open the PostgreSQL example](sql/idempotency-demo.sql). Read **begin transaction → create isolated table → insert → repeat insert → verify → commit**. It uses synthetic data in `week6_learning.event_receipts`, separate from the homework table.

The primary key forbids two rows with the same event identity. `ON CONFLICT DO NOTHING` lets a retry leave the existing row alone. `received_at` uses the statement timestamp, not a promised commit-completion timestamp. This illustrates the database boundary only; it does not coordinate a streaming checkpoint. Run it only in your own learning PostgreSQL database with `psql -v ON_ERROR_STOP=1 -f ...`; database execution remains pending.

### requirements.txt — install the cloud-only SDK

[Open the dependency file](requirements.txt). Boto3 is needed for live publication and the optional SDK check. The capture, inspection, demonstration, and ordinary tests use only the standard library. The pinned version records the local SDK environment; it does not pin the remote AWS service.

### tests/test.py — check failures without AWS

[Open the tests](tests/test.py). `setUp` builds a fresh synthetic sample before each test. Test names describe the behavior being protected: selective retry, exhaustion, source preservation, identity stability, and duplicate inspection.

Replaceable functions let tests choose failures and delays without the real API or real waiting. Assertions check observed outcomes rather than claiming cloud durability. Read the test matching the concept you are studying; you do not need to master the test loader first.

### tests/check-sdk.py — check the real SDK call shape locally

[Open the SDK check](tests/check-sdk.py). This later-stage example requires Boto3. `Stubber` intercepts the SDK calls and checks their parameters against queued expectations; fake credentials prevent credential-provider lookups. `patch` temporarily substitutes the session and command-line arguments while executing the actual producer/journal flow.

Temporary files hold the input and journal. The final assertions verify two accepted entries and retrying only B. No remote AWS request is made; passing this check does not prove permissions or delivery.

## Knowledge checks

- Why does the producer retry one entry after the partial response but the entire pending set after a timeout?
- Why is regenerating `event_id` inside the retry loop a correctness problem?
- If B was accepted before A's retry, can partitioning alone restore source event-time order?
- Which timestamp would you use to measure source freshness? Which additional timestamp would a real consumer generate?
- What remains unresolved if the producer exits after exhausting its retry budget?
- Why does a PostgreSQL uniqueness constraint protect a different boundary from a streaming checkpoint?
