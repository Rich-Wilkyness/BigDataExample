## Part 1 — Infrastructure as Code (IaC)

Suggested reading time: 20 minutes

### What is Infrastructure as Code?

Traditionally, engineers created cloud resources manually through web interfaces. For example, an engineer might open the AWS Console, create an S3 bucket, configure an IAM role, and then create a Glue job.

This works for small demonstrations, but it becomes difficult when an organization has dozens or hundreds of resources.

Infrastructure as Code allows engineers to define cloud resources in configuration files instead.

For example, instead of manually creating an S3 bucket, an engineer can write a configuration describing the bucket and use a tool to create it.

### Why IaC matters

IaC provides several advantages:

- Repeatability: The same configuration can create similar environments.
- Version control: Infrastructure changes can be tracked in Git.
- Consistency: Development, testing, and production environments can follow the same patterns.
- Automation: Infrastructure can be created without manually clicking through the AWS Console.
- Reviewability: Teams can review proposed infrastructure changes before applying them.

IaC does not eliminate the need to understand AWS. Engineers still need to know what resources are required, how they communicate, and what permissions they need.

## Part 2 — Terraform Fundamentals

Suggested reading time: 30 minutes

### What is Terraform?

Terraform is an Infrastructure as Code tool developed by HashiCorp. It uses a declarative configuration language called HCL (HashiCorp Configuration Language).

Declarative means we describe the infrastructure we want rather than writing every individual step required to create it.

Consider this example:

```
provider "aws" {
  region = "us-east-2"
}

resource "aws_s3_bucket" "example" {
  bucket = "my-example-data-bucket-12345"
}
```

This configuration declares an AWS S3 bucket. Terraform communicates with AWS through the AWS provider to manage the resource.

### The Terraform workflow

terraform init

Initialize the project and install providers

terraform plan

Preview proposed infrastructure changes

terraform apply

Apply the approved changes

terraform destroy

Remove Terraform-managed resources when appropriate

### Terraform state

Terraform maintains a record of the resources it manages, commonly called the state file.

The state helps Terraform understand which resources already exist and how they correspond to the configuration.

For team environments, state is commonly stored remotely rather than on an individual engineer's laptop.

State files may contain sensitive information and should be protected.

## Part 3 — Workflow Orchestration

Suggested reading time: 20 minutes

### What is orchestration?

Data pipelines often involve several tasks that must happen in a particular order.

Consider our Citi Bike project:

1\. Lambda

Collect Citi Bike data

2\. S3 Bronze

Store raw JSON

3\. AWS Glue

Transform data into Silver Parquet

4\. AWS Glue

Load data into Redshift

5\. Redshift

Update analytical tables

We could run these tasks manually, but that would be inefficient and error-prone.

An orchestration system coordinates them automatically.

A good orchestrator can manage task dependencies, detect failures, retry operations, and report execution status.

### Scheduling versus orchestration

These concepts are related but different.

Scheduling determines when something should run.

Orchestration determines what should run, in what order, and what should happen when something succeeds or fails.

A scheduler might start a pipeline every morning at 8 AM. An orchestrator manages the tasks within that pipeline.

### Reading

[AWS — Step Functions Developer Guide](https://docs.aws.amazon.com/step-functions/latest/dg/welcome.html)

### Review questions

1. Why should the Redshift load wait until the Silver transformation finishes?
    - because redshift loads from silver and if that is not done, it won't have data to use
    - **additions**: The load might find no data, partial output, or old data from a previous run. The dependency protects correctness: load only the complete, validated Silver output belonging to the intended run.
2. What should happen if the first Glue job fails?
    - have a retry policy. work that comes later should wait
    - **additions**: Use bounded retries for errors that may resolve, such as temporary service failures. If retries are exhausted or input is invalid, stop dependent tasks and report failure rather than leave them waiting indefinitely. A retry must also be safe if the job already wrote some output.
3. How is orchestration different from scheduling?
    - scheduling is when, orchestration is what and in what order
    - **additions**: That distinction is correct. Orchestration also determines what happens after success or failure: completion checks, retries, failure paths, and reporting.
4. Why is monitoring important in production data pipelines?
    - if a step gets stopped we need a way to know and isolate how to fix it
    - **additions**: Also monitor slow runs, missing expected runs, stale output, and data-quality problems. A job may report success while producing incomplete data, so operational monitoring needs data checks too.

## Part 4 — AWS Step Functions

Suggested reading time: 25 minutes

### What are Step Functions?

AWS Step Functions is a managed workflow orchestration service.

It allows engineers to create state machines that coordinate AWS services.

A state machine consists of states, such as:

- Task: Performs an action, such as starting a Glue job.
- Choice: Selects a path based on a condition.
- Wait: Delays execution.
- Parallel: Executes multiple branches.
- Succeed / Fail: Marks a workflow outcome.

### Example: Handling a Glue failure

Start Glue job

Did Glue succeed?

Yes

Continue to Redshift

No

Retry or fail workflow

Step Functions can wait for supported Glue jobs to complete before continuing. This is particularly useful when a later task depends on the successful completion of an earlier task.

[AWS — State Machines](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-statemachines.html)[AWS — States in Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-states.html)

    - **corrections**: A state machine defines workflow behavior, not just monitoring. 
        - A **state** is a named step or control point, such as `TransformSnapshot`; 
        - a **transition** specifies where execution goes next; 
        - an **outcome** is how the execution ends, such as success or failure. 
        - For example, a Task starts Glue and waits for successful completion, then transitions to validation; error handling can instead retry or take a failure path. “State” here is not a Bronze/Silver/Gold data layer, although a task can produce one of those layers. The state machine is the reusable definition; an execution is one run of it. [Reference](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-statemachines.html).

    - **additions**: Yes, your conditional interpretation is correct. Choice evaluates workflow data and selects the next state: for example, `input_ready = true` could lead to transformation, otherwise to a wait/reporting path. A task error is handled with Retry/Catch rather than automatically becoming a false condition. See the lecture’s [Choice, Retry, and Catch](2_Tue_Terraform_Airflow.md#choice-retry-and-catch) section and [AWS Choice documentation](https://docs.aws.amazon.com/step-functions/latest/dg/state-choice.html).
3. Why is it important to wait for a Glue job to complete rather than only waiting for it to start?

## Part 5 — Apache Airflow

Suggested reading time: 25 minutes

### What is Apache Airflow?

Apache Airflow is an open-source platform for developing, scheduling, and monitoring workflows.

Airflow workflows are defined in Python using Directed Acyclic Graphs (DAGs).

A DAG describes tasks and their dependencies.

Directed means tasks have a defined direction of execution. Acyclic means the dependency graph cannot contain a loop.

For example:

```python
from datetime import datetime, timedelta, timezone

from airflow.sdk import dag, task

@dag(
    dag_id="snapshot_pipeline_demo",
    start_date=datetime(2026, 10, 1, tzinfo=timezone.utc),
    schedule="@daily",
    catchup=False,
)
def snapshot_pipeline_demo():
    @task(retries=2, retry_delay=timedelta(minutes=1))
    def extract():
        print("Extracting a snapshot: demonstration only")

    @task
    def transform():
        print("Transforming a snapshot: demonstration only")

    @task
    def load():
        print("Loading a snapshot: demonstration only")

    # Build task nodes and declare dependency direction.
    extract_task = extract()
    transform_task = transform()
    load_task = load()
    extract_task >> transform_task >> load_task

snapshot_pipeline_demo()
```

This is a simplified example using Airflow 3-style imports.

### Airflow versus Step Functions

Airflow and Step Functions can both coordinate data pipelines, but they have different designs.

Airflow is particularly useful for Python-defined workflows, complex scheduling, and integrations across different systems.

Step Functions is a managed AWS service that integrates closely with AWS resources and uses state-machine definitions.

### Reading

[Apache Airflow — DAGs](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/dags.html)[Apache Airflow — Tasks](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/tasks.html)

### Review questions

1. What does DAG stand for?
    - directed = defined direction of flow
    - asyclic = cannot move backwards after a step
    - graph = tasks are nodes; dependencies are edges.
    - **corrections**: Directed and graph are right. The spelling is **acyclic**, meaning there is no dependency path that returns to the same task. It does not mean “you can never reprocess data or retry a task.” Historical reruns and retries are possible without creating cycles in the dependency graph.
2. Why can't a DAG contain circular dependencies?
    - because it's about getting data to a certain state before moving forward. once you get it to gold, you shouldn't be going back to silver for the same data
    - **corrections**: A dependency cycle makes prerequisites impossible to satisfy: if A waits for B and B waits for A, neither can start. The rule concerns task dependencies, not medallion layers. You can recompute Silver and Gold from retained Bronze in another run when correcting data. [Reference](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/dags.html).
3. How does Airflow represent dependencies between tasks?
    - are you talking about the decorators from the example? like `@task def extract`
    - **corrections**: `@task` creates a task definition from a function. The dependency is expressed by `extract_task >> transform_task >> load_task`: transform is downstream of extract, and load is downstream of transform. Under the default success-based rule in this example, each downstream task waits for upstream success. `>>` is an Airflow dependency operation here, not a call that executes all three functions immediately. [Reference](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/tasks.html).
4. What is one reason to choose Airflow instead of Step Functions?
    - you're not using AWS cloud, either on-prem or another option
    - **additions**: That is a valid reason to consider Airflow, especially for workflows spanning different systems. Airflow can also orchestrate AWS services. Python-defined workflows, scheduling, and historical backfills can be reasons to choose it even when the data lives in AWS.

## Part 6 — Cron and Scheduling

Suggested reading time: 15 minutes

### What is Cron?

Cron is a traditional Unix/Linux utility used to schedule commands at specific times or intervals.

A Cron expression commonly contains five fields:

## 0

Minute

## 8

Hour

## \*

Day

## \*

Month

## 1-5

Weekday

Runs at 8:00 AM, Monday through Friday, in the configured timezone.

Other examples:

```
# Every day at midnight
0 0 * * *

# Every 15 minutes
*/15 * * * *

# Every Sunday at 2 AM
0 2 * * 0
```

Cron is useful for scheduling individual commands, but it doesn't provide the same built-in workflow dependency management as Airflow or Step Functions.

AWS EventBridge Scheduler provides cloud-based scheduling functionality. Its Cron syntax differs from traditional Linux Cron, so expressions should not be copied between them without checking the documentation.

### Review questions

1. What does `*/15 * * * *` mean?
    - every 15 mins of every day, of every month, do the thing
    - **additions**: Correct. More precisely, it matches minutes 0, 15, 30, and 45 of every hour. It does not mean “wait 15 minutes after the previous run finishes”; slow commands can overlap. [Reference](https://man7.org/linux/man-pages/man5/crontab.5.html).
2. What is the difference between Cron and Step Functions?

    - **additions**: Correct distinction. Say “tasks or service operations” rather than resources: Step Functions coordinates actions using resources, while Terraform provisions the resource definitions. Step Functions also handles configured completion and error paths.
3. Why might a cloud-based scheduler be preferable to a Cron job running on someone's laptop?
    - more employees can have access, if someone is sick or leaves the company
    - you can couple it with other AWS resources more naturally
    - **additions**: Both are useful benefits. The main reliability benefit is removing dependence on a personal laptop being awake, connected, and correctly configured. Shared access still depends on permissions, and a successful scheduled invocation does not prove the downstream workflow completed.
4. Can Cron automatically coordinate a multi-step pipeline with complex dependencies?
    - it can schedule the first part of a step function pipeline, from there the step functions handle the flow of start and stop
    - **corrections**: Your example describes a workable combination, but answer the question explicitly: **Cron alone does not manage those dependencies.** Cron can run a command that requests a Step Functions execution, using suitable credentials; Step Functions then coordinates the tasks. If Cron launches a custom script instead, that script must implement dependency and recovery behavior.

## Part 7 — Comparing the technologies

Study this table before completing the final exercise.

| Technology            | Primary purpose                      | Typical example                  |
| --------------------- | ------------------------------------ | -------------------------------- |
| Terraform             | Provision infrastructure             | Create a Glue job and IAM role   |
| Step Functions        | Orchestrate AWS workflows            | Run Glue after Lambda            |
| Apache Airflow        | Schedule and orchestrate DAGs        | Coordinate daily ETL             |
| Cron                  | Schedule commands                    | Run a script every hour          |
| EventBridge Scheduler | Trigger AWS operations on a schedule | Invoke Lambda every five minutes |

An important distinction is that these tools are often used together rather than as direct alternatives.

For example, Terraform can create a Step Functions state machine, EventBridge Scheduler can start it periodically, and Step Functions can coordinate the Glue and Redshift operations.
