### 3. Idempotency and deduplication

An idempotent operation produces the same intended final state when repeated with the same input.

For example, suppose a station observation has:

```
station_id = 123
snapshot_timestamp = 2026-10-14 12:00:00
available_bikes = 8
```

If the same observation is loaded three times, the canonical table should still contain only one logical observation for that station and timestamp.

You must understand how to achieve this using stable business keys, staging tables, `MERGE`, `NOT EXISTS`, or other appropriate SQL techniques.

**additions — SQL walkthrough:** These are isolated Amazon Redshift teaching examples, not the assignment's completed transformation. They use temporary tables and synthetic values. They have not been executed against Redshift. Run the blocks in one database session if you choose to try them.

Choose the logical key first: here it is `(station_id, snapshot_timestamp)`, with both fields non-null. This example assumes duplicate copies of an observation agree on `available_bikes`. Your real design must define what to do if the same key arrives with conflicting values.

```sql
-- Session-local tables keep this example separate from pipeline tables.
CREATE TEMP TABLE learning_landing (
    station_id VARCHAR(20) NOT NULL,
    snapshot_timestamp TIMESTAMP NOT NULL,
    available_bikes INTEGER NOT NULL
);
CREATE TEMP TABLE learning_canonical (
    station_id VARCHAR(20) NOT NULL,
    snapshot_timestamp TIMESTAMP NOT NULL,
    available_bikes INTEGER NOT NULL
);

-- A retry has left two identical copies in landing.
INSERT INTO learning_landing VALUES
    ('123', '2026-10-14 12:00:00', 8),
    ('123', '2026-10-14 12:00:00', 8);

-- DISTINCT collapses identical copies; conflicting values need another policy.
CREATE TEMP TABLE learning_batch AS
SELECT DISTINCT station_id, snapshot_timestamp, available_bikes
FROM learning_landing;
```

**additions — `MERGE`:** `ON` identifies the logical observation. An existing match receives the same value; a new key is inserted. Replay the statement with unchanged `learning_batch` to see the same intended table contents. [Redshift MERGE reference](https://docs.aws.amazon.com/redshift/latest/dg/r_MERGE.html).

```sql
MERGE INTO learning_canonical
USING learning_batch AS b
ON learning_canonical.station_id = b.station_id
AND learning_canonical.snapshot_timestamp = b.snapshot_timestamp
WHEN MATCHED THEN UPDATE SET available_bikes = b.available_bikes
WHEN NOT MATCHED THEN INSERT
    (station_id, snapshot_timestamp, available_bikes)
VALUES (b.station_id, b.snapshot_timestamp, b.available_bikes);

SELECT station_id, snapshot_timestamp, available_bikes
FROM learning_canonical;
-- Expected after the first execution and an unchanged replay:
-- 123 | 2026-10-14 12:00:00 | 8
```

**additions — `NOT EXISTS`:** This alternative inserts only observations whose keys are absent. Unlike the update above, it leaves an existing value unchanged. After the merge, the following inserts zero rows. To try it independently, start with a fresh empty temporary target. Use one of these strategies for a given write policy.

```sql
INSERT INTO learning_canonical
    (station_id, snapshot_timestamp, available_bikes)
SELECT b.station_id, b.snapshot_timestamp, b.available_bikes
FROM learning_batch AS b
WHERE NOT EXISTS (
    SELECT 1
    FROM learning_canonical AS c
    WHERE c.station_id = b.station_id
      AND c.snapshot_timestamp = b.snapshot_timestamp
);

-- Expected: no rows. A returned group would indicate duplicate logical keys.
SELECT station_id, snapshot_timestamp, COUNT(*) AS copies
FROM learning_canonical
GROUP BY station_id, snapshot_timestamp
HAVING COUNT(*) > 1;
```

- `SELECT DISTINCT station_id, snapshot_timestamp, available_bikes` returns **two rows**: one with 8 bikes and one with 9. They are different complete rows, but they share the observation key `(station_id, snapshot_timestamp)`.

- `DISTINCT` also does not compare incoming rows with rows already stored in canonical. Inserting the same distinct source row on three runs can still append three target rows. Source deduplication and repeat-safe target writes solve different parts of the problem.

**additions — yes, with different write policies:** Both can help prevent repeated inserts when the match uses the correct logical key. Neither is a general command to clean all duplicates already present in a target.

| Situation | `MERGE` as written above | `INSERT ... WHERE NOT EXISTS` as written above |
| --- | --- | --- |
| Key is absent from canonical | Inserts the source row | Inserts the source row |
| Key already exists with the same value | Assigns the same value again | Skips the row |
| Key already exists with a different value | Replaces the count with the incoming count | Keeps the existing count |
| Typical policy | Accept authoritative corrections to existing observations | Preserve the first accepted observation as immutable |

The `WHEN MATCHED THEN UPDATE` clause gives this particular merge its update behavior; `MERGE` supports other policies too. [Redshift MERGE](https://docs.aws.amazon.com/redshift/latest/dg/r_MERGE.html).

- **Pitfall: duplicate source keys.** If a new key appears twice in the input, `NOT EXISTS` is not a uniqueness constraint: both source rows can qualify for insertion. For `MERGE`, multiple source rows matching one existing target row cause an error. Prepare one source row per logical key first.
- **Pitfall: the wrong match key.** Matching on `station_id` alone confuses different observation times. Including `available_bikes` in the key treats a corrected count as a new observation. Match on the columns that define identity.
- **Pitfall: replaying stale corrections.** An unconditional merge update can replace a newer accepted value with an older replayed value. Update only according to your documented version/authority rule. `NOT EXISTS` avoids that overwrite but also ignores legitimate corrections.
- **Pitfall: concurrent writers.** Two runs must not independently decide that the same key is new and accept conflicting work. Use the pipeline's concurrency/transaction strategy and retry handling; do not rely on an unenforced Redshift key declaration. [Redshift constraints](https://docs.aws.amazon.com/redshift/latest/dg/t_Defining_constraints.html).

For the original example, both approaches leave one row because the prepared source has one key, its value is unchanged, and there is one writer.

- **additions:** `USAGE` on a schema and table `SELECT` serve different purposes; neither substitutes for the other. Verify the actual database user before changing grants.
- **additions:** Stored procedures default to invoker security, so the caller needs underlying object privileges. A reviewed `SECURITY DEFINER` procedure uses its owner's privileges for its body; callers still need permission to invoke it. Do not assume `EXECUTE` always grants direct table access. See [procedure security](https://docs.aws.amazon.com/redshift/latest/dg/stored-procedure-security-and-privileges.html).


Required reading: [Amazon Redshift GRANT documentation](https://docs.aws.amazon.com/redshift/latest/dg/r_GRANT.html).

### 7. Infrastructure as code and recovery

Terraform describes and manages AWS infrastructure. Its state records which existing resources belong to a configuration.

Understand why Terraform state must be preserved, why importing existing resources differs from creating them, and why a plan showing unexpected replacements or destruction must be investigated before applying.

- State Preservation = this is important because it keeps track of your resources, this means if state is lost, then you might be using resources you no longer need or you might not have a full picture 

    - **additions:** Right concern. State maps Terraform resource addresses to actual remote resource IDs and records management metadata. Losing it does not delete AWS resources; Terraform can lose their ownership mapping. Configuration and state serve different purposes, so retain both appropriately.

- importing vs creating = importing can have data already associated with the resource, you don't want to empty or erase that. the resources might also have connections already made, you need to ensure those are handled correctly

    - **corrections:** Import adopts an already existing remote object into Terraform state. Creation provisions a new object. Import itself does not empty the resource, but later configuration differences can cause changes or replacement, so inspect the plan after import too. Data preservation matters for both. [Terraform import overview](https://developer.hashicorp.com/terraform/language/import).

- plan = this is why running plan before apply is important. For the reasons above, you don't want to lose data or break a pipeline that is already working

    - **additions:** Correct. Inspect which resource is replaced/destroyed and why. A successful apply establishes infrastructure changes, not successful ingestion, correct Gold results, or safe checkpoint recovery; those require execution evidence.

### Phase A — Data ingestion

Build a Lambda function that retrieves data from your source and writes it into your own S3 bucket.

### Phase B — Incremental Bronze-to-Silver

Create a Glue job that processes only the records eligible for the current batch.

Acceptance standards:

- The job receives or determines a processing boundary.
- It avoids scanning and transforming all historical data unnecessarily.
- It applies explicit schemas and appropriate data types.
- It removes duplicates using a documented logical key.
- It writes Parquet data into Silver.
- It produces identifiable batch output.
- It fails visibly when a required input or transformation is invalid.

An acceptable batch directory might look like:

```

```

### Phase C — Incremental Silver-to-Redshift

Create a second Glue job that loads the current Silver batch into a Redshift landing table.

Acceptance standards:

- The job loads the intended batch rather than the entire Silver history.
- Every loaded record can be associated with its batch ID.
- Redshift credentials are handled through an approved connection or IAM mechanism, not hardcoded in scripts.
- Loading failures cause the job to fail.
- Repeated staging loads cannot cause duplicate canonical or Gold records.

### Phase D — Canonical and Gold modeling

Create a canonical table and a small star schema.

Minimum requirements:

- One fact table.
- Two dimension tables.
- At least three useful analytical SQL queries.
- Documented fact-table grain.
- A deduplication strategy.
- Checks for duplicate business keys and orphan dimension references.

For Citi Bike, appropriate analyses include station utilization, availability by hour, and stations frequently reporting low availability.

For another dataset, select equivalent business questions.

### Phase E — Checkpoint management

Implement a mechanism that records successful processing progress.

You may use a Redshift checkpoint table, DynamoDB, or another justified approach.

Acceptance standards:

- A batch reads the prior completed checkpoint.
- Its input window is deterministic once the batch begins.
- A failed batch does not advance the checkpoint.
- A successful batch advances it only after the required downstream writes and checks complete.
- A retry can safely recover without duplicating final records.
- The pipeline has a documented policy for late-arriving data.

You do not need to backfill historical data. You may initialize the checkpoint when your pipeline first begins collecting data, provided you explain how that initial boundary is chosen.

### Phase F — Orchestration and scheduling

Implement a Step Functions state machine that runs the processing stages in order.

Acceptance standards:

- Each Glue job runs only after its predecessor succeeds.
- Task failures are visible in execution history.
- The workflow reaches a Succeed state only after Gold processing and checkpoint completion.
- A schedule starts the workflow automatically.
- The schedule interval is documented; 30 minutes is recommended for this assignment.
- Overlapping executions are prevented or safely handled through an explicit concurrency strategy.
- Retries are configured only where safe, and their behavior is explained.

### Phase G — Terraform

Use Terraform to manage at least the Step Functions state machine, scheduling resources, and the IAM roles and policies created for them.

You may also manage Lambda and Glue resources through Terraform.

Acceptance standards:

- `terraform fmt` succeeds.
- `terraform validate` succeeds.
- `terraform plan` is reviewed before applying.
- Terraform state is preserved between deployments.
- Existing resources are imported when appropriate rather than recreated.
- No unexpected resource destruction is present in the plan.
- Secrets and AWS credentials are not committed to source control.
