## Warehouse acceptance and orchestration

### Atomic warehouse acceptance

[Acceptance installation](sql/11-create-acceptance-procedure.sql) defines the now-installed accepted-batch ledger and `public.sp_richard_accept_citibike_batch`. The six inputs are batch ID, inclusive capture-window start, exclusive end, expected prior checkpoint, expected distinct landing-row count, and a required controlled-failure flag. Installation itself does not move progress; successful acceptance does. The initial test began at 15:50 UTC and advanced to 15:55; it has already been accepted.

The procedure uses Redshift's default atomic mode, locks the checkpoint/ledger/landing/canonical/Gold tables before reading state, checks the prior checkpoint and batch identity, deduplicates exact landing copies, rejects conflicting within-batch keys and invalid input, preserves insert-only canonical observations, updates touched stations from their latest canonical observations, inserts dates/facts without repeating keys, checks integrity/content agreement, and records acceptance plus checkpoint advancement. A matching accepted-batch replay returns without writes; a changed context or stale new batch fails. Call it as a standalone statement with autocommit enabled; do not introduce `COMMIT`, `TRUNCATE`, `NONATOMIC` or an error-swallowing exception handler. It now uses SECURITY DEFINER with fixed `search_path = pg_catalog` and restricted execution grants; the workflow's password-disabled IAMR database identity receives procedure execution rather than direct warehouse table writes. [Database grants](sql/14-grant-workflow-acceptance.sql) are separate from IAM Data API authorization.

[Acceptance tests](sql/12-test-acceptance.sql) document the original section-by-section exercise. Live tests are complete and include the [transactional repair](sql/13-repair-first-batch.sql): the intentional post-write failure rolled back cleanup and checkpoint/ledger writes; recovery repopulated valid canonical/Gold rows and advanced to 15:55; identical replay was a no-op. The malformed initial numeric load was repaired from existing Silver using the type-corrected loader. Silver count was independently confirmed as 2,518 from the original loader's CloudWatch output. An empty input is intentionally rejected until a verified-empty-window policy is implemented. Do not rerun the repair as a normal recurring pipeline step.

This warehouse lock serializes acceptance and blocks competing table writes during the transaction; it does not prevent two workflows from preparing/running Glue concurrently. Durable preparation/lease ownership, frozen source manifests and published Silver completion markers, late-data overlap/catch-up and automatic schedules remain separate pending work. Global integrity/content scans are conservative checks for this small lab; new transforms target the current batch/touched stations. Accepted batch identity assumes published input is immutable; manifest hashes or stronger replay-content verification are not yet implemented. Procedure compilation, controlled rollback/recovery/replay were executed live; overlapping-call behavior has not been load-tested.

Primary references: [Redshift procedure transactions](https://docs.aws.amazon.com/redshift/latest/dg/stored-procedure-transaction-management.html), [LOCK](https://docs.aws.amazon.com/redshift/latest/dg/r_LOCK.html), [CREATE PROCEDURE](https://docs.aws.amazon.com/redshift/latest/dg/r_CREATE_PROCEDURE.html).
