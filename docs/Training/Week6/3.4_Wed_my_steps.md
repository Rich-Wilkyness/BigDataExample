2. Here’s why we added each:

   | Table | Purpose |
   |---|---|
   | Landing | Receives a Glue batch before acceptance; retries may leave repeated rows here. |
   | Canonical | Keeps one accepted observation per station/capture pair. |
   | Station and date dimensions | Describe stations and dates for analysis. |
   | Snapshot fact | Stores availability measurements linked to those dimensions. |
   | Checkpoint | Records the processing boundary successfully completed through Gold. |
   | Accepted-batch ledger | Records which batch committed, so a retry can recognize prior success. |

3. Canonical is the most debatable extra layer here. It overlaps substantially with your fact table. A simpler design could deduplicate landing directly into the fact and update the dimensions in the same transaction. I should have explained that tradeoff before adding it.
4. For this homework, though, your teacher explicitly requires “Redshift landing → canonical → Gold fact and dimensions,” plus checkpoint management. That’s why we kept those separate. The accepted-batch ledger was our implementation choice for reliable retries; it isn’t an explicitly required table.
5. Think of two related paths:
   - Data: landing → canonical → dimensions/fact.
   - Control: accepted-batch ledger + checkpoint.
