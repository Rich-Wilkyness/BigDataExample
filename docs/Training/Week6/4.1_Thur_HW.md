### B. Window functions

Review these SQL functions:

- `ROW_NUMBER()` = 
- `RANK()` = 
- `LAG()`
- `AVG() OVER (...)`

> **addition**: Section B refresher — `OVER (...)` defines which related rows a window function examines. These examples are expression fragments for learning, not completed homework queries. 
>
> - `ROW_NUMBER()` labels rows 1, 2, 3, ... within each partition. Example fragment: `ROW_NUMBER() OVER (PARTITION BY station_id ORDER BY snapshot_timestamp ASC)`. For station A observed at 09:00, 09:05, and 09:10, this gives 1, 2, and 3. Numbering restarts for station B. Equal ordering values still receive different numbers, but their assignment is unpredictable unless the ordering uniquely identifies rows.
> - `RANK()` gives tied ordering values the same rank and leaves gaps afterward. Fragment: `RANK() OVER (PARTITION BY station_id ORDER BY bikes_available DESC)`. Measurements 8, 5, 5, 2 produce ranks 1, 2, 2, 4. This ranks observations within a station; it does not rank stations by their average availability.
> - `LAG(value, 1)` retrieves the previous row's value in the chosen sequence. Fragment: `LAG(bikes_available, 1) OVER (PARTITION BY station_id ORDER BY snapshot_timestamp ASC)`. For chronological values 8, 5, 5, the previous values are NULL, 8, 5. The first row has no predecessor. One previous row does not necessarily mean one previous hour.
> - `AVG(value) OVER (PARTITION BY station_id)` places the station's sample mean beside every observation instead of collapsing them into one summary row. For values 8, 5, 5, the mean is 6 on all three rows. Use `AVG(CAST(bikes_available AS DOUBLE PRECISION))` when fractional results matter; Redshift's integer-input AVG returns an integer type.
> - To learn a moving average, examine this fragment: `AVG(CAST(bikes_available AS DOUBLE PRECISION)) OVER (PARTITION BY station_id ORDER BY snapshot_timestamp ASC ROWS BETWEEN 1 PRECEDING AND CURRENT ROW)`. Its outputs for 8, 5, 5 are 8, 6.5, 5. `ROWS BETWEEN` selects the previous and current observations; the first row has only itself. Redshift requires an explicit frame when an aggregate window includes `ORDER BY`.

Pay particular attention to `PARTITION BY` and `ORDER BY` inside window functions.
- Partition By = very similar to group by, you provide a column that will be used to create partitions. if we use station_id as the partition and we have 6 stations, there will be 6 partitions, this is where you can run into hot keys or shuffle issues. If one station has 10x the amount of rows, but in our citibike situation that shouldn't happen, as each row is an hour of the day, with 24 rows per day per station.

> **correction**: Six distinct station IDs do define six logical window partitions. `GROUP BY` reduces rows to summaries; window `PARTITION BY` retains individual rows. These logical groups are not a promise of six physical workers or Spark storage partitions. Uneven groups can affect performance, but confirm actual sampling and missing/duplicate records before assuming 24 observations per day; the declared grain is station plus timestamp, not station plus hour. See [Redshift window concepts](https://docs.aws.amazon.com/redshift/latest/dg/c_Window_functions.html).
- order by simply orders data in ascending or descending alphanumeric order, based on the column(s) selected

> **addition**: Sorting follows the column's data type: numbers numerically, timestamps chronologically, and text as text. Inside `OVER`, ordering controls the calculation's sequence; a final query `ORDER BY` controls displayed results. `ASC` is earliest/smallest first, and `DESC` is latest/largest first. Decide how NULL timestamps should be treated; in Redshift, descending ordering places NULL first unless you specify otherwise.

Learn how Amazon Redshift's `QUALIFY` clause can filter the results of a window function.
- all i remember is that qualify is similar to having and where, but for window functions? 

> **addition**: Yes. `WHERE` filters input rows, `HAVING` filters grouped results, and `QUALIFY` filters after window results are calculated. A window function cannot be used directly in the same query level's `WHERE`. If `QUALIFY` immediately follows `FROM`, Redshift requires an alias for that relation. See [QUALIFY](https://docs.aws.amazon.com/redshift/latest/dg/r_QUALIFY_clause.html).

**Think about:** How could you retrieve only the most recent observation for each station?
```sql

FROM gold.fact_station_snapshot
```

## Part 3 — Reading: Introduction to Amazon Bedrock

**Estimated time: 15 minutes**

Amazon Bedrock is an AWS service that provides access to foundation models through managed APIs.

Unlike training a model from scratch, an application can send instructions and context to an existing model and receive a generated response.

Our classroom demonstration used Bedrock to translate questions about Citi Bike data into Redshift SQL.

Review these concepts:

**1. Foundation models**

What is a foundation model, and how does it differ from a traditional application with explicitly programmed rules?
- LLMs can turn human readable conversation into explicit code. 

> **addition**: A foundation model is broadly pretrained on large datasets and can be adapted or prompted for multiple tasks. LLMs are language-focused examples; foundation models can also handle images, audio, and other modalities. The category exists beyond Bedrock; Bedrock is one service for accessing models. Generating code from natural language is one capability, not the definition. Traditional rule-based code follows developer-written rules; a model learns patterns during training and uses them at inference time, so its output is not guaranteed correct.

**2. Prompt engineering**

How can instructions and examples influence the SQL a model generates?
- we can pre-prompt the LLM with things like our database models to provide a smaller chance of halucinations, because it now knows what data we are working with when prompted.
- we can also define how we would like the response/output, like asking for numbered, tables, or even SQL output

> **addition**: Both points are sound. Examples can also show the desired SQL dialect, join relationships, and result grain. Providing schema in a prompt supplies context for that request; it does not retrain the model or enforce that its output uses only valid columns.

**3. Context and schema grounding**

Why is it important to provide the model with the actual database tables, columns, and relationships?
- mentioned above, but provides less opportunity for the LLM to halucinate 

> **addition**: Include data types, keys, row meaning, timestamp conventions, and business metric definitions as well as column names. Real columns can still be combined incorrectly: a join that duplicates observations may execute successfully while giving the wrong answer.

**4. Hallucinations**

Why might a model generate SQL referencing columns that do not exist?
- because it wants to try and provide an answer, so it halucinates an answer

> **correction**: “Wants to answer” is a useful shorthand, but the model generates likely output from learned patterns and supplied context; it does not automatically verify your catalog. Missing or stale schema, ambiguous questions, and familiar naming patterns can lead to invented column names even in confident-looking SQL.

**5. Human approval**

Why should generated SQL be reviewed before execution?
- you could run up an expensive bill potentially, or leak confidential data

> **addition**: Those risks are valid. Also review whether the SQL answers the intended question: correct tables, joins, time range, grain, and metric meaning. Human approval should be supported by database permissions and application validation; approval alone does not prove correctness.

Suggested reading:

- [Amazon Bedrock — Getting started](https://docs.aws.amazon.com/bedrock/latest/userguide/getting-started.html)
- [Amazon Bedrock — Converse API](https://docs.aws.amazon.com/bedrock/latest/userguide/conversation-inference-call.html)

## Part 5 — Conceptual Questions: AI and Data Engineering

**Estimated time: 10–15 minutes**

Answer each question in approximately 2–4 sentences.

1. Why does a text-to-SQL application need information about the database schema?
    - so it doesn't halucinate columns. If it knows the columns it is more likely to provide SQL that will work.

> **addition**: Correct direction. Extend this with relationships and grain: valid column names alone cannot prevent a wrong join or an incorrect aggregation. Schema context reduces guessing but does not guarantee accuracy.
2. What should an AI system do when a user asks a question requiring data that doesn't exist in the database?
    - say that it doesn't exist or provide an error.

> **addition**: Prefer an explicit explanation of the missing table, field, or evidence and a clarification request where useful. Distinguish “the database does not store trips” from “a valid trip query returned no rows.” A generic error gives the user less help; inventing data would be worse.
3. Why is a database's fact-table grain important when generating SQL?
    - It makes joining tables easier and more intuitive for LLMs to connect the data. Grain definition can also make queries more or less meaningful.

> **correction**: The central role of grain is to define what is being counted or measured. If a row means one station observation, counting rows counts observations; it does not count trips. Grain also helps identify valid join cardinality and prevent double counting. Use one concrete example when revising your answer.
4. What is the difference between an SQL syntax error and a hallucinated column name?
    - syntax error -> the SQL was written incorrectly, but the column names can be correct.
    - hallucination -> the SQL can be correct, but the column does not exist.

> **addition**: Your distinction is right if “correct” means syntactically well formed. A nonexistent column is a name-resolution error during database analysis, even when the parser accepts the SQL's structure. A misspelled column can produce the same database error without being an AI hallucination; hallucination describes the unsupported generation, not a unique database error type.
5. Why might a developer choose a smaller, less expensive foundation model for a SQL-generation application?
    - it is cheaper to use and generating SQL is a simple process when provided the schema(s). You would want to run some tests to figure out which handles errors/hallucinations the best per dollar and what your limit is. like less than 1% hallucinations might mean you don't have the smallest/least expensive model, but also not the most expensive. 

> **correction**: Your evaluation-based choice is strong, but SQL generation is not always simple: multi-table joins, time windows, ambiguous metrics, and missing information require reasoning. Evaluate representative questions for correct results and appropriate refusal/clarification, as well as syntax, latency, and cost. “Less than 1% hallucinations” would be a proposed acceptance target measured on a defined test set, not an established property of a model.
6. What are the advantages of separating SQL generation, user approval, query execution, and result interpretation into distinct steps?
    - it follows CLEAN principles, making it easier to maintain, debug, and understand. If failure happens, you can isolate it to which step it occured and can easily read the code without needing to detangle logic.

> **addition**: Those maintenance benefits are correct; “separation of concerns” is the precise principle. Separate steps also make it possible to review the exact SQL before execution, record approval and execution outcomes, retry generation without rerunning a query, and ensure explanations use the returned results. If a query changes after approval, it needs review again.
7. Why should the database credentials used by an AI application have read-only permissions?
    - you don't want AI to accidentally delete/change the data. AI can be unpredictable, so it's safest to limit it's capabilities.

> **addition**: Correct. The application executes SQL using its database identity, so that identity should have only the reads its task requires. Read-only access prevents permitted writes but can still expose sensitive rows or run costly queries; scope readable objects/data and bound execution too.
