## Overview and learning objectives

A useful analytical answer depends on reliable data before it depends on a model. Follow this walkthrough alongside the expanded [Thursday lecture](4_Thur_AI.md) and the [lab file map](4.3-thur-bedrock-streamlit-lab/README.md). You will trace a question through schema context, Bedrock SQL generation, human review, validation, Redshift execution, explanation, and optional repair with renewed approval.

The [Thursday assignment](4.1_Thur_HW.md) makes pipeline progress the highest priority and does not require building an AI application overnight. This guide supplies setup and diagnostic plumbing. Your transformations, Gold model, analytical exercise SQL, and conceptual answers remain yours to write. Reading and offline verification can proceed while your pipeline is incomplete; live warehouse questions wait for readiness.

After these checkpoints, you should be able to identify which file owns each action, distinguish AWS authentication from database permissions, recognize incorrect result grain, explain the limits of parsing and sampled explanations, and stop the resources you actually use.

## Mental model, ownership, and prerequisites

The pipeline owns authoritative records: source → scheduled ingestion → S3 Bronze → Glue Silver → Glue landing → canonical → physical Gold facts/dimensions. Step Functions coordinates processing and accepted checkpoint progress. The UI consumes those records; a model cannot repair missing ingestion, duplicated facts, or premature checkpoint advancement.

The AI path is question + saved schema → Bedrock proposal → editable SQL → explicit approval → SQLGlot validation → Redshift Data API → bounded rows → Bedrock explanation. Local Streamlit still calls AWS for inference and warehouse reads. Questions, schema, SQL, error text, and up to 50 returned rows can be sent to the configured model. Use data approved for that boundary.

You need basic SELECT/JOIN/keys/timestamps, the [Wednesday guide](3_Wed_Step_Functions.md), Python with a virtual environment, and the lab dependencies. AWS credentials and a ready warehouse are required only for live steps. The home map reads public GBFS independently; a working map does not prove warehouse readiness.

All terminal blocks below assume macOS/zsh. Start at the repository root and keep the same shell for configuration and launch. Placeholders beginning `YOUR_` require replacement. There is no `.env` loader in this application.

## Where RAG and vector search would fit

The supplied demo implements **no document ingestion, embeddings, vector index, similarity retrieval, or Bedrock Knowledge Base**. It loads the complete schema text directly and queries structured warehouse tables. Calling Redshift and sending rows to the model does not establish a vector-based RAG implementation.

A later document-RAG path could index approved data dictionaries, business definitions and operational documentation; retrieve relevant passages for a question; then place those passages alongside verified schema context before generation or explanation. Vector search compares embeddings to find related passages; it does not train the model or validate SQL. Metadata filters and source citations help restrict and inspect retrieved evidence, while current schema and reader permissions remain separate boundaries. This is an extension to design after pipeline readiness, not another deployment checkpoint here. See [Bedrock Knowledge Bases](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base.html).
