# Deployment source review — reference only

No deployment script, remote SSM command, bootstrap or Terraform operation was executed. Shell checks use `bash -n`, which parses without running commands. Treat all files here as historical source until the following gaps are resolved.

| Source | Finding | Consequence / required work |
| --- | --- | --- |
| `deploy-chatbot.sh` | Downloads, compiles, backs up and installs the home app, Bedrock helper, schema, requirements and AI page, but omits `redshift_query.py` everywhere. | A fresh host cannot import the AI page; an existing host may silently retain an incompatible helper. Include/check/backup/install the complete application as a versioned set in any future deployment. |
| `deploy-chatbot.sh` | Positional arguments are used without a usage check; assumes AWS CLI, existing writable app directory, venv, S3 objects, privileged systemctl access and existing service. | It is an update script for a particular Linux host, not macOS setup or a fresh deployment. |
| `deploy-chatbot.sh` | Installs dependencies in the live venv before publishing files; individual installs then restart; no automatic rollback or application request check. | Staging and backups do not make updates atomic. A failed pip install/restart can leave mixed dependencies/code. `systemctl status` alone does not prove the AI page works. |
| `ssm-chatbot-v2.json` | Adds Redshift helper deployment but omits home app/schema provisioning and installs only SQLGlot despite replacing requirements. | Useful evidence of the omitted helper; insufficient as a fresh install or complete dependency upgrade. |
| `ssm-prompt-update.json`, `ssm-sql-repair.json` | Replace subsets of files and restart a hardcoded service. | They assume compatible prior installation. Executing fragments in an arbitrary order can produce mixed application versions. No sequence is certified by the local bundle. |
| `dashboard-user-data.sh.tftpl` | Embeds only `app.py` and `requirements.txt`. | Fresh EC2 boot launches only the map/history application. AI page, Bedrock helper, Redshift helper and schema are absent. Bootstrapping requirements does not provision SQL tables/grants. |
| `dashboard.tf` | Defines a dynamic Amazon Linux AMI data lookup, but instance uses literal `ami-0938c21410d9519c6` instead. | AMI validity/architecture/region were not checked. The lookup does not select the actual boot image. |
| `dashboard.tf` | Requires a default VPC/default subnet; takes first sorted subnet and assigns public IP. | Default subnet availability, route/Internet access, package downloads and AWS/GBFS reachability are unverified. Data API access does not require a direct browser-to-Redshift JDBC connection. |
| `dashboard.tf` | CIDR validation only checks parseability; description says never use `0.0.0.0/0` but validation allows it. URL is HTTP on 8501; no UI login/TLS configured. | Source intent is narrower than enforced behavior. Public classroom hosting needs a reviewed access boundary. This lab does not deploy it. |
| `dashboard.tf` | Bedrock invocation and Data API statements use broad `Resource = "*"`; Serverless credentials cover any workgroup in instructor account/region. | Supplied policy is not a scoped learner policy. Review applicable IAM resource support, intended model/profile/workgroup, boundaries and SQL reader privileges before reuse. |
| `dashboard.tf` | Template change can replace EC2 (`user_data_replace_on_change = true`); default Redshift enabled; IAM role has generated name. | Changes affect resource lifecycle and database identity. Terraform cannot create missing SQL grants merely by attaching this IAM policy. |
| `main.tf`, `orchestration.tf`, `scheduler.tf` | Hardcoded instructor profile/account/resource names, coordinator packaging and enabled schedule. Missing warehouse SQL objects/grants and Glue definitions. | Applying the directory could modify instructor resources or start scheduled work. It is context, not a standalone Thursday project or Richard migration. |
| Instructor `README.md` | Claims no schedule and cleanup removes only state machine/role/log group, despite current combined directory including schedule, coordinator and dashboard. | Its deploy/destroy instructions do not describe this bundle's actual resource scope. Preserve it as an original; never use that cleanup claim to authorize destroy. |
| `coordinator.py` | Up to 105 polls with two-second sleeps, no timeout cancellation; prepares overlapping windows without an execution lock. | Source describes coordination but does not prove safe concurrent writers, completion after lost replies or transactional checkpoint advancement. Procedure source and execution evidence are still missing. |

The scripts hardcode `s3://citi-bike-nyc-pipeline/scripts/dashboard`, `us-east-2`, `/opt/citibike-dashboard`, and `citibike-dashboard.service`. Those are instructor deployment coordinates. Existence, contents, object versions, instance/service status and SSM access were not checked. The source hashes in this lab identify local snapshots only; the scripts download mutable S3 paths without comparing those hashes.

A future deployment review needs a complete artifact set, pinned/tested dependency environment, scoped target identity, database reader grants, host/network/access decisions, an atomic release and rollback approach, and actual end-to-end smoke checks. Preparing those cloud changes is outside this task. The Richard folder supports local study and does not include a repaired remote installer or Terraform stack.
