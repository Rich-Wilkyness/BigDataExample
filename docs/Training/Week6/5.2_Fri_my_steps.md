## Goal and application flow

Extend the existing AWS pipeline with a local Streamlit dashboard and an AI page that generates SQL, lets me review it, queries Redshift, and explains the returned results.

```text
Question in Streamlit
        |
        v
Bedrock generates SQL using the saved Gold schema
        |
        v
Review or edit the SQL
        |
        v
Redshift executes the approved query
        |
        v
Streamlit displays the results
        |
        v
Bedrock explains the actual results
```

The home page has two data paths: its live map reads the Citi Bike API directly, while its history button reads stored observations from Redshift. The AI page queries the stored Gold model. A live map and stored warehouse data can have different timestamps.

This implementation provides schema-grounded text-to-SQL and result-grounded explanation. Embeddings, vector search, and document retrieval are separate extensions; they are not part of the application built in these steps.

## Step 3 — Verify local Bedrock access

Redshift access and Bedrock model invocation are separate permissions. Test Bedrock from the repository root:

```bash
.venv/bin/python - <<'PY'
import boto3

client = boto3.client("bedrock-runtime", region_name="us-east-2")

response = client.converse(
    modelId="us.amazon.nova-micro-v1:0",
    messages=[{
        "role": "user",
        "content": [{"text": "Reply with: Bedrock connection works"}],
    }],
    inferenceConfig={"maxTokens": 32, "temperature": 0},
)

for block in response["output"]["message"]["content"]:
    if "text" in block:
        print(block["text"])
PY
```

| Piece | Meaning |
| --- | --- |
| `bedrock-runtime` | AWS client used to invoke the model |
| `modelId` | Selects the Nova Micro inference profile |
| `converse()` | Sends the messages and inference settings |
| `maxTokens` | Limits generated output tokens |
| `response["output"]["message"]["content"]` | Contains the model's response blocks |

The [Converse API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html) accepts messages and system instructions and returns model output and usage information.

**Observed response:**

```text
Bedrock connection works. If you need any further assistance or have additional questions, feel free to ask!
```

This confirmed a successful live model invocation from my local environment.

## Step 8 — Test the full question-to-answer flow

Use this question:

> How many distinct stations have stored observations?

| Action | What happens |
| --- | --- |
| Enter the question | Streamlit collects the user's request |
| Click **Generate SQL** | Bedrock receives the question, schema, and SQL instructions |
| Review or edit the SQL | Check table names, columns, aggregation, and intended result grain |
| Click **Query Redshift** | The helper checks the SQL structure, executes the query, and retrieves the result |
| Read **Redshift Results** | Streamlit displays the returned rows |
| Read **AI Answer** | Bedrock explains a sample of the actual returned data |

The application performs two separate model tasks: **generate SQL** and **explain results**. A successful query automatically triggers the explanation request. The helper returns at most 200 rows, and the explanation receives at most the first 50 rows.

If a query fails, **Repair SQL** asks Bedrock to propose a correction. The repaired SQL must be reviewed and submitted with **Query Redshift** again. Repair-path behavior is described by the inspected source; a live repair test was not recorded in this session.
