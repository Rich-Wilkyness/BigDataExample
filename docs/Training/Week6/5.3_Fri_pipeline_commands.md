## Trigger the pipeline

The current flow has two triggers:

```text
Invoke ingestion Lambda → API data lands in S3 Bronze
Start Step Functions   → PrepareBatch → Glue jobs → Redshift acceptance → release lock
```

Invoking the ingestion Lambda alone stops at Bronze. The current Step Functions workflow prepares its own window, checkpoint, row count, and frozen inputs through the PrepareBatch Lambda.

### Start processing with automatic preparation

After the ingestion response confirms success, start the existing workflow with an empty input object:

```bash
aws stepfunctions start-execution \
  --state-machine-arn arn:aws:states:us-east-2:866934333672:stateMachine:richard-citibike-incremental-workflow \
  --input '{}' \
  --region us-east-2 \
  --no-cli-pager
```

The new PrepareBatch Lambda reads the checkpoint, selects new captures, calculates the distinct observation count, freezes the inputs, and returns the arguments to Glue. You no longer need to construct the five-field input JSON. The archived `first-workflow-run.json` is historical evidence and must not be reused as a current input.

To preview the proposed batch without acquiring the lock, writing prepared objects, or running Glue:

```bash
aws stepfunctions start-execution \
  --state-machine-arn arn:aws:states:us-east-2:866934333672:stateMachine:richard-citibike-incremental-workflow \
  --input '{"preview":true}' \
  --region us-east-2 \
  --no-cli-pager
```

The command returns an execution ARN. Follow it in **Step Functions → `richard-citibike-incremental-workflow` → Executions**, or replace the placeholder below with that ARN:

```bash
aws stepfunctions describe-execution \
  --execution-arn 'PASTE_RETURNED_EXECUTION_ARN' \
  --region us-east-2 \
  --query '{status:status,output:output,error:error,cause:cause}' \
  --no-cli-pager
```

Wait for **`SUCCEEDED`**, then inspect the output. `NO_DATA` means there were no new captures and Glue did not run; `PREVIEW` means only preparation was inspected. A processed batch finishes after warehouse acceptance and lock release. See the [AWS execution reference](https://docs.aws.amazon.com/cli/latest/reference/stepfunctions/start-execution.html) and [PrepareBatch guide](3.4-wed-incremental-pipeline/prepare-batch-guide.md).

| Execution result | Meaning |
| --- | --- |
| SUCCEEDED with output status READY and lock_release.Payload.status RELEASED | Processing and warehouse acceptance finished, then the lock was released |
| SUCCEEDED with PREVIEW | Proposed batch inspected; no lock or frozen-data writes, no Glue |
| SUCCEEDED with NO_DATA | No eligible captures; no Glue and no checkpoint advance |
| FAILED, TIMED_OUT or ABORTED | Inspect the failing state, lock owner, Glue output and ledger/checkpoint before recovery |

The run lock prevents overlapping participating executions. A failed run retains it for inspection; do not blindly retry Glue or clear the lock. Preparation is bounded to 14 days and 128 captures, with further size limits documented in the guide.

## Three useful Redshift queries

Run these in database **`dev`**. The `gold` schema is inside that database.

### What batches reached Gold, and how fresh are they?

```sql
SELECT
    batch_id,
    MIN(snapshot_timestamp) AS first_capture_utc,
    MAX(snapshot_timestamp) AS latest_capture_utc,
    COUNT(DISTINCT snapshot_timestamp) AS captures,
    COUNT(DISTINCT station_id) AS stations,
    COUNT(*) AS observations
FROM gold.incremental_fact_station_snapshot
GROUP BY batch_id
ORDER BY latest_capture_utc DESC
LIMIT 20;
```

This helps confirm that a new batch produced warehouse observations. One observation represents one station at one capture timestamp.

### Which operational stations had the fewest bikes at the latest stored capture?

```sql
SELECT
    s.station_name,
    f.snapshot_timestamp AS capture_utc,
    f.bikes_available,
    f.ebikes_available,
    f.docks_available
FROM gold.incremental_fact_station_snapshot AS f
JOIN gold.incremental_dim_station AS s
  ON f.station_id = s.station_id
WHERE f.snapshot_timestamp = (
    SELECT MAX(snapshot_timestamp)
    FROM gold.incremental_fact_station_snapshot
)
  AND f.is_operational = TRUE
ORDER BY f.bikes_available, f.docks_available DESC, s.station_name
LIMIT 20;
```

The timestamp shows how current the stored availability is. This selects stations present in the latest network capture; stations absent from that capture are excluded.

### How did network availability change between captures?

```sql
SELECT
    snapshot_timestamp AS capture_utc,
    COUNT(*) AS operational_stations,
    SUM(bikes_available) AS bikes_available,
    SUM(docks_available) AS docks_available,
    SUM(CASE WHEN is_empty THEN 1 ELSE 0 END) AS empty_stations,
    SUM(CASE WHEN is_full THEN 1 ELSE 0 END) AS full_stations
FROM gold.incremental_fact_station_snapshot
WHERE is_operational = TRUE
GROUP BY snapshot_timestamp
ORDER BY snapshot_timestamp DESC
LIMIT 100;
```

Compare station coverage alongside the totals. These are availability snapshots; they do not measure trips or rentals.
