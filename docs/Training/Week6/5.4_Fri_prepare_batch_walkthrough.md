# Friday walkthrough: build and deploy automatic batch preparation

> Level: Beginner to intermediate. Starting point: Richard's deployed incremental S3 → Glue → Redshift workflow. Implementation status: deployed and tested on 2026-10-19. This walkthrough reconstructs that change; its commands were not rerun merely to write this document.

## Overview

The existing pipeline needed five manually prepared inputs before it could process a capture. This change makes the workflow calculate those inputs, preserve the exact source files it counted, and reserve ownership while processing them. The warehouse acceptance procedure remains responsible for committing progress.

The resulting manual flow is ingestion Lambda → start Step Functions with `{}` → PrepareBatch → two Glue jobs → warehouse acceptance → lock release. EventBridge and an ingestion completion marker remain a later checkpoint.

This is an extension of an existing pipeline, not a complete first-time AWS account or warehouse build. The bucket, ingestion Lambda, two incremental Glue jobs, Redshift connection/workgroup/tables/procedure, and Terraform state already existed. Start with the [pipeline README](3.4-wed-incremental-pipeline/README.md) for those prerequisites. For routine startup use [5.3 Friday pipeline commands](5.3_Fri_pipeline_commands.md); for presenting the graph use the [Step Functions guide](3.4-wed-incremental-pipeline/step-functions-presentation-guide.md).

## Learning objectives

After following the checkpoints, explain how to:

- Convert an accepted warehouse boundary and raw captures into a fixed processing batch.
- Separate a workflow lock, frozen manifest, accepted-batch ledger and checkpoint.
- Package a Lambda, declare its resources in Terraform, and grant the two layers of warehouse access.
- Add a Lambda Task to an existing state machine while preserving downstream JSON fields.
- Review a plan, deploy it, and distinguish local checks from actual warehouse acceptance.
- Recognize an incomplete run and inspect it before retrying.

## Step 2 — Design the ownership and data contract

Decide which question each artifact answers before writing service calls:

| Artifact | Meaning | When it changes |
| --- | --- | --- |
| `control/citibike/incremental/active.json` | Current participating workflow owner | Acquire before preparation; release after confirmed acceptance or an empty window |
| Frozen batch JSON and manifest | Exact inputs chosen for this attempt | Create once before Glue reads them |
| `public.richard_citibike_accepted_batch` | Warehouse batch committed successfully | Inside warehouse acceptance |
| `public.richard_citibike_pipeline_checkpoint` | Accepted exclusive capture boundary | Inside the same acceptance transaction |

The batch grain is distinct `(station_id, snapshot_timestamp)`. Read the existing checkpoint as window_start and checkpoint_before. Choose source captures within `[start, requested_end)`, then set the proposed window_end to one second after the latest chosen capture. Count the selected observations, not a remembered station total.

A manifest lists frozen input URIs and source provenance. It is published after its frozen JSON files exist. It does not certify that Redshift accepted the data, and it is distinct from the future ingestion completion marker.

**Checkpoint:** Explain why releasing a lock does not move the checkpoint and why copying files prevents later source changes from altering this batch.

## Step 3 — Create the preparation Lambda source and offline checks

Implementation files:

| File | What to implement or inspect |
| --- | --- |
| [lambda/prepare_batch.py](3.4-wed-incremental-pipeline/lambda/prepare_batch.py) | Handler and BatchPreparer implementation |
| [lambda/test_prepare_batch.py](3.4-wed-incremental-pipeline/lambda/test_prepare_batch.py) | Offline source-selection, failure and ownership checks |
| [lambda/package.py](3.4-wed-incremental-pipeline/lambda/package.py) | Reproducible ZIP builder using the standard library |

Build the handler in these logical pieces:

1. Validate the action and workflow execution ARN. Accept an empty processing request and optional preview/window_end values.
2. For a normal preparation, acquire the S3 lock with a conditional write. A different active owner causes failure; there is no automatic lock expiry.
3. Read exactly one checkpoint through the Data API. Submission returns a statement ID, so poll the read until FINISHED before reading its result.
4. List status capture objects in the selected UTC day prefixes and filter by filename capture timestamps.
5. Read source objects conditionally using their listed ETags. Reject invalid IDs and conflicting observations; collapse exact duplicate observations when counting.
6. Require corresponding station metadata. Freeze each selected status JSON and the latest selected capture's metadata in this batch's control prefix.
7. Publish manifest.json last and return READY plus the generated workflow fields. Preserve an existing matching prepared manifest for the same execution.
8. For preview, perform reads/counting without locks or frozen-data writes. For no eligible input, return NO_DATA and release any normal-run lock.
9. For release, require matching execution ownership and conditionally change active.json to idle. Never update the warehouse checkpoint here.

Use the linked source as the complete implementation. The two Lambda actions are entry points into the same deployed function. The tests use fake service behavior and mocks; passing them does not establish live IAM, Spark or warehouse behavior.

```bash
.venv/bin/python -m unittest discover \
  -s "$CITIBIKE_LAB/lambda" \
  -p 'test_*.py' -v
```

The recorded implementation passed 16 checks. Review the individual test names so you know which failure and concurrency cases are simulated.

Preparation is intentionally bounded: 14 days between checkpoint and requested end, 128 status captures, 64 MiB of listed status data, 8 MiB per JSON object, and 200,000 observations. Smaller windows can bound dense catch-up work; if the checkpoint is more than 14 days behind with no eligible capture in an earlier window, empty runs do not advance it. That sparse-gap case needs an explicit recovery/design decision rather than repeated empty runs or a guessed checkpoint reset.

**Checkpoint:** Offline checks pass, and the code has no warehouse progress-write path.


The builder produces `terraform/.build/prepare-batch.zip` containing `prepare_batch.py` at the ZIP root. That matches the handler setting `prepare_batch.lambda_handler`. The archive uses a fixed entry timestamp so an unchanged source produces an unchanged archive hash.

The AWS SDK comes from the Lambda runtime; this package does not install additional dependencies.

## Step 7 — Update the state machine and invocation permission

Edit or inspect [workflows/incremental.asl.json.tftpl](3.4-wed-incremental-pipeline/workflows/incremental.asl.json.tftpl) and [terraform/step-functions.tf](3.4-wed-incremental-pipeline/terraform/step-functions.tf).

## Failure model, common pitfalls and recovery

| Symptom | What to inspect before the next action |
| --- | --- |
| ZIP/hash error during planning | Run the package builder; verify Terraform's artifact path |
| Lambda fails to read checkpoint | Check IAM API permissions, database identity/grants, and statement error/status separately |
| Pipeline busy | Read active.json and inspect its owning execution; a preview does not reserve processing |
| Missing metadata or conflicting source rows | Inspect that capture; preparation may have retained its lock and frozen partial input |
| Silver output already exists | Reconcile partial/completed output and execution state; automatic overwrite/resume is not implemented |
| Workflow fails after SQL submission | Inspect statement status, accepted ledger and checkpoint; submission may have committed |
| LockReleaseFailed | Acceptance already reported FINISHED; verify commitment before releasing the retained lock |
| Empty window | Expect NO_DATA; checkpoint is not advanced merely to skip unobserved time |

Do not add broad retries to the processing Tasks without a publication/recovery design. Warehouse rollback does not remove S3 output, and a landing retry can append copies. The lock stays active after failed processing, timeout or stop so the owner and outputs can be reconciled. The [PrepareBatch recovery guide](3.4-wed-incremental-pipeline/prepare-batch-guide.md#lock-ownership-and-recovery) documents the ownership-checked release action; it does not repair data.
