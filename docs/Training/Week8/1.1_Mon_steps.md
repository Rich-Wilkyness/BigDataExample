For your Azure Event Hubs hospital pipeline, there are numerous ways to shut down gracefully, ranging from pressing `Ctrl+C` to coordinating shutdown across an entire distributed streaming system.

The important distinction is that graceful shutdown means more than stopping the process. Ideally, the pipeline stops accepting new work, finishes processing events already in flight, commits offsets or checkpoints, closes connections, and exits without losing or duplicating events.

## 1. Ways to initiate a graceful shutdown

| #  | Method                   | Example                                     | Best use case                     |
| -- | ------------------------ | ------------------------------------------- | --------------------------------- |
| 1  | Keyboard interrupt       | `Ctrl+C`                                    | Local Python producer or consumer |
| 2  | SIGTERM                  | `kill -TERM <PID>`                          | Linux services and containers     |
| 3  | SIGINT                   | `kill -INT <PID>`                           | Terminal applications             |
| 4  | Application command      | Type `quit` or `exit`                       | Interactive applications          |
| 5  | REST shutdown endpoint   | `POST /shutdown`                            | Managed streaming services        |
| 6  | Stop file                | Create `/tmp/stop-producer`                 | Simple batch/streaming scripts    |
| 7  | Environment/config flag  | `shutdown_requested=true`                   | Configuration-driven workers      |
| 8  | Scheduled shutdown       | Stop after 10 minutes                       | Classroom demonstrations          |
| 9  | Event count limit        | Stop after 1,000 events                     | Tests and bounded simulations     |
| 10 | Idle timeout             | Stop after 60 seconds without events        | Temporary consumers               |
| 11 | Control message          | Send `{"type":"SHUTDOWN"}`                  | Message-driven applications       |
| 12 | Kafka control topic      | Publish shutdown instruction                | Distributed Kafka workers         |
| 13 | Consumer lag threshold   | Stop after backlog reaches zero             | Draining a queue                  |
| 14 | Kubernetes termination   | `kubectl delete pod`                        | Containerized deployments         |
| 15 | Docker stop              | `docker stop container-name`                | Containerized applications        |
| 16 | systemd stop             | `systemctl stop hospital-producer`          | Linux services                    |
| 17 | Airflow orchestration    | Stop/cancel a streaming task                | Orchestrated pipelines            |
| 18 | Azure deployment control | Stop Eventstream or associated processing   | Managed Fabric pipelines          |
| 19 | Lease expiration         | Worker voluntarily exits after losing lease | Distributed consumers             |
| 20 | Supervisor instruction   | Parent process signals child workers        | Multiprocessing applications      |

These are shutdown triggers. The application still needs to handle the trigger properly.

## 2. Graceful shutdown with `Ctrl+C` or SIGTERM

This is the first approach I'd demonstrate in your class.

Your existing Python producer uses an infinite loop. We can add signal handling so it finishes the current send operation before exiting.


## 3. Stop after a fixed number of events

Especially useful for your hospital training lab:

```
MAX_EVENTS = 100with producer:    for i in range(MAX_EVENTS):        batch = producer.create_batch()        batch.add(EventData(json.dumps(generate_event())))        producer.send_batch(batch)print("100 events sent. Exiting.")
```

This is a bounded producer rather than an infinite stream.

## 4. Stop after a fixed duration

```
import timedeadline = time.monotonic() + 300  # 5 minuteswith producer:    while time.monotonic() < deadline:        batch = producer.create_batch()        batch.add(EventData(json.dumps(generate_event())))        producer.send_batch(batch)        time.sleep(1)print("Five-minute simulation completed.")
```

Using `time.monotonic()` is preferable to wall-clock time because system clock adjustments won't affect the elapsed duration.

## 6. Stop using a control message

Kafka and Event Hubs both support application-defined control messages.

For example:

```
{
  "event_type": "CONTROL",
  "command": "SHUTDOWN",
  "target": "hospital-consumer-1"
}
```

Consumer logic:

```
if payload.get("event_type") == "CONTROL":    if payload.get("command") == "SHUTDOWN":        shutdown_requested.set()        return
```

The consumer's receiving loop should observe that shutdown flag and close the client from its controlling thread.

Important: Control messages are not guaranteed to reach every consumer instance. In Kafka, members of the same consumer group divide partitions among themselves. A control record on one partition may be seen by only one instance.

For distributed shutdown, use a dedicated control channel or coordinated control service.

## 8. Graceful shutdown in Kafka

Kafka has additional concerns: consumer groups, partition ownership, offsets, rebalances, and transactional producers.

### Kafka consumer shutdown

With `kafka-python`:

```
import signalfrom kafka import KafkaConsumerrunning = Truedef stop(signum, frame):    global running    running = Falsesignal.signal(signal.SIGINT, stop)signal.signal(signal.SIGTERM, stop)consumer = KafkaConsumer(    "patient-events",    bootstrap_servers="localhost:9092",    group_id="hospital-analytics",    enable_auto_commit=False,    consumer_timeout_ms=1000,)try:    while running:        records = consumer.poll(timeout_ms=1000)        for partition, messages in records.items():            for message in messages:                process_event(message.value)            # Commit after successful processing            consumer.commit()finally:    consumer.close()
```

For production code, ensure offsets are committed only for successfully processed records. A failure midway through a batch should not cause offsets for unprocessed records to be committed.

### Kafka producer shutdown

With `kafka-python`:

```
try:    for event in events:        producer.send("patient-events", event)finally:    producer.flush(timeout=30)    producer.close(timeout=30)
```

`flush()` waits for previously submitted messages to complete, subject to the timeout.

### Kafka Streams

In Java:

```
KafkaStreams streams = new KafkaStreams(topology, props);

Runtime.getRuntime().addShutdownHook(
    new Thread(() -> {
        streams.close(Duration.ofSeconds(30));
    })
);

streams.start();
```

This is the standard lifecycle pattern for a Kafka Streams application.

## 9. Graceful shutdown in container environments

For a Dockerized producer:

```
docker stop --timeout 30 hospital-producer
```

Docker normally sends `SIGTERM`, waits for the grace period, and then sends `SIGKILL` if the container hasn't exited.

For Kubernetes:

```
spec:
  terminationGracePeriodSeconds: 60
  containers:
    - name: hospital-consumer
      image: hospital-consumer:latest
      lifecycle:
        preStop:
          exec:
            command: ["/bin/sh", "-c", "sleep 5"]
```

The application must still respond correctly to termination signals. A `preStop` delay does not itself flush data or commit offsets.

## 10. Graceful shutdown in Spark Structured Streaming

This is particularly relevant to your Spark and Databricks teaching.

```
query = (    df.writeStream      .format("delta")      .option("checkpointLocation", "/checkpoints/hospital")      .start("/data/hospital"))# Later, after the required processing window:query.stop()
```

You can also wait for a bounded amount of time:

```

```

Spark checkpoints preserve progress across restarts, provided the streaming query and source/sink configurations remain compatible.

## The most important teaching distinction

Abrupt termination

`kill -9`

Process stops immediately. No application cleanup, no final flush, no orderly checkpoint.

Graceful termination

`kill -TERM`

Application receives a signal and can finish work, checkpoint, release resources, and exit.

Even graceful shutdown doesn't automatically guarantee exactly-once processing. Kafka and Event Hubs consumers can replay messages after failures; durable checkpoints, idempotent writes, and transactional processing are what make recovery safe.
